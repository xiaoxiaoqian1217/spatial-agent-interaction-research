# 研究方法与验证思路

> **2026-09-16 收敛版。** 研究方法围绕 **Context → Situation → Interaction Need → Interaction Strategy → Dynamic Map Interaction** 展开。当前阶段不以 LLM 为必要技术条件，优先采用显式上下文模型、规则/状态机和可解释的需求推理完成第一版闭环。

## 1. 总体研究路线

采用文献比较、业务任务分析、情境建模、规则/状态设计、交互机制设计、原型实现、专家评审及小规模对照研究。

```text
文献与任务分析
      ↓
Context / Situation 建模
      ↓
Interaction Need 定义与标注
      ↓
规则 / 状态转换与策略映射
      ↓
Dynamic Map Interaction 原型
      ↓
功能验证 + 专家评审
      ↓
用户对照实验
```

验证分三层：

1. **推理层**：情境识别、Need 输出和 Initiative 策略是否合理、稳定、可解释；
2. **系统层**：地图、调整、状态和反馈是否按设计正确运行；
3. **用户层**：动态组织是否改善理解、判断、介入和核查表现。

实现成功不等于用户效果；专家认可也不能替代用户实验。

## 2. 文献与任务分析

以情境感知、Situation Awareness、Mixed-Initiative Interaction、监督控制、空间交互、Adaptive/Intelligent Map 和 Dynamic UI 为主要文献线索。

任务分析关注：

- 用户目标与关键决策；
- 任务、平台、区域、路径及其关系；
- 运行时事件、风险、计划变化和执行证据；
- 用户何时只需理解，何时需要判断、控制或核查；
- Agent 何时应保持静默、主动告知、建议、征询或请求确认。

区分现场/日志事实、专家意见、文献依据和待验证假设，不用“单位尚未实现”证明学术空白。

## 3. Context 与 Situation 建模

### 3.1 Context 数据项

第一阶段优先纳入：

- Task：目标、阶段、计划、进度、约束；
- Agent / Platform：状态、当前任务、规划/等待/失败/接替等；
- Spatial：设备、区域、路径、目标点及空间关系；
- Event：异常、新要求、计划变化、反馈事件；
- Risk / Impact：风险和受影响对象/任务；
- Decision：是否存在候选方案、待确认项或权限边界；
- Evidence：已确认事实、最后报告、当前未知、后续计划；
- User Context：当前选区、查看对象、已提交调整和待确认动作。

### 3.2 Situation 表示

每个代表性任务片段记录：

```text
Context Facts
→ Current Task State
→ Trigger / Change
→ Affected Objects / Tasks
→ Risk / Impact
→ Decision State
→ Evidence State
```

第一阶段不要求复杂概率模型。先用显式状态、事件、有限状态转换和规则验证概念边界与覆盖性。

## 4. Interaction Need 的建立

Need 表示任务导出的交互支持需求，不代表用户真实意图。第一版采用：

- **Understand**：理解当前事实、位置、状态和变化；
- **Assess**：判断影响、风险、方案差异和后果；
- **Control**：决定是否介入、表达调整、确认关键动作；
- **Verify**：核查调整是否落实、结果是否符合要求、哪些仍未知。

### 4.1 Need 标注

先由研究者形成工作标签，再由业务专家独立标注、记录分歧并修订；作者自拟标签只算设计自检。四类 Need 是工作分类，允许多标签和多种可接受策略。标注至少记录：

- 情境描述；
- 主 Need / 次 Need；
- 是否需要主动打断用户；
- 合理的 交互方式；
- 判断依据与反例。

允许一个情境对应多个 Need，不强迫单标签。

### 4.2 第一阶段推理实现

第一阶段不使用 LLM。上下文模型、规则和状态机跨环节组合，具体对应见[框架第6节](framework.md#6-驱动机制的关系)。规则可以判断 Need、直接决定部分策略或检查权限；状态机可以描述任务和协作流程，二者不被限定在情境识别环节。

每条规则至少记录：标识/版本、输入条件、所需证据及有效时间、输出 Need 与对象、策略与操作、优先级、冲突处理、退出条件、适用范围和反例。未匹配或证据不足时保留基础态势与未知说明，不猜测任务完成或自动提升权限。多条规则合并后仍须检查策略冲突及视野保护。

规则设计集与保留测试集分开。先冻结模型、规则、策略和评分，再回放未用于修正规则的情境组合；在保留集上修改规则后，该批数据只能算开发数据，不能继续充当独立验证。

### 4.3 推理层验证

候选指标（统计单位和分母在实验前冻结）：

- 代表性情境覆盖率；
- 规则冲突率；
- 未匹配率；
- 状态转换正确率；
- Need 输出与专家标注的一致性；
- 交互方式与专家判断的一致性。

覆盖率以预先列出的情境及分支为分母，不以规则自身定义的事件集合自证覆盖；规则冲突与未匹配分别记录触发次数和占全部待决策片段的比例。Need 记录逐类漏判/误判和多标签一致性，不只报告一个总正确率。

如果规则在组合情境或跨任务泛化中表现出明确不足，再记录为后续引入学习方法/LLM 的动机，而不是现阶段预设结论。

## 5. Interaction Strategy 与原型

Interaction Strategy 分为：

### 5.1 Information Organization

组织当前事实、变化原因、影响、未知项、后续计划、候选方案和执行证据。

### 5.2 Spatial Visualization

动态决定地图中的：

- 视野与聚焦范围；
- 设备/区域/路径/目标点显隐；
- 原计划与新计划；
- 计划与实际轨迹；
- 风险和受影响范围；
- 候选方案对比；
- 地图对象与任务/变化/反馈联动。

### 5.3 Initiative Management

Mixed Initiative 作为交互策略的一部分，使用本文自定义的交互方式编号（不是标准自动化等级）：

- I0 Observe；
- I1 Inform；
- I2 Suggest；
- I3 Request；
- I4 Confirm。

“谁发起”与“谁有执行权限”分开记录。

## 6. 代表性协作情境与案例

继续使用以下协作情境作为覆盖检查：

| 情境 | 主要观察 |
| --- | --- |
| S1 目标委托与理解确认 | 初始目标与约束是否明确 |
| S2 正常执行与过程监督 | Understand，低干预监督 |
| S3 Agent 主动征询 | Assess / Control，主动权切换 |
| S4 用户主动调整 | Control，空间调整表达 |
| S5 异常处理与协同恢复 | Understand / Assess / Control |
| S6 结果确认与后续衔接 | Verify |

重点案例：

1. **异常后的自主接替**；
2. **新增区域后的主动调整**。

详细输入、分支、评分和反馈见 [design-traceability.md](design-traceability.md)。

## 7. 脚本冻结与评分

实验前冻结：

- 输入数据及来源；
- 事件触发时间；
- 当时可见证据；
- 正确/可接受的 Situation 与 Need 标注；
- 合理的用户操作集合；
- 预期界面策略；
- 评分表和终止条件。

评分原则：

- 理解题按状态、变化、原因、影响和未知项分别计分；
- 介入判断分别记录漏介入和误介入；
- 调整表达分别核对对象、区域和约束；
- 落实判断区分完整、部分、失败和未知；
- 操作耗时固定起止事件，未完成和超时单列。

## 8. 功能验证

功能验证覆盖：

- Context 更新与 Situation 状态转换；
- Need 与 Initiative 输出；
- 地图视野/图层/路径/对象变化；
- 调整输入和方案预览；
- 成功、部分落实、拒绝、失败和未知；
- 连续修改和迟到反馈归属；
- 历史事实、当前状态和后续计划区分。

用脚本真值、执行回执、观测或独立场景记录核对，不以界面自身标签自证正确。

## 9. 专家评审

专家评审重点回答：

- Context / Situation 是否遗漏关键业务因素；
- Need 分类是否能解释实际交互需求；
- 某情境下的主动交互方式是否合理；
- 地图信息和操作边界是否符合任务与权限；
- 是否存在规则冲突、过度打扰或漏提示。

专家意见用于修订规则和策略，不直接声称提升用户表现。

## 10. 用户对照实验

### 10.1 对照条件与资源安排

| 条件 | 机制 | 可回答的问题 |
| --- | --- | --- |
| B0 固定组织界面 | 数据实时更新，地图、任务列表、变化记录和操作入口组织固定；必要告警仍保留 | 动态组织整体是否优于固定组织 |
| B1 直接规则动态界面 | 使用完整情境和规则，直接选择信息、地图、操作与交互方式；无显式 Need 表示 | 合理的动态适配对照 |
| P 显式需求层方案 | 相同情境 → Need → 策略；策略仍可访问情境、权限和用户当前操作 | 显式需求层是否有增量价值 |

B0 不能称为静态数据界面，B1 不能弱化成只看单一事件的弹窗。三者共享任务事实、数据质量、Agent能力、业务操作、权限、安全告警、策略能力和结果证据；差别仅在信息组织和策略选择机制。B1 与 P 的规则设计投入、案例覆盖和调试条件须记录并尽量一致。

最小安排：先对 B1/P 做独立情境回放和专家盲评（隐去方案名称），比较策略适切性、依据完整性、未见组合表现与维护成本；再进行 B0/P 的小规模用户对照，验证整体交互效果。若要宣称需求层改善用户表现，必须增加 B1/P 用户对照，不能用 B0/P 替代。若 B1/P 输出交互一致，报告等效输出，并将比较限定为维护和追溯价值，不制造用户效果差异。

具体执行与记录约定见[对照协议](../experiments/protocols/context-driven-comparison.md)。

### 10.2 评价问题

**EQ1：** 情境与 Need 推理是否合理、稳定、可解释？

**EQ2：** 动态地图交互组织是否提高用户理解、判断、介入和核查表现？

**EQ3：** 相对 B1，显式 Need 表示是否改善策略适切性、解释依据或跨情境复用，并且新增复杂度是否值得？

### 10.3 用户指标

- 状态、变化、原因和影响理解正确率；
- 变化遗漏；
- 判断耗时；
- 漏介入 / 误介入；
- 对象、范围、约束错误；
- 落实判断正确率；
- 重复提交、错误确认和恢复操作；
- 操作耗时；
- 主观负荷、控制感、可用性和访谈反馈。

## 11. 持续运行与结论边界

| 方式 | 可支持结论 |
| --- | --- |
| 加速回放数小时事件 | 事件、状态和规则逻辑在所测序列下正确 |
| 系统实际数小时运行 | 系统持续运行和多次情境变化处理能力 |
| 短时人员实验 | 特定情境下的理解、判断和操作表现 |
| 人员实际数小时监督 | 对应条件下的长期使用表现 |

短时实验不能证明降低长期疲劳或改善长期警觉性。未覆盖长期人员使用时，应把“长时”限定为任务和系统运行特征。

## 12. 当前推进顺序

1. 补齐 IR1—IR5 的实际需求和权限依据；
2. 为两个重点案例建立 Context / Situation / Need 标注；
3. 建立第一版状态机和规则表；
4. 建立 Need → Information / Spatial / Initiative 策略表；
5. 低保真验证交互变化是否合理；
6. 实现最小原型；
7. 做推理层和功能验证；
8. 专家修订后冻结独立回放与用户实验，记录 B1/P 增量比较和 B0/P 整体比较各自的结论边界。
