# 研究方法与验证思路

> 2026-09-13 统一优化版，与 [研究问题](research-question.md)、[研究框架](framework.md) 和 [论文大纲](outline.md) 对齐。论文主线为长时空间任务中的人–多智能体协同交互；自主接替为核心验证场景，新增区域/任务变化为第二验证场景。

## 1. 研究路线与证据结构

采用以下研究路线：

> 文献比较 → 业务任务分析 → 交互机制设计 → 原型实现 → 专家/业务走查 → 功能验证 → 用户对照评价

三类证据分别回答不同问题：

1. **设计依据证据**：需求是否真实、机制是否有理论和已有研究依据；
2. **工程正确性证据**：状态、关联、事件和反馈是否按规则正确运行；
3. **用户效果证据**：用户是否因此更准确理解、介入和判断结果。

专家认可不能替代用户实验，实现成功也不能替代用户理解效果。

---

## 2. 文献与任务分析

主要理论与相关研究包括：

- 情境感知与自主系统监督；
- 不确定性与证据信息表达；
- Norman 行动模型；
- 混合主动交互；
- 可解释规划与计划差异；
- 多机器人/空间交互与地面站工效。

文献的作用不是直接推出控件，而是形成设计要求和比较基线。

任务分析按以下结构进行：

> 用户目标 → 关键判断 → 必要信息 → 可用操作 → 结果判断条件

对应 R1–R5：

- R1 理解进展与空间分布；
- R2 理解关键变化与后续安排；
- R3 准确表达空间调整；
- R4 理解影响并判断是否介入；
- R5 确认落实并衔接后续任务。

每项需求标注来源：文献、业务流程、专家/内部人员核查或待验证假设。

---

## 3. 从系统应用到验证场景

系统应用为操作员远程监督异构无人平台班组执行长时、广域任务。协作情境用于需求覆盖检查，验证场景用于原型和实验。

| 层次 | 内容 | 作用 |
| --- | --- | --- |
| 系统应用 | 长时空间任务监督与人–多智能体协同 | 定义论文边界 |
| 协作情境 | S1 目标委托、S2 正常监督、S3 Agent 征询、S4 用户主动调整、S5 异常恢复、S6 结果确认 | 检查需求覆盖 |
| 核心验证场景 | 设备失联/异常后的自主接替 | 验证理解、影响判断、必要介入 |
| 第二验证场景 | 新增区域/任务变化 | 检查机制跨场景复用 |
| 实验条件 | 合理/需修正、完全/部分落实、失败/未知、连续修改 | 构造可控真值 |

自主接替场景不研究接替算法本身；后台接替结果作为固定条件或场景输入。

## 4. 原型与专家/业务走查

原型实现 M1–M3：

- **M1 基于证据的任务状态与空间变化表达**；
- **M2 自主变化/决策的解释与影响呈现**；
- **M3 用户介入与执行结果追踪**。

至少形成一个从目标/空间要求、正常执行、关键变化、必要介入到结果确认的可运行流程。

原型明确区分：

- 真实后台接口；
- 真实业务数据；
- 固定脚本/事件模拟；
- 尚未实现能力。

专家/内部人员走查重点核查：

- 任务流程与权限是否符合实际；
- R1–R5 是否成立；
- “需要介入/不需要介入”的业务条件是否合理；
- 接替合适/需修正、部分落实/失败/未知等实验真值是否可接受；
- M1–M3 是否遗漏关键情形或引入多余操作。

专家评审支持设计合理性，不直接证明用户效果。

---

## 5. 功能与持续状态验证

通过可重复脚本验证系统在持续变化中的正确性，重点包括：

- 任务、设备、区域、路径映射；
- 当前状态与历史状态区分；
- 自主变化事件与空间对象关联；
- 用户调整与执行反馈关联；
- 成功、部分落实、拒绝、失败、未知；
- 连续修改和迟到反馈；
- 旧反馈不得覆盖新要求；
- 消息发送成功不得被当成任务落实成功。

真值来源于执行端回执、日志或事前定义的场景规则，不以界面自身标签自证。

关于“长时”的证据需严格区分：

| 方式 | 可以支持的结论 |
| --- | --- |
| 加速回放数小时事件 | 状态逻辑、事件处理和多次介入衔接能力 |
| 系统实际数小时运行 | 对应条件下持续运行能力 |
| 短时人员实验 | 特定任务条件下的理解、操作和判断效果 |
| 人员实际数小时监督 | 对应条件下长期使用表现 |

短时人员实验不能证明降低疲劳或提高长期警觉性。

## 6. 公平对照设计

### 6.1 主要评价：整体方案 A/B 对照

**主要用户实验比较整套交互方案，不把 M1、M2、M3 默认拆成三个独立实验。**

两组保持一致：

- 相同任务事实和场景；
- 相同 Agent/后台算法和执行能力；
- 相同地图和空间数据；
- 相同任务难度；
- 相同基本操作权限；
- 相同必要成功/失败信息。

基线采用合理常规方案，例如：

> 常规地图 + 任务列表 + 事件/变化记录 + 基本调整入口 + 必要执行反馈

本文方案在同样事实和后台能力基础上增加：

- M1 的任务—空间—变化组织及证据边界；
- M2 的自主变化原因和影响表达；
- M3 的调整要求与执行结果关联追踪。

不能通过故意删掉基线失败信息、地图定位或必要反馈来制造优势。

整体实验支持的是**整套方案效果**，不能据此声称某个单项机制独立有效。

### 6.2 可选特色机制实验

资源允许时，从 M1–M3 中选择一个相对已有方法最有差异、最值得验证的设计进行单项对照。例如：

- 空间影响显式关联 vs 普通事件通知；
- 调整要求—执行结果显式关联 vs 分散显示。

单项实验固定其他主要功能，只操纵目标机制。

如果没有完成该实验，则论文贡献表述保持为“整套协同交互机制及其整体实证”，不强行拆分独立因果贡献。

## 7. 评价问题与指标

### EQ1：任务过程与自主变化理解

评价用户是否更准确理解：

- 当前任务/设备/区域状态；
- 关键变化；
- 自主变化原因；
- 受影响任务、对象和空间范围；
- 后续安排。

指标示例：

- 任务事实题正确率；
- 关键变化遗漏率；
- 影响判断正确率；
- 判断耗时。

可以采用 SAGAT 式冻结探针思路，但自编题目明确称“任务事实探针”，不冒称标准 SAGAT 实验。

### EQ2：协同介入与结果确认

评价用户是否能够：

- 正确判断是否需要介入；
- 准确表达对象、范围和约束；
- 避免不必要否决/重复操作；
- 正确判断调整是否完全落实、部分落实、失败或未知。

指标示例：

- 对象/范围/约束表达错误率；
- 漏介入率；
- 误介入/误否决率；
- 重复提交/错误确认次数；
- 落实判断正确率；
- 介入和判断耗时。

后台实际结果与用户判断分别统计。

### 辅助评价

可记录：

- 主观工作负荷；
- 控制感；
- 信任/信任校准；
- 用户访谈；
- 操作次数和路径。

辅助指标不能替代 EQ1/EQ2 的客观任务指标。

## 8. 实验控制与分析

实验设计至少控制：

- 参与者经验；
- 场景难度；
- A/B 顺序；
- 接替是否合理；
- 是否需要人工介入；
- 调整是否完全落实/部分落实/失败/未知。

合理介入条件和评分规则需由业务专家事前核定，不能根据参与者结果事后修改。

同一参与者多次任务不能当成多个独立参与者。结果按参与者和情境报告正确性、错误类型、耗时及适当不确定性，不只报告总体平均值。

未发现问题的参与者也要纳入统计，不能只计算“成功发现者”的处理速度。

---

## 9. 结论边界

论文需要严格区分：

- **跨结果状态**：成功、部分落实、失败、未知；
- **跨协作情境**：监督、征询、主动调整、异常恢复等；
- **跨业务场景**：自主接替与新增区域；
- **跨应用推广**：其他无人系统或 Agent 应用。

两个验证场景能够支持“机制可跨部分任务变化复用”的证据，但不足以证明适用于所有无人系统或所有 Agent 应用。

无人员实验时，只能报告设计合理性和功能正确性，不能声称提升用户效果。

无人员长时实验时，不声称降低疲劳、改善长期警觉性或解决 out-of-the-loop。

---

## 10. 最小推进顺序

1. 核查 R1–R5 的业务来源、权限和结果判断条件。
2. 完成自主接替与新增区域两个场景的低保真交互流程。
3. 检查两场景是否真正复用 M1–M3，而非分别设计两套界面。
4. 实现最小原型并完成状态/反馈功能验证。
5. 通过专家/内部人员反例修订实验条件和合理操作集合。
6. 开展整体 A/B 对照。
7. 根据文献差异与整体实验结果决定是否增加一个特色机制单项实验。
8. 最后根据实际证据收敛论文贡献和创新表述。
