# 研究方法与验证思路

## 当前原则

论文重点是提出并验证面向长时空间任务的智能体交互机制，而不是追求大规模用户样本。

在实际条件有限的情况下，可以采用“文献研究 + 框架构建 + 交互原型 + 专家评审 + 小规模对照实验”的组合方式。

验证需要区分两类证据：

- **框架合理性证据**：说明五维是否定义清楚、覆盖关键需求、能够指导设计；
- **交互效果证据**：说明用户是否因此更准确地理解执行情况，并更正确地完成干预。

专家评审不能替代用户任务实验中的效果证据，界面提供了信息也不能直接等同于用户已经正确理解。

## 建议方法

### 1. 文献研究与相关工作比较

目标：建立理论基础，明确已有研究如何处理态势感知、自动化监督、人机协作、Agent 透明性、空间信息交互和动态干预。

主要产出：

- 相关工作分类；
- 关键概念定义；
- 长时空间任务相关设计问题；
- 代表性研究比较表；
- 已有方法覆盖范围与本文研究空间。

相关工作比较不应先预设“本文一定全面优于已有工作”，而应围绕执行过程呈现、任务与空间对象关联、中断后上下文恢复、动态干预和生效反馈等维度如实比较。

### 2. 五维框架构建

目标：说明五维不是任意命名或对常见原则的简单重新包装。

保留可追溯构建链：

**文献或任务观察 → 用户困难 → 设计需求 → 候选维度 → 合并、去重与修订 → 五维框架。**

每个维度至少需要记录：

- 来源于哪些用户困难；
- 对应哪些设计需求；
- 有哪些文献依据；
- 与其他维度的边界是什么；
- 通过哪些机制落实；
- 后续通过什么证据检查其合理性。

其中“连续性”需要特别说明其统一问题：帮助用户跨时间、跨执行阶段以及跨任务/地图视图维持对同一任务过程的上下文联系。

### 3. 交互原型

围绕五个设计维度实现可操作原型，而不是完整业务系统。

建议选取 2~3 个典型长时空间任务，使不同任务共同覆盖以下关键情境：

- 多阶段持续执行；
- 环境或计划发生变化；
- 用户离开执行过程后重新返回；
- 用户需要调整剩余任务范围、路线或约束；
- 修改可能成功、部分生效、被拒绝或因执行进度无法完全生效。

原型重点实现三类机制：

1. 执行信息组织与呈现，包括关键变化摘要和离开后返回的上下文恢复；
2. 任务与地图关联，包括任务、计划步骤与空间对象的持续关联，以及 Agent–Frontend 协同边界；
3. 动态干预与结果反馈，包括干预范围、影响说明、生效、部分生效、失败和恢复反馈。

#### Agent–Frontend 协同实现原则

原型区分三种前端职责：

- **前端规则**：已有业务结果足以唯一确定界面响应时，直接确定性呈现；
- **共享前端状态 / 上下文**：Agent 需要当前交互环境中的必要信息时，共享最小必要状态；
- **Frontend Tool / 前端交互能力**：Agent 的任务执行需要当前前端交互环境完成一次能力时，由 Agent 主动调用，并在后续任务需要时取得结果。

该划分用于验证机制能否实施和分析适用边界，不单独把 Frontend Tool 的存在作为效果变量，也不预设 Tool 相对规则具有普遍优势。

### 4. 专家评审

在难以获取大量真实用户时，可邀请少量具备相关经验的内部成员或领域专家进行结构化评审。

重点评估：

- 五维定义和边界是否清楚；
- 是否遗漏关键的长时空间任务需求；
- 信息是否足以形成正确态势认知；
- 信息是否过载；
- 离开后返回时的变化摘要是否覆盖关键上下文；
- 关键介入时机、对象和范围是否合理；
- 生效、部分生效、拒绝和失败反馈是否符合实际任务流程；
- Agent–Frontend 的规则、共享状态和前端能力边界是否可实施。

专家评审主要提供框架合理性、需求覆盖和设计可实施性的证据。

### 5. 小规模对照实验

实验围绕两个评价问题组织：

- **EQ1：** 相比基础交互，本文机制能否帮助用户更准确地理解 Agent 当前执行状态、关键变化及其后续影响？
- **EQ2：** 本文机制能否帮助用户正确实施任务调整，并准确判断调整是否真正生效？

#### 对比条件

两种方案保持以下能力尽量一致：

- 相同任务与任务事实；
- 相同 Agent 能力；
- 相同地图数据；
- 相同业务操作和可执行干预范围；
- 尽量一致的视觉复杂度和任务难度。

**基线方案**不是“只展示最终结果”。它应提供合理的传统 Agent 交互能力，例如：

- Agent 对话；
- 地图；
- 常规任务状态或进度；
- 与实验方案相同的基本业务操作和干预能力。

但不提供本文重点研究的机制，例如：

- 任务、计划和空间对象的连续关联；
- 离开期间的关键变化摘要；
- 计划变化前后的差异组织；
- 干预对象、范围和影响的明确表达；
- 提交、接受、部分生效、拒绝、实际生效等细粒度反馈。

**实验方案**在相同业务能力基础上加入第 4 节提出的交互机制。

这样的对照主要回答“本文的组织和协同机制是否有效”，而不是简单证明“有更多信息比没有信息好”。

#### EQ1：用户态势感知指标

围绕离开后返回、环境变化和计划变化等情境，以预设任务事实和实际执行状态为判断依据，可观察：

- 当前状态理解正确率；
- 关键变化识别正确率；
- 变化对目标或计划影响的判断；
- 下一步或后续影响判断；
- 离开后返回时的上下文恢复表现；
- 完成理解任务所需时间。

#### EQ2：人机协同控制指标

围绕执行中修改要求以及成功、部分生效或失败情境，可观察：

- 干预对象是否正确；
- 干预范围是否正确；
- 是否完成指定调整；
- 实际执行是否符合调整要求；
- 是否正确识别修改已生效、部分生效、被拒绝或未生效；
- 发现问题后是否采取合理的后续操作；
- 完成干预任务所需时间。

#### 辅助指标

可结合：

- 主观认知负荷；
- 主观控制感；
- 满意度；
- 结构化访谈。

这些指标用于解释用户为什么表现更好或更差，不替代 EQ1、EQ2 的客观任务证据。

### 6. 实验控制与结果解释

建议使用难度相近的任务，并安排不同使用顺序以降低学习效应。若样本较小，应将实验定位为探索性评估，根据实际样本量选择适当的描述统计或推断方法，不预写显著提升结论。

结果解释需要注意：

- 整套界面更有效，不能直接证明五个维度分别具有独立因果作用；
- 专家认为设计合理，不等于普通用户一定表现更好；
- 少量任务中观察到某种 Agent–Frontend 分工有效，不足以推出 Frontend Tool、共享状态或规则在所有系统中的普遍优劣；
- 用户表示“更有控制感”，不等于实际干预已经正确生效；
- 若研究用户信任，需要对照系统实际能力与用户判断，不能只使用满意度替代信任校准。

## 当前不建议作为主要验证方式

- 只用代码实现证明框架有效；
- 只统计大模型准确率；
- 只展示一个 Demo 后主观声称体验提升；
- 将“使用了 Frontend Tool”本身作为交互效果证据；
- 使用明显弱于实验方案的基线制造效果差异；
- 为追求样本量而使用与真实任务无关的大量普通用户。

## 最小可行验证方案

如果最终参与者较少，建议至少完成：

1. 通过文献和任务观察建立“五维形成链”，而不是仅逐项寻找文献；
2. 设计 2~3 个代表性长时空间任务，覆盖计划变化、离开返回和动态干预；
3. 实现能力相同但交互机制不同的基线方案和实验方案；
4. 邀请少量专家或内部领域成员完成框架与机制的结构化评审；
5. 邀请具备相近任务背景的参与者完成对照任务；
6. 使用 EQ1、EQ2 的客观任务指标 + 主观量表 + 访谈进行三角验证；
7. 明确记录失败情境、设计边界和不能从小样本推出的结论。

该方案比单纯做系统实现更能支撑“交互机制研究”的论文贡献，也能保持研究范围与当前可获得参与者条件相匹配。
