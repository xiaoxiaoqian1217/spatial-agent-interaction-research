# 研究方法与验证思路

> **研究起点补充：** 从用户逐步操作转向目标委托后，Agent持续产生多类过程输出。本文研究如何组织这些输出、支持用户理解并参与；长时空间任务是应用与验证背景，状态证据与数据关联服务于这一主线。

> **2026-09-14 题目与主体确认：** 采用《面向长时空间任务的人—智能体交互机制设计与实现》。研究主体为人与 Agent；多智能体内部协同为支撑能力。保留 M1—M3 及自主接替、新增区域两个重点案例。

> **整体定位（2026-09-14 更新）：** 工作题目为“面向长时空间任务的人—智能体交互机制设计与实现”。全文围绕执行理解、协同介入、执行衔接与反馈；自主接替和新增区域为重点场景，特色机制不预先指定为唯一创新。当前设计与评价入口：[需求—机制—实现—评价表](design-traceability.md)。

> 2026-09-13 对齐整体定位，对齐[论文大纲](outline.md)的G1/G2、M1—M3与EQ1/EQ2。以下为研究计划，不预写结果。

## 研究路线与证据

采用文献比较、业务任务分析、机制设计、原型实现、专家评审及小规模对照研究。理论解释问题，任务分析确定具体需求，原型实现机制，验证检验合理性、正确性及用户效果。

三类证据分别回答：设计是否覆盖需求并有依据；关联与状态是否按规则运行；用户是否更准确理解、操作及判断落实。专家认可不替代用户实验，实现成功不等于用户理解。

## 1. 文献与任务分析

以情境感知、Norman行动模型及混合主动交互为主要分析依据，结合监督职责、执行透明性和空间交互研究。比较已有方法的介入表达、范围约束、执行证据关联、不可回退动作及部分落实反馈。

按用户目标、关键决策、必要信息、可用操作和结果判断条件分析实际流程，区分日志观察、专家意见和待验证假设。原五维用作设计检查准则，不再证明五维完备性。

补充可解释规划、计划差异及不确定性表达的比较，分别对应变化四问与状态证据规范。沿用现有[计划证据](../literature/notes/planning-evidence-2026-09-13.md)及[状态证据](../literature/notes/supervision-evidence-2026-09-13.md)，按原文边界形成比较表，不把解释、时间戳或未知标记本身认定为创新。

## 2. 从系统应用到验证案例

系统应用为操作员远程监督异构无人平台班组执行数小时以上、地理分布的任务。典型协作情境是需求与覆盖检查单位，案例是实验载体。

| 情境 | 覆盖检查 | 主要观察 |
| --- | --- | --- |
| S1 目标委托与理解确认 | 目标和约束是否明确、是否需要补充或确认 | 初始理解与输入 |
| S2 正常执行与过程监督 | 进展、变化和后续安排是否清晰 | EQ1、常态操作成本 |
| S3 Agent主动征询 | 原因、选项、影响及确认是否清楚 | EQ1与EQ2 |
| S4 用户主动调整 | 对象、范围、约束及可修改部分是否明确 | EQ2表达与落实判断 |
| S5 异常处理与协同恢复 | 已落实、未落实或未知部分及后续处理 | EQ2判断与后续操作 |
| S6 结果确认与后续衔接 | 是否达到目标及已确认要求、是否还有未完成项 | EQ1与EQ2结果回顾 |

情境表是工作分类，不是独立实验变量或固定执行阶段。每个情境在协议中记录案例、输入、预期行为、指标和未覆盖部分；不能要求所有情境都开展等量人员实验，但需如实报告覆盖范围。

分别检查协作情境覆盖与成功、部分落实、拒绝、失败、未知等结果状态覆盖。一个道路封闭案例的不同分支不等于完整应用覆盖。优先包含正常任务过程、Agent征询、用户主动改变要求及异常恢复；具体案例数量取决于覆盖与资源，不为凑数量扩展业务。

### 脚本冻结与评分口径

以[两个重点案例的脚本工作稿](design-traceability.md#两个重点案例的脚本工作稿)为入口，将输入、触发、用户判断、操作、反馈和评分依据固定成可重复流程。脚本应记录版本、提问时点、当时可见证据及事前核定的合理操作集合；有多种合理操作时不强设唯一答案。

- 理解题：按固定问题逐项记录状态证据、变化原因、受影响对象与未知范围，分别报告正确数/有效题数；开放回答事前制定评分规则。
- 介入判断：需要介入的分支记录漏介入次数/该类机会数；无需介入的分支记录误介入次数/该类机会数。合法的查看和补充查询不自动计为误介入，业务截止条件事前确定。
- 调整表达：分别核对对象、区域和约束；预置区域按对象标识判断，自由绘制的几何容差在实验前确定。
- 落实判断：将用户对完整、部分、失败及未知的回答与当时可用执行证据对照；后台实际结果另列，不用事后信息把合理的未知回答判错。
- 操作耗时：固定起止事件，未完成或超时单列；查询、重复提交、错误确认及额外解释成本分别记录。

功能脚本检验最后报告与当前状态的区分、部分反馈和迟到反馈归属；用户对照检验是否真正减少误解。参与者分组、顺序与任务难度沿用第 7 节控制，不将多个分支当作独立参与者。

## 3. 原型与专家评审

实现M1信息呈现、M2协同介入、M3执行衔接与反馈，明确真实接口、实际数据与脚本模拟。至少形成从目标委托、过程监督到结果确认的可运行流程，并接入必要介入。

前端规则完成确定性响应，共享必要上下文，Agent确需前端操作时使用受控工具。前端操作完成与设备任务调整落实分别记录。

专家依据情境需求检查信息充分性、三项机制衔接、权限、落实依据和异常处理；记录反例及修订。重点是需求覆盖和可实施性，不要求专家认可人为设定的“五维理论”。

## 4. 功能、关联与持续运行验证

核查用户要求、计划差异与执行依据的关联，覆盖成功、部分落实、拒绝、失败、未知、连续修改与迟到反馈。用执行回执、观测或独立场景真值核对，不以界面自身标签自证正确。

记录调整是否被接受、何时开始按新计划执行、阶段或最终目标是否完成，不合并成单一成功状态。已发生动作不可通过回退对话撤销。

| 方式 | 可以支持的结论 |
| --- | --- |
| 加速回放数小时事件 | 事件处理和状态逻辑 |
| 系统实际数小时运行 | 对应条件下的持续运行和多次介入处理能力 |
| 短时人员介入实验 | 特定协作条件下的理解、操作和结果判断 |
| 人员实际数小时监督 | 对应条件下的长期使用表现，需独立记录分析 |

短时实验不能证明降低疲劳或改善长时警觉性，未覆盖长期使用时限制结论并审视题目表述。

## 5. 公平对照与可选特色评价

### 整体方案对照

背景比较分析传统逐步操作与Agent目标委托的职责差异；效果验证则固定后台Agent能力，比较合理常规交互与本文方案的信息组织和参与方式。两类比较承担不同作用，不以更强后台证明界面更好。

基线使用合理现有界面或有文献依据的方案。两组保留相同任务事实、Agent及执行能力、地图数据、基本操作和成功/失败反馈。本文方案增加情境化组织、对象与影响表达、调整要求与计划及落实依据的关联。

两组都保留必要时间戳、最后报告/未知提示、变化原因和已有影响信息；方案差异在信息组织、空间关联及上下文衔接。常规方案可使用清晰文案、同屏表格和变化记录。若这些简单方式已足够，报告无增益或额外负担；整体 A/B 不能分别证明四问结构或证据标识有效。

不要删掉基线必要的失败信息；记录信息可获得性、视觉复杂度和任务难度差异。若新增后台能力，单独说明并控制，不能归因于界面机制。

### 可选特色机制的针对性比较

不预先指定必须验证的单项创新。若选择关联反馈作为特色，资源允许时固定M1/M2其他主要功能，比较相同事实分别展示与显式关联到同一调整要求的展示，检查落实判断、部分落实发现及后续错误操作。

在Agent征询后调整、用户主动变更等不同来源或事件中检查机制，不仅测试道路封闭。包含易混淆的部分落实、反馈延迟和连续修改，同时保留普通成功条件，观察何时关联组织没有收益或反而增加负担。

只有整体对照时，结论限于整套方案；没有针对性比较不能宣称某项机制独立有效。数据关联本身也不构成新颖性，仍需与已有方法比较。

## 6. 指标与记录

| 评价内容 | 指标示例 | 判断依据 |
| --- | --- | --- |
| EQ1 执行理解 | 状态、变化、目标和空间影响判断正确性及耗时 | 任务事实、事前定义的合理影响条件 |
| EQ2 调整表达 | 对象、范围、约束错误，指定操作完成情况 | 预设要求与输入日志 |
| EQ2 后台结果 | 接受与实际执行情况，未落实范围 | 回执、观测或独立真值 |
| EQ2 用户判断 | 已落实、部分落实、失败或未知判断；重复提交、错误确认和恢复操作 | 用户行为与独立真值对照 |
| 辅助评价 | 操作成本、主观负荷、控制感、访谈 | 日志与规范实施的测量 |

后台结果与用户判断分别统计。未发现问题的参与者需报告，不只计算成功发现者的速度。预测题依据事前条件评分，不用随机未来结果反推错误。自编事实题不冒用标准SA测量名称，使用标准工具时按要求实施。

## 7. 实验控制、分析与结论边界

说明人员经验与目标用户匹配程度，平衡体验顺序，使用难度相当案例。样本、任务数和分析方法按目标及资源事前确定，同一人多次操作不当成独立参与者。

按参与者和情境报告正确性、错误与耗时及适当不确定性，不只报告总平均或有利结果。主观控制感不能替代实际落实，满意度不能替代信任校准。专家认为合理也不等于用户表现更好。

区分跨结果状态、跨协作情境、跨业务案例和跨应用的证据；一套界面更有效不证明所有准则独立必要，也不证明Frontend Tool普遍优于规则。无人员实验时只报告功能与合理性，不能声称用户效果。

完整需求—实现—指标关系见[设计追溯表](design-traceability.md)。若单位没有完整现有界面，用有依据的常规地图、任务列表、变化记录及编辑反馈构造合理基线，不能用无界面作对照。自主接替场景补充需要/无需介入条件，记录漏介入和误介入；判断规则由业务专家事前核定。

## 写作、设计与验证的迭代

先写引言和任务场景与需求工作稿，同时核查需求、比较空间交互方案并制作低保真原型。优先探索空间交互，但具体机制与创新判断保持开放。写作中的证据缺口反馈到调研，操作流程中的困难反馈到设计。结果和改善幅度在实验后填写。

如形成支撑交互的技术方法，另行记录方法差异及与用户问题的联系，按相同负载或事件条件比较响应延迟、状态正确性或恢复表现等相关指标。技术验证与用户评价分别报告，不能互相替代。

## 最小推进顺序

1. 撰写引言和任务场景与需求工作稿，同步核查系统工作过程，建立情境与需求表。
2. 完成需求—机制—实现—评价对应与交互流程。
3. 根据情境覆盖选取案例，实现原型并检查状态关联。
4. 以专家反例修订，开展合理的用户任务对照。
5. 资源允许时增加候选创新针对性比较及长时研究。
6. 依据实际覆盖和结果提炼贡献，不以案例演示代替整体论证。
