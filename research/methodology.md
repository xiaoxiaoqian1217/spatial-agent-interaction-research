# 研究方法与验证思路

> 2026-09-11 修订，对齐[论文大纲](outline.md)的G1/G2、M1—M3与EQ1/EQ2。以下为研究计划，不预写结果。

## 研究路线与证据

采用文献比较、业务任务分析、机制设计、原型实现、专家评审及小规模对照研究。理论解释问题，任务分析确定具体需求，原型实现机制，验证检验合理性、正确性及用户效果。

三类证据分别回答：设计是否覆盖需求并有依据；关联与状态是否按规则运行；用户是否更准确理解、操作及判断落实。专家认可不替代用户实验，实现成功不等于用户理解。

## 1. 文献与任务分析

以情境感知、Norman行动模型及混合主动交互为主要分析依据，结合监督职责、执行透明性和空间交互研究。比较已有方法的介入表达、范围约束、执行证据关联、不可回退动作及部分落实反馈，同时核查调整依据变化后的影响说明与重新确认方式。提交检查和版本记录作为工程支撑，不扩展为通用并发控制研究。

按用户目标、关键决策、必要信息、可用操作和结果判断条件分析实际流程，区分日志观察、专家意见和待验证假设。原五维用作设计检查准则，不再证明五维完备性。

## 2. 从系统应用到验证案例

系统应用为操作员远程监督异构无人平台班组执行数小时以上、地理分布的任务。典型协作情境是需求与覆盖检查单位，案例是实验载体。

| 情境 | 覆盖检查 | 主要观察 |
| --- | --- | --- |
| S1 目标委托与理解确认 | 目标和约束是否明确、是否需要补充或确认 | 初始理解与输入 |
| S2 正常执行与过程监督 | 进展、变化和后续安排是否清晰 | EQ1、常态操作成本 |
| S3 Agent主动征询 | 原因、选项、影响及确认是否清楚 | EQ1与EQ2 |
| S4 用户主动调整 | 对象、范围、约束及可修改部分是否明确 | EQ2表达与落实判断 |
| S5 异常处理与协同恢复 | 已落实、未落实或未知部分及后续处理 | EQ2判断与后续操作 |
| S6 结果确认与后续衔接 | 是否达到目标及已确认要求、是否还有未完成项 | EQ1与EQ2结果回顾 |

情境表是工作分类，不是独立实验变量或固定执行阶段。每个情境在协议中记录案例、输入、预期行为、指标和未覆盖部分；不能要求所有情境都开展等量人员实验，但需如实报告覆盖范围。

分别检查协作情境覆盖与成功、部分落实、拒绝、失败、未知等结果状态覆盖。一个道路封闭案例的不同分支不等于完整应用覆盖。优先包含正常任务过程、Agent征询、用户主动改变要求及异常恢复；具体案例数量取决于覆盖与资源，不为凑数量扩展业务。

## 3. 原型与专家评审

实现M1信息呈现、M2协同介入、M3执行衔接与反馈，明确真实接口、实际数据与脚本模拟。至少形成从目标委托、过程监督到结果确认的可运行流程，并接入必要介入。

补充大纲4.2.4的依据有效性判定，实际实现相关依赖检查、变化分类、保留有效输入与重新确认，并与同一调整记录关联。执行态势和回执可以模拟，判定与反馈不能只播放预制界面。核实修改能力、时间与标识、执行前复核及回传接口，缺失能力标为模拟或未覆盖。

前端规则完成确定性响应，共享必要上下文，Agent确需前端操作时使用受控工具。前端操作完成与设备任务调整落实分别记录。

专家依据情境需求检查信息充分性、三项机制衔接、权限、落实依据和异常处理；记录反例及修订。重点是需求覆盖和可实施性，不要求专家认可人为设定的“五维理论”。

## 4. 功能、关联与持续运行验证

核查用户要求、计划差异与执行依据的关联，覆盖成功、部分落实、拒绝、失败、未知、连续修改与迟到反馈。用执行回执、观测或独立场景真值核对，不以界面自身标签自证正确。

依据检查覆盖无关变化、相关但仍适用、需要重新确认、部分或全部不可行、必要依据不足，以及提交检查后至执行接受前的再次变化。事先独立定义输入、预期处置和允许继续的条件，统计相关变化检出率、无关变化误触发率与分类处置正确率，记录规则来源。版本变更不能直接作为冲突真值。

记录依据检查是否通过、调整是否被接受、何时开始按新计划执行、阶段或最终目标是否完成，不合并成单一成功状态。已发生动作不可通过回退对话撤销。

| 方式 | 可以支持的结论 |
| --- | --- |
| 加速回放数小时事件 | 事件处理和状态逻辑 |
| 系统实际数小时运行 | 对应条件下的持续运行和多次介入处理能力 |
| 短时人员介入实验 | 特定协作条件下的理解、操作和结果判断 |
| 人员实际数小时监督 | 对应条件下的长期使用表现，需独立记录分析 |

短时实验不能证明降低疲劳或改善长时警觉性，未覆盖长期使用时限制结论并审视题目表述。

## 5. 公平对照与候选创新评价

### 整体方案对照

基线使用合理现有界面或有文献依据的方案。两组保留相同任务事实、Agent及执行能力、地图数据、基本操作和成功/失败反馈。本文方案增加情境化组织、对象与影响表达、调整要求与计划及落实依据的关联。

不要删掉基线必要的失败信息；记录信息可获得性、视觉复杂度和任务难度差异。若新增后台能力，单独说明并控制，不能归因于界面机制。

### 调整意图与执行落实关联的针对性比较

资源允许时固定M1/M2其他主要功能，比较相同事实分别展示与显式关联到同一调整要求的展示，检查落实判断、部分落实发现及后续错误操作。

在Agent征询后调整、用户主动变更等不同来源或事件中检查机制，不仅测试道路封闭。包含易混淆的部分落实、反馈延迟和连续修改，同时保留普通成功条件，观察何时关联组织没有收益或反而增加负担。

### 依据变化与重新确认的针对性比较

支撑机制先完成必需的功能验证；资源允许时再固定执行端检查、拒绝能力、任务事实、关联反馈和可用操作，比较常规变化或冲突提示与“说明受影响要求、保留有效输入、按条件重新确认”的交互。以介入处置正确率为主，记录无关变化打断、确认次数及耗时。不关闭基线执行检查，不把后台拒绝能力归因于界面效果。

优先进行核心关联反馈对照，避免同时新增两个机制而无法解释收益。未开展支撑机制的人员比较时，只报告其功能结果，不宣称其独立改善用户表现。

只有整体对照时，结论限于整套方案；没有针对性比较不能宣称某项机制独立有效。数据关联本身也不构成新颖性，仍需与已有方法比较。

## 6. 指标与记录

| 评价内容 | 指标示例 | 判断依据 |
| --- | --- | --- |
| EQ1 执行理解 | 状态、变化、目标和空间影响判断正确性及耗时 | 任务事实、事前定义的合理影响条件 |
| EQ2 调整表达 | 对象、范围、约束错误，指定操作完成情况 | 预设要求与输入日志 |
| EQ2 后台结果 | 接受与实际执行情况，未落实范围 | 回执、观测或独立真值 |
| EQ2 落实判断（主指标一） | 正确判断落实状态的要求或对象单元数／全部应判断单元数 | 用户回答与执行端或独立场景真值对照，分别报告部分落实及未知 |
| EQ2 介入处置（主指标二） | 依据变化检查窗口中正确选择继续、重新确认、修订或等待等的次数／全部应处置次数 | 事前独立定义的预期处置；无关变化不额外确认也纳入 |
| 支撑机制功能 | 相关变化检出率、无关变化误触发率、分类处置正确率 | 独立场景规则及检查日志 |
| 辅助评价 | 操作成本、主观负荷、控制感、访谈 | 日志与规范实施的测量 |

后台结果、系统检查与拦截、用户判断分别统计，不用自动拦截成功代替用户理解。未响应单列并保留在应判断或应处置分母中；计分单元及规则在实验前固定。未发现问题的参与者需报告，不只计算成功发现者的速度。预测题依据事前条件评分，不用随机未来结果反推错误。自编事实题不冒用标准SA测量名称，使用标准工具时按要求实施。

## 7. 实验控制、分析与结论边界

说明人员经验与目标用户匹配程度，平衡体验顺序，使用难度相当案例。样本、任务数和分析方法按目标及资源事前确定，同一人多次操作不当成独立参与者。

按参与者和情境报告正确性、错误与耗时及适当不确定性，不只报告总平均或有利结果。主观控制感不能替代实际落实，满意度不能替代信任校准。专家认为合理也不等于用户表现更好。

区分跨结果状态、跨协作情境、跨业务案例和跨应用的证据；一套界面更有效不证明所有准则独立必要，也不证明Frontend Tool普遍优于规则。无人员实验时只报告功能与合理性，不能声称用户效果。

## 最小推进顺序

1. 核查系统工作过程，建立情境与需求表。
2. 完成理论—需求—机制对应、核心关联反馈及依据有效性处置规则，核实接口与模拟边界。
3. 根据情境覆盖选取案例，实现原型并检查状态关联。
4. 以专家反例修订，开展合理的用户任务对照。
5. 资源允许时增加候选创新针对性比较及长时研究。
6. 依据实际覆盖和结果提炼贡献，不以案例演示代替整体论证。
