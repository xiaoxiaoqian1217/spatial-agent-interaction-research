# 研究问题

> **2026-09-16 研究问题收敛版。** 研究主线由“完整协同界面包含什么”调整为“为什么在当前任务情境下，此刻应提供这种交互”。当前阶段不把 LLM 作为必要技术前提，优先研究上下文模型、规则/状态机与交互需求推理的组合机制。

> **工作题目：面向无人系统任务的情境驱动地图动态交互组织方法研究。**

## 1. 论文定位与研究对象

研究面向操作员监督无人系统执行持续、多阶段、空间分布的任务。业务背景包括空中、地面、四足等异构无人平台及其执行智能体，以及信息处理、态势分析、任务规划等支撑智能体。操作员通过地图等空间界面理解任务过程，在必要时参与判断、调整和结果核查。

本文不研究无人平台控制算法、任务规划算法或通用多智能体编排；重点研究**运行时任务情境如何转化为适当的人机交互**。

“长时”作为应用特征保留，指任务持续演化、多阶段、多次变化和多次可能介入；除非开展对应长期人员实验，不将疲劳、警觉性下降等长期效应作为论文必证结论。

## 2. 核心研究链

本文采用如下主线：

```text
Runtime Context
      ↓
Context Model
      ↓
Task Situation
      ↓
Interaction Need
      ↓
Interaction Strategy
      ↓
Dynamic Map Interaction
```

其中：

- **Runtime Context**：任务、平台、空间对象、事件、风险、计划、执行证据及用户当前操作等运行时事实。
- **Task Situation**：对当前任务状态及其变化进行结构化解释，是从原始上下文到交互决策的中间表示。
- **Interaction Need**：依据任务事实、约束和权限判断，此刻界面应支持理解、判断、控制或核查什么。这是任务导出的交互支持需求，不是对用户内心意图或认知状态的测量。
- **Interaction Strategy**：决定信息如何组织、地图如何表达、以及人和 Agent 如何分配主动权。
- **Dynamic Map Interaction**：将策略落实为地图视野、图层、路径、对象高亮、信息面板、候选方案、确认/调整入口等具体交互。

这几个环节不是互斥的“驱动类型”。当前阶段允许上下文模型、规则、状态机和需求推理共同组成实现机制；暂不将 LLM 作为必要条件，也不预先排除后续使用学习或大模型方法处理复杂情境。

## 3. 总研究问题

> **在无人系统持续执行空间任务的过程中，如何依据运行时任务情境判断当前任务要求界面支持的交互需求，并据此动态组织地图信息、空间可视表达和人机交互方式？**

## 4. 三个研究问题

### RQ1 — Task Situation Modeling

> **无人系统任务执行过程中，哪些运行时上下文因素会影响操作者的交互需求，以及如何将这些因素组织为可用于交互决策的任务情境？**

候选情境维度包括：

| 维度 | 示例 |
| --- | --- |
| Task | 任务目标、阶段、进度、约束、计划变化 |
| Agent / Platform | 自主执行、等待、重规划、失联、失败、接替 |
| Spatial | 平台、区域、路径、目标点及空间关系 |
| Event | 新任务、偏航、风险出现、计划更新、反馈到达 |
| Risk / Impact | 风险等级、受影响对象、受影响任务与范围 |
| Decision | 无需判断、待比较、待确认、需人工调整 |
| Evidence | 已确认事实、最后报告、当前未知、后续计划 |

RQ1 不预设必须采用某一种形式化模型。第一阶段优先使用显式上下文模型、有限状态/事件表示和可检查规则，验证其是否足以覆盖典型任务情境。

### RQ2 — Interaction Need Inference

> **如何依据任务情境判断当前任务要求界面支持的理解、判断、控制和核查内容，显式需求表示相较直接策略映射有何价值？**

第一版交互需求空间定义为：

- **Understand**：现在发生了什么、在哪里、当前状态是什么。
- **Assess**：变化是否重要、影响什么、候选方案或后果是什么。
- **Control**：是否需要介入、可以修改什么、需要确认什么。
- **Verify**：调整是否落实、执行结果是否符合已确认要求、哪些仍未知。

当前阶段重点不是比较 LLM，而是验证：

1. 情境特征是否足以区分这些需求；
2. 基于规则/状态转换的推理能否稳定覆盖代表性场景；
3. 多种需求同时出现时如何组合、排序和处理冲突；
4. 与同样使用完整情境的直接规则映射相比，显式需求层能否改善策略适切性、解释依据或跨情境规则复用；若输出与成本均无优势，应报告零收益并考虑简化。

### RQ3 — Dynamic Interaction Organization

> **如何将交互需求转化为适当的信息组织、空间可视化和人机主动权策略，并通过动态地图界面支持任务理解与人机协同？**

交互策略至少包含三个维度：

```text
Interaction Strategy
├─ Information Organization
├─ Spatial Visualization
└─ Initiative Management
```

- **Information Organization**：当前事实、变化原因、影响、未知项、后续计划及执行证据如何组织。
- **Spatial Visualization**：地图视野、图层、路径、风险区、受影响对象、原/新方案等如何呈现。
- **Initiative Management**：Agent 何时仅执行、主动告知、提出建议、请求选择或要求确认。

Mixed Initiative 属于 RQ3 中的 Initiative Management，是交互策略的重要组成部分，但不是全文唯一研究对象；“谁发起交互”也不等于“谁拥有最终执行权限”。

## 5. 用户交互需求（Interaction Requirements）

以下需求用于设计追踪和实验任务构造，不与 RQ1—RQ3 混用：

- **IR1** 理解任务进展与空间分布。
- **IR2** 理解关键变化、原因及后续影响。
- **IR3** 准确表达空间调整及约束。
- **IR4** 判断是否需要介入以及介入到什么程度。
- **IR5** 核查调整落实与任务结果。

## 6. 评价问题

### EQ1 — 情境与需求推理是否合理

在独立于规则设计的代表性任务脚本中，情境模型与推理机制能否合理识别需要关注的信息、任务导出的交互需求及交互方式？

候选指标：情境覆盖率、规则冲突率、未匹配率、需求判断与专家标注的一致性、状态转换正确性。

### EQ2 — 动态交互组织是否改善任务表现

在相同任务事实、Agent能力、地图数据和基本操作条件下，与明确定义的固定组织界面（B0）或直接规则动态界面（B1）相比，情境驱动地图交互是否帮助用户更准确、更高效地理解变化、判断影响、实施必要调整并核查结果？

候选指标：理解正确率、变化遗漏、判断耗时、漏介入/误介入、对象/范围/约束错误、落实判断错误、操作耗时、主观负荷及控制感。

### EQ3 — 显式需求层是否值得保留

在相同情境输入、权限约束和可用策略下，P（Situation → Need → Strategy）相较 B1（Situation → Strategy）是否改善策略适切性、追溯质量或跨情境复用？同时记录新增规则、修改位置和维护成本。离线规则比较不能直接证明用户收益；若二者最终交互相同，不预期仅凭内部结构获得用户表现差异。

## 7. 当前技术立场

第一阶段不使用 LLM。上下文模型、规则、状态机可以跨环节组合：规则既能识别情境，也能判断 Need、选择地图策略和检查权限；状态机既能描述任务，也能管理人机协作过程。研究过程与实现方法不是一一对应的层级关系，详见[框架第6节](framework.md#6-驱动机制的关系)。

显式需求层作为主方案实现并与直接映射比较。其存在本身不能证明先进性；仅凭任务状态也不能宣称识别用户真实意图。四类 Need 是本文的工作分类，不等同于 Endsley 三级 SA，也不是已验证的心理模型。

## 8. 贡献与边界

拟形成三个方法贡献，均须验证；原型和实验作为支撑证据：

1. 面向无人系统空间任务的运行时任务情境表示及设计变量；
2. 从任务情境到 Interaction Need 的可解释推理机制；
3. 从 Interaction Need 到信息、空间表达和 Mixed-Initiative 策略的动态地图交互组织方法；

支撑材料：可运行原型及代表性情境下的功能验证、专家评审和用户评价。

不因组合三种方法或增加需求层本身宣称创新；需求层收益由 EQ3 回答。不因采用某种协议、Agent框架、LLM或地图组件本身宣称创新。论文贡献需由文献差异、任务需求、机制设计和实验结果共同支持。
