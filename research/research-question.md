# 研究问题

当前处于交互困难发现阶段，具体研究问题、核心机制与创新点尚未确定。
已进入候选机制细化，结合[执行中新增区域的任务走查](interaction-walkthrough.md)与原型比较继续核查困难和设计效果。

已形成[交互困难探索报告](interaction-difficulties-2026-09-15.md)，将执行中的局部修改及落实确认列为优先候选。
报告依据相邻研究与场景推演，尚未完成本项目用户验证，也未确定动态界面或交互 Agent 为核心机制。

另有[装备失联后的处理探索报告](lost-link-interaction-difficulties-2026-09-15.md)，从失联事件开始，分析了解情况、理解系统处理、必要时参与决策和核查落实的候选困难。
接替是失联后可能采用的策略，不是场景起点或必然结果；系统具有自主接替能力不等于本次已经决定接替。
两份报告并列保留，分别探索用户主动修改与异常发生后的协同处理，不据此确定唯一主线。

工作题目与长时空间任务背景暂予保留，自主接替与新增区域为候选案例。

> **工作题目：面向长时空间任务的人-智能体交互机制设计与实现。**

## 论文定位与背景

系统工程领域的工程应用研究，研究人与智能体的交互设计、实现与评价。
多个智能体共同支撑用户任务：内部编排不属于本文独立研究对象，后台输出形式与可用信息待核查，不将多源输出聚合、归因与冲突处理作为研究目标。
单位尚无所需交互实现是建设动机；论文通过需求依据、设计理由、可运行系统和评价形成论证。
不要求每个组件首创，不预设效果。

设备群自主执行任务并自主接替，人通过空间界面监督，必要时介入。
既有业务描述为空中、地面、四足异构平台及其执行智能体，配合信息处理、态势分析和任务规划支撑智能体。
操作员保留否决/改派权；具体流程与权限生效条件待核查。

长时空间指任务持续数小时以上、对象分布于地理空间。
关注持续变化、多次参与以及任务、设备、区域、路径之间的关系；不从时长直接推断疲劳或脱离回路。
业务背景不等于实验覆盖。

上述依据为对话和现有业务记录，未经独立日志/现场研究验证。
早期“逐台人工比较、期待新增自动接替”属于旧设计，不再作为当前事实。

## 待收敛的问题与目标

> 在长时空间任务中，用户理解情况、表达调整和核查结果时遇到哪些具体困难，需要怎样的交互支持？

| 目标 | 评价问题 | 证据 |
| --- | --- | --- |
| G1 支持任务过程理解 | EQ1：是否更准确理解当前状态、关键变化及其与任务目标和后续安排的关系？ | 理解正确性、变化遗漏、判断耗时 |
| G2 支持有效介入与结果确认 | EQ2：是否能准确表达调整，合理介入，并正确判断落实与结果？ | 对象/范围/约束错误、漏介入/误介入、落实判断及操作耗时 |

自主接替后的判断、新增区域后的调整是重点设计与验证场景，不代替整体论题。
“为什么推荐某设备”不是全文必要问题。

## 暂定分析框架

- **M1 任务信息呈现**：核查用户需要哪些信息、何时需要及后台能否提供，具体呈现形式依据实际困难确定。
- **M2 用户与Agent的协同介入**：支持主动调整及必要征询，明确对象、范围、约束、影响与确认边界。
- **M3 执行衔接与反馈**：关联用户要求、实际调整与执行反馈，支持阶段/最终结果确认和必要的再次介入。

完整主线为“理解执行-参与调整-确认落实”，允许循环、并发和无人介入的正常执行。
调整意图与落实关联可作为特色设计，暂不指定唯一核心创新。

## 优先探索方向

优先探索空间交互：围绕任务、设备、区域与路径，研究用户如何理解变化、表达调整和核查结果。
空间对象与任务过程的联动、空间操作与语言表达的衔接是候选设计入口，尚未选定具体创新。
交互机制和支撑交互的技术实现均可形成贡献，但需说明相对已有方案的差异及证据；不能由“单位尚未实现”或“感觉研究较少”推断新颖性。

“提升用户体验”需落实为可观察目标：理解更准确、空间调整表达错误更少、衔接更顺畅或操作负担更低。
满意度作为辅助证据。
技术方案需针对实际交互难点，不因采用某种协议、框架或Agent工具便称为创新。

## 贡献与边界

拟形成业务交互需求与约束、完整机制及原型、有代表性场景下的评价与设计经验。
按实际完成及证据区分应用整合与机制改进。
算法、设备控制和通用多智能体编排为依赖能力，不研制接替推荐算法。

对照保留相同后台能力、任务信息与基本反馈，比较交互组织与操作机制。
整体对照支持整体结论；单项机制独立效果需针对性比较。
无人员长期实验时不声称长期认知或疲劳收益。

## 候选机制与技术决策

已同意将“根据当前任务情境、用户已表达的要求及尚未明确的信息组织交互，并随信息补充和情况变化调整后续交互”作为优先探索的候选机制。
具体候选问题是：在空间任务中，如何依据这些信息组织此刻需要的交互，并动态调整后续交互？
覆盖范围尚不清楚、必要信息缺少、信息完整、存在冲突及过程中发生修改等情况，不假设区域已经选好。
输入保留和局部重新检查属于修改衔接的子机制，不代表整个研究问题。
具体规则、两个场景的推演、实现分工和比较条件见[动态交互机制草案](contextual-interaction-mechanism.md)。
保留输入不等于沿用旧验证结论，已有内容发生依赖变化时需要重新检查；后台未知信息不能转成要求用户猜测的必填项。

“任务情境 → 交互需求 → 能力组合”仅为候选机制，动态界面尚未确定为论文主线。
地图能力调用、地图交互模式与页面控件是不同能力，其是否需要动态协同，应由任务走查确定。
理解、参与和核查保留为研究目标，不据此预定必须实现的界面。

固定流程、组合规则与交互 Agent 都可能实现交互组织，是否使用 LLM 不是创新判据。
规则方案只有在解决明确困难、具有可复用的方法并获得比较证据时，才可能形成研究贡献。
增加需求解析中间层、采用 AG-UI 或 A2UI、让界面发生变化，都不自动构成创新。

暂不确定独立交互 Agent 或双 Agent 架构。
首个原型先采用规则组织交互，验证范围澄清、信息补充、影响检查、冲突处理和修改衔接及其转换，不预设规则必然足够或必然不足。
只有观察到规则难以承接的要求组合、规则维护问题或其他明确不足，再评估 LLM 辅助规划。
需比较其收益与响应延迟、语义偏差、业务约束遗漏、职责耦合和调试成本。
将业务理解和交互规划放进同一次 LLM 调用也会增加业务 Agent 的职责，不作为默认方案。

## 当前推进任务

依据[机制草案](contextual-interaction-mechanism.md)准备新增区域的小原型，并用装备失联后的处理分支核查适用边界。
原型从不同明确程度的初始要求开始，覆盖范围不清楚、只缺参数、输入完整、存在冲突及修改五类情况。
结合[任务走查草稿](interaction-walkthrough.md)探索实际流程，比较方案保留预填、输入保存、基本校验和反馈，不以故意重复操作衬托动态交互。
记录用户目标、可观察行为、困难后果、现有处理办法、数据与权限限制，并标明实际观察、参与者陈述或研究者推演。
候选困难包括查找、重复输入、理解确认与修改衔接等，但目前均无实际困难证据。
同时记录顺利完成的情况及其他可能原因，避免为预设方案寻找支持。
找到具体困难后，再进行相关工作比较、机制设计与评价规划。
