# 需求—机制—实现—评价对应表

> **2026-09-16 对齐版。** 研究主线为 **Context → Situation → Interaction Need → Interaction Strategy → Dynamic Map Interaction**。原 R1—R5 改为 **IR1—IR5（Interaction Requirements）**，避免与论文 RQ1—RQ3 混淆。

工作题目：**面向无人系统任务的情境驱动地图动态交互组织方法研究**。

## 1. RQ、IR 与实现机制的层次

| 层次 | 内容 | 作用 |
| --- | --- | --- |
| RQ1 | Task Situation Modeling | 研究哪些运行时上下文因素影响交互需求，以及如何表示任务情境 |
| RQ2 | Interaction Need Inference | 研究任务导出的 Understand / Assess / Control / Verify 及需求层相对直接映射的价值 |
| RQ3 | Dynamic Interaction Organization | 研究如何把 Need 转成信息、地图表达和 Mixed-Initiative 策略 |
| IR1—IR5 | 用户交互需求 | 用于设计追踪、案例构造和实验评分 |
| M1—M3 | 具体交互实现机制 | 将策略落实为可运行界面 |

## 2. 核心交互需求对应表

| 需求 | 主要情境依据 | 对应 Need | 机制与拟设计交互 | 最小实现与所需数据 | 主要评价 |
| --- | --- | --- | --- | --- | --- |
| **IR1 理解任务进展与空间分布** | 正常监督、阶段变化 | Understand | M1：任务与地图双向定位、状态详情 | 任务/步骤、设备、区域、路径及对应关系 | 状态与对象匹配正确性、查找耗时 |
| **IR2 理解关键变化及后续影响** | 事件、计划变化、风险、异常 | Understand + Assess | M1：变化条目联动地图、原/新计划差异、按需历史 | 带时间及对象的事件、当前状态、后续计划、影响对象 | 变化遗漏、原因/影响判断、耗时 |

## 3. 情境—需求—策略追踪

每个代表性情境需记录以下链条：

```text
Context Facts
   ↓
Task Situation
   ↓
Interaction Need
   ↓
Interaction Strategy
   ↓
UI / User Action
   ↓
Evaluation Evidence
```

建议为每个情境至少填写：

- Context：任务、平台、空间对象、事件、风险、证据、用户当前操作；
- Situation：当前阶段、变化、受影响对象、待决策项；
- Need：Understand / Assess / Control / Verify，可多选；
- Strategy：Information / Spatial Visualization / Initiative；
- UI：地图、列表、对比、告知、建议、请求、确认等具体实现；
- Evaluation：规则输出是否合理、用户是否正确理解和操作。

## 4. 信息规范与设计依据

M1/M2 共用“发生什么—为什么—影响什么—还有什么未知”的信息结构。状态表达继续区分：

- 已确认事实；
- 最后报告；
- 当前未知；
- 后续计划；
- 候选方案；
- 执行依据与结果。

这些信息应关联对象、来源、依据时间及适用范围。最后报告可以包含历史事实，不能直接当作当前状态。

| 设计补强 | 主要对应 | 实现与评价 |
| --- | --- | --- |
| 变化四问及原/新计划差异 | IR2 / IR4；Understand / Assess | 变化、计划及任务/空间对象关联；测原因与影响判断 |
| 证据与时间标识 | IR1 / IR2 / IR5；Understand / Verify | 来源、产生/接收时间、适用范围；测已知/未知和落实判断 |
| 空间对象与任务过程联动 | IR1—IR5 | 地图对象、任务步骤、变化和反馈双向定位；测查找、理解和操作错误 |
| 主动交互方式 | IR4；Assess / Control | Observe / Inform / Suggest / Request / Confirm；测漏介入、误介入和打扰成本 |

## 5. 两个重点案例的脚本工作稿

以下是原型与实验设计提案。A/B 组使用相同事件、证据、Agent后台能力和基本操作；差异只来自交互组织方式。

| 脚本环节 | C1 异常后的自主接替 | C2 新增区域后的主动调整 |
| --- | --- | --- |
| 输入与触发 | 原任务/区域、平台 A 最后报告及时间；注入失联事件和自主接替安排，关联平台 B 原任务 | 当前任务/区域及计划；加入新区域和任务约束，保留原要求，提供候选计划及原/新差异 |
| Context / Situation | 失联、接替、原任务受影响、部分状态未知 | 新空间要求、计划变化、约束冲突或相容 |
| 主要 Need | Understand → Assess；必要时 Control；接替后 Verify | Understand / Assess → Control → Verify |
| 用户关键判断 | 哪些进展已确认、失联后哪些未知；谁接替；影响什么；是否需要介入 | 新要求涉及什么区域与约束；哪些安排改变/保留；是否冲突；是否需补充 |
| 交互策略 | 重要变化主动告知；地图突出失联对象、接替关系和受影响任务；必要时提供否决/改派 | 地图选区与约束表达；原/新方案空间对比；冲突时请求澄清；执行前按权限确认 |
| 操作 | 查看任务/地图关联；继续监督，或在权限内否决/改派/补充约束 | 地图选择区域或对象，结合结构化/自然语言输入补充约束；预览后确认、修订或放弃 |
| 预期反馈 | 自主变化与人工决定分别关联；展示发送、接受、实际执行及结果，缺证据时显示未知 | 展示输入形成、方案更新、执行端接受与落实；按新要求及保留原要求核查 |
| 对照分支 | 接替符合已知约束，可继续监督；接替违反明确约束，需要介入 | 新要求与原安排相容；新要求与保留约束冲突，需要澄清/修订 |
| 反馈分支 | 完整落实、部分落实、未知；允许迟到回执 | 完整落实、部分落实、失败；允许连续修改 |
| 评分依据 | 固定任务证据、约束和可接受操作集合；记录原因/影响回答及漏介入/误介入 | 固定目标几何、约束和可接受修订集合；记录对象/范围/约束输入及落实判断 |

共同前置流程保留目标委托与理解确认（S1），共同结束流程核查阶段结果（S6）。两案例用于重点验证，不宣称穷尽所有无人系统情境。

## 6. 最小情境与规则集

第一阶段不追求覆盖全部组合，先建立可检查的代表性情境集。建议至少覆盖：

1. 正常稳定执行；
2. 重要状态变化但无需人工介入；
3. 异常发生且影响范围明确；
4. Agent 自动调整且不违反约束；
5. 候选方案存在取舍，需要用户判断；
6. 关键调整需要确认；
7. 用户主动增加/修改空间要求；
8. 调整已接受但尚未执行；
9. 部分落实/失败；
10. 当前证据不足，结果应保持未知。

每条规则记录版本、输入条件、证据与时间、Need及对象、策略和操作、冲突优先级、退出条件、适用范围和反例；规则可跨多个环节使用。样例见[规则示例](context-rule-examples.md)。Need 是任务导出的交互支持需求，不代表用户真实意图。

规则只是当前阶段实现手段，不等同于研究贡献本身。

## 7. 最小原型范围

拟实现：

- 运行时 Context / Situation 状态维护；
- 可检查的情境识别与 Need 映射；
- 地图、任务/过程视图、变化与影响信息；
- 空间调整输入和方案预览；
- 交互方式对应的告知、建议、请求和确认；
- 调整—计划—执行反馈关联与核查。

串联流程：

```text
目标/空间要求确认
→ 自主执行与监督
→ 情境变化
→ Need识别
→ 交互策略调整
→ 用户按需介入
→ 执行反馈
→ 阶段/最终核查
```

已有后台能力优先复用；不可接入部分可用确定脚本/事件数据模拟并明确标注。当前不建设完整设备平台、不研制接替算法、不默认引入 LLM、VR 或用户心理状态估计。

## 8. 对照与评价边界

| 层次 | 实施 | 可支持结论 |
| --- | --- | --- |
| 情境/规则验证 | 固定情境集检查状态转换、Need与策略输出 | 所测情境下推理逻辑正确性与覆盖性 |
| 专家评审 | 对照任务和权限判断 Situation / Need / Initiative 是否合理 | 设计合理性与专家一致性，不等于用户效果 |
| 功能验证 | 固定脚本检查地图、调整、状态和反馈关联 | 所测条件下系统正确运行 |
| 整体用户对照 B0/P | 同信息、Agent能力、地图数据和业务操作，固定组织与需求层动态方案比较 | 整套动态组织效果，不能单独证明需求层有效 |
| 需求层比较 B1/P | 同情境与策略能力，直接规则映射与显式 Need 映射比较 | 回放支持策略/维护价值；用户收益需另做 B1/P 用户对照 |
| 可选单项比较 | 固定其他能力，只改变一项策略/机制 | 对该单项的增量效果 |

B0 为固定组织但数据实时更新的常规界面；B1 为使用多因素情境的规则动态界面。二者不能混称一个基线，也不能故意缺失必要信息。条件控制与评分见[对照协议](../experiments/protocols/context-driven-comparison.md)。

## 9. 候选评价指标

### RQ1 / RQ2

- 代表性情境覆盖率；
- 状态转换错误；
- 规则冲突率；
- 未匹配率；
- Need 输出与专家标注的一致性；
- 交互方式与专家判断的一致性。

### RQ3 / 用户效果

- 状态、变化、原因、影响理解正确率；
- 变化遗漏；
- 判断耗时；
- 漏介入 / 误介入；
- 对象、范围、约束错误；
- 完整/部分/失败/未知的落实判断正确率；
- 重复提交、错误确认和恢复操作；
- 操作耗时；
- 主观负荷、控制感及访谈反馈。
