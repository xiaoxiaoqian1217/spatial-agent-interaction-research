# 协同交互研究框架

> 2026-09-11 修订，与[论文大纲](outline.md)一致。原五维改为设计准则，研究主体为两个目标与三项协同机制。机制与效果仍待验证。

## 背景、目标与范围

操作员通过现有终端远程监督空中、地面、四足三类无人平台组成的班组，各有执行智能体，另有信息处理、态势分析、任务规划三类支撑智能体。长时空间指任务持续数小时以上、被控对象分布于地理空间。具体规模与实验时长据实报告。

核心问题：任务持续执行和变化时，用户怎样理解执行、参与决策和调整，并确认后续执行是否符合要求？

G1 支持正确的用户态势感知；G2 支持有效的人机协同。EQ1 检查理解与影响判断，EQ2 检查调整表达、操作及落实判断。

## 场景分析的三个层次

| 层次 | 内容 | 研究位置 |
| --- | --- | --- |
| 系统应用场景 | 异构无人平台班组的长时空间监督任务 | 背景与边界 |
| 典型协作情境 | S1目标委托与理解确认、S2正常执行与过程监督、S3 Agent主动征询、S4用户主动调整、S5异常处理与协同恢复、S6结果确认与后续衔接 | 需求分析、机制与覆盖检查 |
| 具体业务案例 | 道路封闭、用户新增限制、任务优先级变化、平台无法继续执行等 | 演示与实验脚本 |

六类情境是工作分类，可循环、交叉，不宣称穷尽所有协作。一个业务案例可覆盖多个情境；一个案例的成功、部分成功、失败不能代替情境覆盖。前端工具是多类情境中的协作手段，不单列为同层情境。

## 三项相互衔接的机制

| 机制 | 输入与输出 | 主要支撑 |
| --- | --- | --- |
| M1 执行信息组织与呈现 | 将目标、计划、事件与空间对象组织为状态、变化、影响和决策上下文 | G1并支持G2 |
| M2 用户与Agent的协同介入 | 结合双向请求、依据有效性和权限，形成清晰的对象、范围、约束与确认决定；条件变化时按需重新确认 | G2 |
| M3 介入后的执行衔接与反馈 | 结合用户要求、计划变化与执行依据，反馈各项要求落实情况和后续处理 | G2并更新G1 |

M3反馈返回M1以支持继续理解或再次调整；正常执行不强制进入人工介入。结果确认需对照目标和既有决定，一次Run结束不代表业务完成。地图贯穿理解、表达和落实核查。

## 专业依据如何进入设计

| 依据 | 分析用途 | 设计要求 |
| --- | --- | --- |
| Endsley情境感知模型 | 分析事实、意义和后续影响的信息需求 | 关联状态、目标与空间影响，区分事实、计划和预测 |
| Norman行动模型 | 分析执行鸿沟和评估鸿沟 | 明确意图到对象及操作的映射、结果到要求的对照 |
| 混合主动交互范式及监督职责分析 | 分析双方发起、澄清、协商与继续 | 明确请求入口、权限及执行条件 |
| 空间交互研究与任务分析 | 确定空间关系如何影响操作员决策 | 任务、平台、区域与路径保持对应 |

构建链为文献与流程证据、用户目标与决策、信息和操作需求、设计要求、机制规则、原型、验证与修订。理论不能唯一推出界面方案，也不直接保证后台正确性。

原五项性质保留为重点突出、含义清楚、上下文连续、后果可预期、操作边界明确等检查准则，允许交叉，不作为独立新理论或五个因果变量。

## 核心候选创新：调整意图与执行落实的关联反馈

按同一用户调整要求组织：
- 调整任务、对象、空间范围、约束及生效条件；
- 保留、改变和无法修改的计划部分，以及确认时的上下文和依据检查结果；
- 各执行对象的回执、观测、时间及来源；
- 后续修改是否替代旧决定，迟到反馈属于哪次调整。

明确关联创建、更新、展示及异常处理。一个对象成功不代表全部落实；缺证据保持待确认或未知；开始执行不等于目标已达成；已发生物理动作不能通过回退对话撤销。

该机制适用于任务调整，不绑定道路封闭。数据关联和增加标签不足以证明创新，需比较已有方法、核查功能，并验证是否帮助用户识别部分落实和采取适当后续操作。机制设计见大纲4.2—4.3，针对性比较见6.6。

## 支撑机制：调整依据有效性与重新确认

保持整体框架，以一项核心候选创新加一项支撑机制组织研究重点。M2记录用户当前决定的依据，比较系统当前可获得的相关信息，M3继续按同一调整要求呈现落实结果。执行—呈现一致性不等于掌握全部物理真值，依据需注明来源、时间及未知部分。

| 判定 | 交互处置 |
| --- | --- |
| 无关变化 | 正常更新背景，不额外确认 |
| 相关变化但决定仍适用 | 更新影响说明，保留输入与确认 |
| 原取舍需要重审 | 突出受影响要求和计划差异，保留有效输入并重新确认 |
| 部分或全部不可行 | 说明原因与可修改范围；剩余部分只有在可独立执行且已获明确授权时继续，否则重新确认或拒绝 |
| 必要依据不足 | 显示待核实，暂缓依赖该信息的提交 |

相关性包含对象、步骤、空间约束和共享资源依赖；判定依据为业务条件及已确认取舍，版本变化不等于决定失效。重新确认关联原依据、当前变化、受影响要求与可继续方式，并保留修订历史。详细规则以大纲4.2.4为准。

提交检查通过不代表执行端接受或调整落实。前端负责输入和差异呈现，适配层关联记录并执行已定义规则，业务服务提供可修改条件和影响依据，执行端按能力复核并回传接受或拒绝。原型可模拟执行端，但检查、处置与关联逻辑须实际运行。

## Agent–Frontend协作边界

| 职责 | 使用原则 |
| --- | --- |
| 前端规则 | 结果已足以确定响应，直接绘制路径或呈现状态 |
| 共享交互上下文 | Agent只缺必要信息，提供当前选区或编辑任务；按需读取或实时计算的数据可使用读取型能力 |
| 受控前端工具 | Agent需要前端完成操作并返回结果，例如发起空间选择 |

工具内部可以使用规则；语义理解不必然需要工具；前端参与不必然增加独立前端Agent。前端操作完成与设备调整落实分别记录。

## 评价与边界

专家评审检查情境需求、机制衔接和可实施性；功能验证核查关联和状态规则；用户任务实验通过EQ1/EQ2检验理解、操作和落实判断。分别检查协作情境覆盖与结果状态覆盖。支撑机制另核查相关变化检出、无关变化误触发与处置正确性；EQ2主要记录落实判断正确率和依据变化后的介入处置正确率，系统拦截与用户判断分别统计。

系统估计用户负荷不是当前必要模块；若以后纳入，仅用终端日志、轻量离散规则、零新增硬件，不把日志直接等同心理状态。注意力转移后的重新参与只在实际需求支持时纳入。信任、负荷和控制感属于辅助评价；金字塔原理只用于组织表达。
