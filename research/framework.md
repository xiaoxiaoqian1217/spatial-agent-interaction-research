# 研究框架

> 2026-09-09 同步已确认大纲。章节安排见[论文大纲](outline.md)。

## 总体结构

当前采用“一个核心问题 → 两个核心目标 → 五个交互设计维度”的分层方式组织研究。

核心问题：

> 在长时空间任务中，如何让用户持续理解 Agent 的执行情况，并在必要时有效调整执行？

两个核心目标：

1. **支持正确的用户态势感知**：感知当前事实，理解其与任务目标的关系，判断后续影响。
2. **支持有效的人机协同控制**：适时介入、调整执行，并确认调整真正生效。

两个对应评价问题：

- **EQ1：** 相比基础交互，本文机制能否帮助用户更准确地理解 Agent 当前执行状态、关键变化及其后续影响？
- **EQ2：** 本文机制能否帮助用户正确实施任务调整，并准确判断调整是否真正生效？

用户需要理解情况才能合理干预；干预后的反馈又帮助用户更新理解。五个维度可以共同支撑两个目标，不要求各自归入互不相交的分支。

## 长时空间任务的研究边界

本文不以绝对运行时长定义“长时”，而关注执行期间是否出现状态演化、上下文累积和重新介入问题。代表性任务通常具有跨阶段执行、环境或任务状态变化、计划调整、用户离开后返回、持续空间关系以及执行中可介入等特征。

“空间”也不是单纯给普通 Agent 任务增加地图界面。研究关注任务、计划步骤、设备、路线、区域等空间对象如何与执行状态持续关联，以及这种关联如何影响用户理解与干预。

## 五维框架的构建原则

五维不能只通过逐项寻找支持文献来证明合理性，而需要保留从问题到维度的可追溯过程：

**文献或任务观察 → 用户困难 → 设计需求 → 候选维度 → 合并、去重与修订 → 五维框架。**

这一过程用于回答“为什么是这五维”，并检查是否只是对已有常见设计原则重新命名。

## 五个设计维度

| 维度 | 核心问题 | 当前含义 | 主要支撑目标 |
| --- | --- | --- | --- |
| 注意力选择 | 哪些信息值得关注，何时需要提醒？ | 筛选与任务有关的关键信息，安排摘要、详情与提醒 | 态势感知 |
| 状态可理解性 | 当前在做什么，为什么处于这个状态，对目标意味着什么？ | 将执行状态与任务目标、约束和事实依据关联，帮助用户理解含义 | 态势感知 |
| 连续性 | 当前事件如何关联目标、计划和地图对象？调整前后及离开返回时如何衔接？ | 维持跨阶段、计划变化、任务与空间对象关联及用户离开再返回时的上下文联系 | 两个目标 |
| 可预期性 | 下一步准备做什么，可能产生什么影响，还有哪些不确定性？ | 帮助用户理解后续行动和可能后果，并据此判断是否介入 | 两个目标 |
| 可介入性 | 用户何时、以什么范围介入，如何确认修改生效？ | 支持确认、纠偏、调整、暂停、中止和恢复，并反馈实际生效、部分生效或失败情况 | 协同控制 |

其中“连续性”不是把多个无关问题简单合并，而是共同处理一个核心困难：用户需要跨时间、跨执行阶段和跨任务/空间视图维持对“同一任务过程”的上下文联系。

## 从框架到机制

在论文第 3 节通过“关键执行情境 × 五维需求”矩阵，分析正常持续执行、关键变化、计划调整、等待用户决定、异常恢复、离开后返回和用户主动干预等情境的设计重点。执行过程允许循环、等待和恢复，不预设为固定线性阶段。

在第 4 节落实为三类机制：

| 机制 | 重点 |
| --- | --- |
| 执行信息组织与呈现 | 状态与任务目标关联、信息分层、关键变化提醒、依据表达，以及离开后返回的变化摘要与上下文恢复 |
| 任务与地图关联 | 任务步骤与空间对象关联、计划变化和后续影响表达，以及 Agent–Frontend 协同边界 |
| 动态干预与结果反馈 | 介入对象与范围、修改前后计划衔接、实际生效、部分生效、拒绝、失败与恢复反馈 |

## Agent–Frontend 协同边界

论文第 4.2.3 节不采用简单的“规则 vs Agent”二分，而是区分前端在 Agent 执行过程中的三种职责。

| 前端职责 | 信息/动作方向 | 作用 |
| --- | --- | --- |
| **前端规则** | Business Result → Frontend | 已有业务结果足以确定界面行为时，由前端稳定、确定地完成呈现 |
| **共享前端状态 / 上下文** | Frontend → Agent | 向 Agent 提供当前任务判断所必需、且只存在于当前交互环境中的最小必要状态 |
| **Frontend Tool / 前端交互能力** | Agent → Frontend → Agent（必要时） | Agent 执行到某一步需要当前前端交互环境提供能力时，由 Agent 主动请求前端执行，并在后续任务需要时取得结果继续执行 |

判断原则：

1. **能由已有业务状态确定的界面响应，优先用前端规则。**
2. **Agent 只是缺少当前交互上下文时，优先共享最小必要状态。** 对持续同步不合适、需要实时计算或适合按需获取的数据，再考虑读取型前端能力。
3. **Agent 的任务执行确实需要当前前端交互环境完成一次能力时，才使用 Frontend Tool。**

需要特别区分：

- Frontend Tool 描述的是 Agent 如何调用前端能力，工具内部仍可完全采用确定性规则执行，因此“工具”和“规则”并不互斥。
- 需要前端参与不等于需要新增一个前端 Agent；前端可以只提供状态和受控函数。
- 需要语义理解不等于需要 Frontend Tool。Agent 可以负责解析用户指代或业务意图，随后由前端规则完成已经确定的地图呈现。

这一边界的研究价值不在于某个具体框架的 Tool API，而在于说明在人—Agent—地图协同任务中，信息、决策和交互能力如何在 Agent 与 Frontend 之间合理分配。

## 使用与验证

本框架是待验证的候选设计框架，不等同于经典态势感知理论原有的维度，也不预设为五个彼此独立的因果变量。

每个维度需要回答：

1. 用户遇到的具体问题是什么？
2. 该维度由哪些文献、任务观察和设计需求推导而来，与其他维度如何区分？
3. 通过什么交互机制解决？
4. 如何通过评审、任务实验和其他证据检验？

框架评审检查定义清晰度、需求覆盖与设计可用性；用户实验检验理解正确性与干预有效性。整套界面优于基础方案，不能直接证明每个维度都不可缺少。

实验中的基础方案应保留地图、常规进度和与本文方案相同的业务操作能力，仅不提供本文重点研究的任务—空间连续关联、关键变化摘要、干预影响范围和明确的生效/失败反馈，避免把“有功能”与“没功能”的差异误当成交互机制效果。

传统态势感知理论已包含时间属性；本文考察连续性如何支持用户理解，不预先声称扩展了传统理论。

## 信任与控制感的位置

用户信任、认知负荷和控制感可作为辅助评价。用户信任不同于系统可靠性，主观控制感不同于实际干预是否生效。

信任也可能影响注意力分配和态势感知，因此不能将“五维 → 信任”简单视为已经证明的单向因果关系。若评价信任校准，需要对照系统实际能力与用户判断设计测量。

## 与金字塔原理的关系

借用金字塔原理的分层组织思路，检查总问题、目标、维度、机制和验证之间是否有清楚的支撑关系。

金字塔原理是组织研究与表达的方法；论文的理论依据来自态势感知、自动化监督、人机协同和空间交互相关研究。五维作为设计视角允许交叉，不机械要求相互排斥。
