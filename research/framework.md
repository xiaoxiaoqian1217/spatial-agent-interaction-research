# 协同交互研究框架

2026-09-13 统一优化版，与 [研究问题](research-question.md) 和 [论文大纲](outline.md) 对齐。以下为研究设计计划，不代表已实现或已验证有效。

## 1. 总体关系

论文研究对象是**长时空间任务中的人–多智能体协同交互**。设备群自主执行任务并可能自主调整；操作员通过空间交互界面持续理解执行过程，在必要时介入，并确认调整是否真正落实。

```text
任务目标与空间要求
        ↓
   多智能体自主执行
        ↓
M1 理解执行与变化
        ↓
   是否出现关键变化？────────────┐
        ↓ 是                    │
M2 理解原因与影响               │
        ↓                       │
   是否需要人工介入？            │
        ↓ 是                    │
M3 表达介入并追踪结果 ───────────┘
        ↓
   更新任务与空间状态
        ↓
      回到 M1
```

正常监督可以持续处于 M1；自主接替、任务变化等事件触发 M2；用户调整、否决、改派等进入 M3。三项机制可以循环、多次发生，也允许长时间没有人工介入。

## 2. 三项机制

| 机制 | 用户核心问题 | 输入与输出 | 拟设计交互 |
| --- | --- | --- | --- |
| **M1 基于证据的任务状态与空间变化表达** | 现在怎样？发生了什么？哪些是事实、最后报告、未知和计划？ | 任务/设备/区域/路径/事件 → 可追溯的过程上下文 | 任务—地图双向定位、关键变化、按需历史、事实/未知/计划区分 |
| **M2 自主变化/决策的解释与影响呈现** | 为什么发生变化？影响什么？接下来可能怎样？ | 自主变化＋当前上下文 → 原因、影响、未知和后续安排 | 变化前后对照、影响对象与区域关联、按需解释、空间化差异 |
| **M3 用户介入与执行结果追踪** | 我要改什么？系统是否接受？到底落实了吗？ | 用户要求＋上下文＋执行反馈 → 调整记录与结果判断上下文 | 对象/区域选择、约束输入、确认、状态追踪、部分落实/失败/未知处理 |

具体控件在需求和低保真验证后确定；已有地图联动、时间线、解释和反馈机制均需正面比较，不逐项宣称原创。

## 3. 长时间与空间如何进入设计

### 3.1 时间维度

“长时”不是单纯任务持续数小时，而是带来以下协同特征：

- 状态持续变化，单点状态不足以支持理解；
- 自主调整与人工介入可能多次发生；
- 历史信息累积，需要区分当前有效状态和旧状态；
- 反馈可能延迟、乱序、部分落实；
- 操作员可能需要重新进入上下文，但本文不预设一定离席或疲劳。

因此 M1–M3 需要保持上下文连续、时间可追溯和状态版本一致。

### 3.2 空间维度

设备、区域、路径既是查看对象，也是任务语义和交互操作对象。空间交互的价值必须体现在具体任务中，例如：

- 查看任务变化时能定位对应设备、区域和路径；
- 选择区域时能关联受影响任务与对象；
- 修改任务时能明确调整范围和后续影响；
- 核查结果时能回到原调整所针对的空间范围。

空间元素不是为了“增加地图感”，而是服务理解、表达和结果判断。

## 4. 场景层次

| 层次 | 内容 | 作用 |
| --- | --- | --- |
| 系统应用场景 | 异构无人平台班组的长时空间任务监督与协同 | 界定论文边界 |
| 协作情境 | S1 目标委托、S2 正常监督、S3 Agent 征询、S4 用户主动调整、S5 异常恢复、S6 结果确认 | 需求与覆盖检查 |
| 核心验证场景 | 设备失联/异常后的自主接替 | 集中验证理解、影响判断和介入 |
| 第二验证场景 | 新增区域/任务变化 | 检查机制能否跨场景复用 |
| 具体实验条件 | 接替合理/需修正、部分落实/失败/未知、连续修改等 | 实验操纵与功能验证 |

### 4.1 自主接替场景

设备失联或异常后，设备群自主完成接替。研究重点不是如何计算最优接替对象，而是：

- M1：操作员是否能看懂失联前最后状态、当前未知和接替后的任务关系；
- M2：是否能理解为什么发生接替、谁接替、影响哪些任务/区域、还有哪些未知；
- M3：需要时能否否决/改派，并确认新安排是否真正落实。

### 4.2 新增区域/任务变化场景

当新增区域或新任务要求进入后：

- M1 支持理解当前执行与新要求之间的关系；
- M2 支持理解原计划变化及影响；
- M3 支持表达补充/修改并确认执行结果。

该场景用于避免全文机制退化成“失联接替专用界面”。

## 5. 共享任务上下文

三项机制共享但不等同于一个大状态对象。至少需要稳定关联：

- 任务目标与计划步骤；
- 设备与执行智能体；
- 区域、路径及其他空间对象；
- 事件与关键变化；
- 当前状态、最后报告、未知和计划；
- 自主变化/决策事件；
- 用户介入要求；
- 执行依据、反馈和结果。

需要区分：**任务生命周期、一次自主变化事件、一次人工介入、一次前端交互操作**。这些概念不能混为同一 Run 或状态。

## 6. 共同规则与实现边界

- 任务、对象、调整和反馈保持稳定标识；历史信息带时间和来源。
- 预测、计划与已发生事实严格区分。
- 下发、接受、开始执行、完成、部分落实、失败、未知不得合并为一个“成功”。
- 已发生动作不能通过编辑历史直接撤销；新的调整应形成新的业务事实。
- 迟到反馈必须归属原调整，不能覆盖后续新要求。
- 前端规则负责确定性展示和操作。
- 共享上下文提供当前任务、选区和空间对象等必要状态。
- 受控前端工具仅用于“必须由前端执行并将结果返回 Agent”的能力，不因使用工具而构成创新。
- 不要求新增“前端 Agent”才能实现本框架。

## 7. 理论与设计关系

- **情境感知**：支持分析用户需要感知、理解和预测什么信息；主要支撑 M1/M2。
- **不确定性与证据表达**：约束事实、最后报告、未知和计划的区分；主要支撑 M1。
- **可解释规划/计划差异**：支持自主变化原因和影响表达；主要支撑 M2。
- **Norman 行动模型**：支持“形成目标—表达意图—执行—观察—解释结果”的闭环；主要支撑 M3。
- **混合主动交互**：支持系统自主与人工必要介入之间的职责切换；支撑 M2/M3。
- **空间交互研究**：支持任务、设备、区域和路径之间的表达与操作方式；贯穿 M1–M3。

理论用于解释设计要求，不唯一推出某个控件或布局。

## 8. 评价原则

优先评价完整系统的 EQ1/EQ2：

- EQ1：任务过程与自主变化理解是否更准确；
- EQ2：介入表达、介入判断和落实确认是否更准确。

整体 A/B 对照用于评价整套方案。只有资源允许且确实发现具有差异性的特色设计时，再固定其他功能做单项机制比较。

功能正确性、专家合理性与用户效果分别验证，不能相互替代。
