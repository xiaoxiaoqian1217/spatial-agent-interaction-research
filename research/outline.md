## 研究定位与全文主线

### 业务背景与研究对象

空中、地面、四足三类异构无人平台组成班组，各由对应执行智能体直接控制；信息处理、态势分析、任务规划三类支撑智能体提供支持。操作员在环，通过现有终端远程监督长时空间任务，必要时参与决策和调整。

**长时空间 = 长时程（任务持续数小时以上）+ 广域（被控对象分布于地理空间）。** 不擅自增加平台数量、地理面积和实测任务时长。持续变化、多次参与和空间对象关系是需要分析的任务特征；长时间运行不直接等同于疲劳或理解下降。

### 一个核心问题、两个目标、三项机制

> 在任务持续执行和变化时，如何支持操作员理解 Agent 的执行情况，在必要时参与决策、准确表达调整，并确认后续执行是否符合双方确认的要求？

| 层次 | 内容 |
| --- | --- |
| G1 研究目标 | 支持正确的用户态势感知：感知事实、理解其与目标的关系、判断后续影响 |
| G2 研究目标 | 支持有效的人机协同：准确参与取舍和调整，并正确判断要求是否落实 |
| M1 协同机制 | 执行信息组织与呈现，为过程理解和决策提供上下文 |
| M2 协同机制 | 用户与 Agent 的协同介入，支持双向发起、澄清、取舍、调整依据有效性检查和必要的重新确认 |
| M3 协同机制 | 介入后的执行衔接与反馈，关联用户要求、计划变化和实际执行依据 |

三项机制共同覆盖理解、参与和确认的协作关系。正常执行可以持续由 M1 支持，不强制每个事件触发人工介入；M2、M3 可多次发生并更新 M1。结果交付需要对照目标和已确认要求，不能只用一次 Agent 运行结束代替业务完成。

“用户态势感知”指用户对任务的感知、理解和预测；系统估计用户负荷或响应状态属于另一问题。本文所说的执行—呈现一致性，是界面准确表达系统当前可获得、有依据的执行情况，并标明过时、缺失和未知；不保证掌握物理世界每一刻的全部事实，也不把界面显示等同于用户已经理解。为避免歧义，不使用“双态势”统称上述概念。用户状态估计不纳入本轮方法。

### 系统应用、协作情境与业务案例的层次

| 层次 | 内容 | 用途 |
| --- | --- | --- |
| 系统应用场景 | 操作员远程监督异构无人平台班组完成长时空间任务 | 确定背景与研究边界 |
| 典型协作情境 | 目标委托、过程监督、Agent 征询、用户主动调整、异常恢复、结果确认与后续衔接 | 提炼需求、构建机制、检查覆盖性 |

第三章主要分析前两层，第五、六章再细化第三层。道路封闭属于一个案例，不能用其成功、部分成功和失败三个分支代替全部协作情境。协作情境也不是固定线性阶段；允许并发、循环、等待和恢复。

**研究重点为一项核心候选创新加一项支撑机制：提交前检查调整决定是否仍适用，提交后对照原要求说明落实情况。** 介入上下文与影响表达仍是 M1/M2 的基础设计；版本号、提交校验或一致性标签本身不单列为创新。

候选创新适用于执行中的任务调整，不绑定遇障、绕行或某种设备。其他机制支撑整体主题，不要求每个情境各有一个创新。“增加状态标签”“建立数据关联”或“组合组件”本身不充分构成新颖性，需要说明已有方法的具体不足、机制差异和证据范围。

### 两个评价问题

- **EQ1（对应 G1）：** 在相同任务信息可获得的条件下，本文机制能否帮助用户更准确地理解当前执行、关键变化及后续影响？
- **EQ2（对应 G2）：** 本文机制能否帮助用户准确表达和实施任务调整，在依据变化时适当重新确认，并正确识别已落实、部分落实、拒绝、失败或状态未知？

后台执行结果与用户对结果的判断分别测量，避免将执行正确等同于用户理解，或将主观控制感等同于实际落实。

## 摘要

按业务背景与问题、方法、原型、验证及实际发现组织。概括完整协作机制，突出调整意图与执行落实的关联反馈。结果、改善幅度与结论在实验后填写，不将具体障碍处理案例写成论文全部主题。

## 1. 引言

### 1.1 研究背景

介绍异构无人平台班组的长时空间任务与操作员远程监督形态，说明目标委托、自主执行和必要人工参与的衔接需求，明确论文研究人—Agent—界面的协作关系。

### 1.2 核心问题与工程动机

分析执行信息分散、变化对目标的影响难理解、调整指代和范围不明确、编辑期间调整依据变化、方案更新与实际落实容易混淆等候选问题。通过项目流程、日志或走查核查，不能将未观察到的现象写成已证实痛点。

围绕“理解执行—必要参与—确认落实”提出问题。告警风暴、疲劳识别、离席返回不设为必然前提；告警在影响任务理解和决策时进入研究。

### 1.3 研究目标、范围与评价问题

明确 G1/G2 与 EQ1/EQ2，解释正常监督、主动与被动参与、结果确认均属于整体研究。任务规划、平台控制及通用多智能体编排为依赖能力，本文重点是交互机制。

### 1.4 本文工作与预期贡献

概括理论和任务分析指导的框架、三项机制、原型与验证。核心候选贡献集中于 M2 与 M3 的衔接，不能把全面展示功能当成创新，也不因关注一项候选贡献而缩小整体主题。

## 2. 理论基础与相关研究

**本章回答“为什么这样设计、已有方法做到哪里”。每节给出概念、适用解释、设计启示与边界。**

### 2.1 用户态势感知与执行透明性

以 Endsley 情境感知模型区分感知、理解和预测，分析操作员对事实、目标意义和未来影响的信息需求。结合 Agent 透明性研究，说明解释应基于任务约束、工具结果和可核查事实，展示内部日志不等于帮助理解。

区分下一步计划与后果估计，表达不确定性。结合脱离回路与自动化监督研究讨论注意力转移和重新参与的条件，不由时长直接推出疲劳；页面持续打开也不代表用户持续理解。

### 2.2 行动模型、执行鸿沟与评估鸿沟

以 Norman 行动模型分析目标到操作、结果到评价之间的困难：
- 执行鸿沟：用户意图与可操作对象、范围及约束的转换。
- 评估鸿沟：系统实际变化与用户判断是否符合原要求的转换。
- 设计启示：对象映射、操作边界、调整确认、结果对照和反馈。
- 理论边界：认知模型不直接保证后台一致性，关联、执行衔接和异常规则仍需工程实现及验证。

### 2.3 混合主动交互与人机监督协同

将混合主动交互明确为交互范式，讨论用户与 Agent 分别发起请求、提出或拒绝方案、澄清并继续任务的方式。结合监督职责和业务权限，区分发起建议、批准方案、执行及运行中调整的责任。

“谁发起交互”不等于“谁拥有执行权限”。当前不承担根据心理状态动态切换自动化等级的研究。

### 2.4 空间任务中的可视化与交互研究

围绕任务、计划步骤与平台、路径、区域的关联，比较空间选择、计划差异表达和多视图对应。说明地图在理解、表达与核查中的作用，不以界面有地图作为空间研究的充分依据。

### 2.5 已有研究比较与候选贡献定位

比较目标用户、任务条件、可见信息、介入表达、可修改范围、不可回退动作处理、落实判断和验证方式。核查已有方案是否支持用户要求与计划、执行依据的对应，以及部分落实与连续调整的处理。同时比较调整依据变化后的提示、重新确认和拒绝规则，区分“数据发生变化”与“变化影响本次决定”。

提交前检查与版本关联作为工程实现参考，具体文献与适用条件在正式写作时核实；仅保留实际用于本方法的技术依据，不扩展为通用并发控制、操作变换或长事务补偿研究。

将领域应用、已有技术组合、机制改进分别说明。不得先认定空白，再选择性寻找文献；工程迁移可以有价值，但不自动等于方法创新。

### 2.6 理论、设计要求与评价的对应

| 专业依据 | 本文提出的设计要求 | 机制 | 拟检验内容 |
| --- | --- | --- | --- |
| 情境感知：事实、意义、未来影响 | 关联状态、目标与空间影响，按当前任务突出必要信息 | M1，支撑 M2 | 状态与影响判断的正确性和耗时 |
| 行动模型：执行鸿沟 | 明确语言、对象、范围、约束和可用操作的对应 | M2 | 调整对象、范围及约束错误 |

### 3.2 完整工作过程与典型协作情境

| 编号 | 协作情境 | 用户需要解决的问题 | 主要机制 |
| --- | --- | --- | --- |
| S1 | 目标委托与理解确认 | Agent 理解了什么目标和约束，准备如何执行，是否需要补充或确认？ | M1、M2 |
| S2 | 正常执行与过程监督 | 当前进展、关键变化及后续安排是什么，是否需要参与？ | M1 |

### 3.3 用户目标、关键决策与信息需求

对 S1—S6 按“用户目标—需要作出的决策—必要信息—可用操作—结果判断条件”进行任务分析。保留来源：实际观察、日志、专家反馈或待验证假设。

归纳 R1 理解执行及变化、R2 准确参与与调整、R3 确认落实及后续处理。原五维改为重点突出、含义清楚、上下文连续、后果可预期、操作边界明确等跨机制准则，允许交叉，不再证明五维完备性和独立因果作用。

### 3.4 协同交互总体框架与共享任务上下文

定义 M1—M3 的职责、输入输出与衔接，以及任务目标、计划步骤、空间对象、执行状态、用户决定、调整记录和执行依据之间的关系。区分任务生命周期、一次 Agent 运行和一次人工介入。

共享上下文需区分：用户此次编辑或确认所依据的记录、系统当前可获得的相关执行信息、用户待提交的调整要求。为相关记录保留来源、时间和可获得的标识；计划版本只能辅助追溯，不能替代执行反馈。仅检查与本次对象、步骤、空间约束及共享资源依赖有关的变化，不以全局版本变化直接判定决定失效。

**候选创新在本节体现为：同一调整要求如何贯穿表达、计划变化和落实反馈，并在再次调整时保持联系；M2 的依据有效性检查为该关联提供提交前的支撑。** M3 将落实依据返回 M1，支撑继续理解和必要再介入；正常监督与结果交付仍在框架内。

## 4. 协同交互机制设计

### 4.1 执行信息组织与呈现机制（M1）

#### 4.1.1 面向目标和决策的信息组织

将事件组织为理解确认、计划、进展、关键变化、异常和结果；区分事实、解释、计划与后果估计。针对正常监督、征询、调整及结果确认确定信息重点。

#### 4.1.2 任务、计划与空间对象关联

使任务视图和地图中的平台、路径、区域能够相互定位，说明变化在哪里、与何种任务相关、影响哪些部分。地图持续支撑过程理解，不仅在出现障碍后使用。

#### 4.1.3 信息分层、变化摘要与影响说明

采用摘要、详情和必要提醒，突出当前决策所需内容并保留依据。界面说明执行信息的来源、观测或回传时间和可确认范围；断连或缺少新依据时保留最后已知状态并标明过时或未知，不继续冒充当前确认状态。区分计划下一步与可能后果，标明估计条件和不确定性。重新参与时的变化摘要仅在任务需要时设计，不将离席当成必然前提。

### 4.2 用户与 Agent 的协同介入机制（M2）

#### 4.2.1 双向发起与职责边界

支持 Agent 征询和用户主动补充、修正；明确提出、确认、拒绝、取消、暂停与继续的权限和条件。只有任务取舍、权限或新约束要求时才进入人工决策。既有规划可自动处理的变化不机械请求确认。

#### 4.2.2 介入上下文与准确表达

将原因、目标任务、涉及对象、可修改范围、相关约束与选项共同呈现。自然语言、地图选择和受控组件可组合使用；不明确的对象与约束需澄清。

输出明确的用户决定及其适用上下文。前端选区完成仅说明输入形成，不能代表任务调整落实。相关规则应适用于范围、优先级或资源安排等业务允许的调整，不绑定单一事件。

#### 4.2.3 影响预览与计划确认

将用户要求与候选计划差异关联，呈现保留、改变及不能调整的部分，允许接受、修订或放弃。用户确认方案与执行端接受指令分别反馈。

#### 4.2.4 调整依据有效性检查与重新确认（支撑机制）

以明确的调整对象、计划步骤、空间范围、约束、资源依赖和已确认取舍建立检查范围。编辑开始及每次确认时记录所依据的信息；相关变化到达时更新提示，提交时再检查当前可获得的依据。任务默认继续执行，不能假定打开编辑界面就暂停设备。

| 变化类别 | 判定条件 | 交互处置 |
| --- | --- | --- |
| 无关变化 | 不影响本次调整对象及其步骤、约束和资源依赖 | 正常更新背景，保留编辑和确认，不额外打断 |
| 相关但决定仍适用 | 相关信息变化，但可行性、范围和已确认取舍仍在明确允许范围内 | 更新变化与影响说明，保留输入；无需重复确认 |
| 原取舍需要重审 | 仍可调整，但范围、代价、约束或候选方案超出原确认条件 | 突出受影响对象与计划差异，保留未受影响输入；提交修订方案前重新确认 |
| 原要求部分或全部不可行 | 待修改步骤已完成、对象不可用或约束冲突等，使原要求不能按确认内容执行 | 明确不能修改的部分及原因；剩余部分仅在可独立执行且已有明确授权时继续，否则重新确认或拒绝原方案 |
| 依据不足 | 必需反馈过时、缺失或相互矛盾，无法判定 | 显示待核实及缺失依据，暂缓依赖该信息的提交；不把未知判为通过或业务失败 |

“相关”由对象关系和业务依赖确定，不能只比较平台 ID；“需要重审”由已确认的范围、取舍及业务条件确定，不以每次位置刷新或统一时间阈值触发。具体阈值和规则来源由任务分析及接口能力给出，不能事后按实验结果调整。先核查必要依据，再判定可行性与取舍；多类变化并存时，逐项显示原因，只限制受影响的操作。

重新确认界面围绕“原依据—当前变化—受影响要求—可继续方式”组织，并与地图对象和计划差异对应。沿用同一调整记录保留修订历史，明确当前确认对应哪一版要求，避免用户重填全部内容。

提交前检查通过只表示在该时点已知条件下可继续提交。提交后至执行前再次变化，由执行端依据能力复核并反馈接受、拒绝或需重新确认；前端不能替代执行端保证原子修改。复核失败回到 M2，已接受或已有执行证据进入 M3；无复核能力时明确原型和结论边界。

### 4.3 介入后的执行衔接与反馈机制（M3）

#### 4.3.1 调整意图、计划变化与执行依据关联（核心候选创新）

定义最小关联内容：调整记录与目标约束、涉及的任务和空间对象、确认时的计划与差异、决定所依据的信息及有效性检查结果、生效条件、执行端反馈及来源和时间。一个调整可对应多个步骤与平台。

说明关联的创建、更新、按用户要求汇总和被后续调整替代的规则。以此支持用户核查原要求，而非仅显示分散的状态标签。数据关联本身不预设为创新，需比较已有方案并验证其交互价值。

#### 4.3.2 依据驱动的落实状态表达

区分请求接收、方案更新、指令下发、执行端接受、开始按新方案执行及后续结果。具体阶段由可获得的业务依据确定，不虚构后端反馈，也不要求所有任务经过同一线性序列。依据检查通过不计作落实，执行前条件变化导致的拒绝须关联到该次调整及其确认记录。

缺少证据时显示待确认或未知，多对象调整保留部分落实情况。“开始执行”不等于“任务完成”或“未来持续满足约束”。阶段与最终结果需对照目标和已确认要求呈现。

#### 4.3.3 异常与连续调整的执行衔接

对应用户要求说明已落实、未落实、不能判断的部分及原因；明确已发生动作或已超出可修改阶段的部分，依据既有能力提供重试、修订、取消或恢复入口。

连续调整时标明反馈属于哪次决定、是否被替代，防止迟到的旧反馈覆盖当前状态。外部动作不能通过回退对话撤销，后续调整以实际状态为依据。

**本章产出：** 信息规范、双向协作流程、调整关联与状态规则，以及4.2.4的依据检查和重新确认规则。核心候选创新承载于4.3并衔接4.2，支撑机制集中于4.2.4，其余内容支撑完整协作主题。

## 5. 原型系统设计与实现

### 5.1 原型范围与总体架构

说明监督终端、交互适配层、既有智能体和执行端之间的职责及信息流。标明真实接入、模拟和未实现部分，不重建完整无人平台或通用多智能体系统。

### 5.2 任务、调整与执行事件的关联实现

实现任务标识、计划变化、介入及调整记录与反馈关联，区分任务与 Run，处理重复事件、迟到反馈和连续修改。消息传输完成不等于任务执行完成。

补充依据记录、相关依赖、变化分类、确认修订与执行回执的最小数据合同。前端负责保留编辑依据、呈现差异并收集决定；适配层负责关联与状态传递，可按已定义规则形成检查结果；业务 Agent 或任务服务提供可修改范围、约束及影响依据；执行端负责可支持的执行前复核和接受/拒绝回传。语义解析可由 Agent 完成，明确的判定规则由可复核逻辑实现。

原型优先选择少量边界清楚的调整类型，实际实现依据检查、交互处置和关联反馈逻辑；执行态势和回执可以由独立脚本模拟，但不能仅播放预制成功界面。核实执行中修改能力、计划与状态标识、反馈时效及复核接口；缺少的能力明确标为模拟或未覆盖，不据此前端原型宣称真实平台一致性已获保证。

结合实际选择描述 MQTT、HTTP/SSE、AG-UI 等实现手段；协议接入本身不作为研究贡献。

### 5.3 前端规则、共享状态与受控工具

| 前端职责 | 使用条件 | 例子 |
| --- | --- | --- |
| 确定性呈现 | 已有业务结果足以确定响应 | 绘制路径、突出区域、显示已知状态 |
| 共享交互上下文 | Agent 缺少当前交互环境中的必要信息 | 提供当前选区、编辑对象及相关任务，只共享必要状态 |
| 可调用前端能力 | Agent 需要前端完成交互或执行能力并取得结果 | 请求区域选择或路线编辑，取得结果后继续 |

判断顺序：结果可确定则用规则；仅缺上下文优先共享，按需读取或计算的可用读取型能力；需要主动请求前端完成交互时采用受控工具。工具内部可使用规则，自然语言不必然需要工具，前端参与不必然增加前端 Agent。

说明注册、参数校验、执行及取消/失败回传。前端工具完成与设备调整落实分别处理，使用工具本身不构成效果证据。

### 5.4 面向协作情境的核心界面实现

以 S1—S6 展示目标和计划确认、过程监督、征询与主动调整、恢复和结果确认的界面及状态关系，复用 M1—M3，避免为每个业务事件各造一套界面。

### 5.5 具体业务案例与端到端流程

根据既有能力选取案例，说明每个案例覆盖哪些协作情境。至少安排正常委托—监督—结果确认的流程，并在需要时加入 Agent 征询、用户主动调整与恢复；案例数依据覆盖和资源确定。

道路封闭可用于展示 Agent 发起取舍；用户新增范围约束或任务优先级变化可用于展示主动调整。方案和效果数据据实际能力或明确的模拟规则给出。此处才细化地图数据、操作步骤、反馈序列及异常分支。

## 6. 实验与评估

### 6.1 评价问题、参与者与公平对照

区分机制合理性、功能正确性、用户效果三类证据。说明内部人员经验与目标用户的差异，按资源和目标确定样本、任务数和分析方法。

基线采用真实现有界面或有依据的合理方案，保留同等业务能力、地图数据、可用操作、任务事实及基本成功/失败反馈。本文方案改变信息组织和关联方式，不能通过删除基线必要反馈制造优势。记录实际可获得信息、视觉复杂度和数据入口的差异。

### 6.2 情境覆盖与机制合理性评审

依据 S1—S6 建立覆盖表：每个情境的需求、实现、案例、指标和未覆盖部分。专家评审检查任务需要、定义、边界及机制衔接，不再评价五维独立性和完备性。

区分两种覆盖：**协作情境覆盖**包括委托、监督、征询、调整、恢复和结果确认；**结果状态覆盖**包括成功、部分落实、拒绝、失败及未知。二者不能互相替代。

### 6.3 功能、状态关联与持续运行验证

用可重复脚本或实际记录核查正常流程、双向介入、关联更新、结果确认，以及部分落实、连续修改和迟到反馈。真值来自执行端回执、观测或独立场景规则，不能用界面自身状态标签自证正确。

依据检查另覆盖无关变化、相关但仍适用、需要重新确认、部分或全部不可行、依据不足，以及“提交检查后、执行接受前再次变化”。以事先独立定义的预期处置核对结果，记录相关变化检出率、无关变化误触发率和分类处置正确率；检测正确不等于用户处置正确。

持续运行验证覆盖实际数小时任务与多次变化；加速回放只能验证事件处理和状态逻辑，不能证明人员长期监督效果。

### 6.4 用户态势感知评价（EQ1）

在不同情境中检查当前状态、变化意义、目标和空间影响、后续安排及不确定性判断。用任务事实或事前明确的合理条件评分，不把随机发生的未来结果作为预测题唯一标准。

记录理解正确性、关键变化遗漏和判断耗时；说明提问对任务的影响。自编事实题不直接命名为标准 SA 测量工具，采用标准方法时遵守相应实施要求。

### 6.5 调整表达与落实判断评价（EQ2）

分别记录输入与操作的对象、范围和约束是否正确；执行端实际落实情况；用户对成功、部分落实、拒绝、失败或未知的判断；重复提交、错误确认和不恰当的后续操作。

EQ2 预先固定两项主要指标，分别对应核心反馈和支撑机制：

- **落实判断正确率**：按预先定义的要求或对象单元，正确判断落实状态的单元数／全部应判断单元数，分别报告部分落实和未知条件。
- **依据变化后的介入处置正确率**：在依据变化检查窗口中，按独立预期正确选择继续、重新确认、修订或等待等处置的次数／全部应处置次数。无关变化时不进行多余重新确认也纳入判断。

分别记录用户所选行动与系统检查、拦截结果，不以系统拦截成功代替用户理解；未响应单列，并保留在应判断或应处置分母中。错误操作、重复提交、确认次数及耗时作为辅助分析。

效率是辅助指标，不能代替正确性。未发现问题或未作出正确判断的情况需单独报告，不能只计算成功发现者的耗时。依据情境分析，不把所有结果混成一个总分。

### 6.6 核心关联反馈与支撑机制的针对性比较

优先完成关联反馈对照；支撑机制必须进行6.3的功能检查，资源允许时再安排小规模人员比较。两项比较分开控制变量：

| 比较对象 | 保持相同 | 比较差异 | 主要证据 |
| --- | --- | --- | --- |
| 核心关联反馈 | 任务与执行事实、依据检查及 M1/M2 的其他功能 | 相同事实分散展示／按同一用户要求关联展示 | 落实判断正确率、部分落实发现及后续操作 |
| 依据变化后的交互处置 | 执行端检查与拒绝能力、任务事实、关联反馈及可用操作 | 常规变化或冲突提示／说明受影响要求、保留有效输入并按条件重新确认 | 介入处置正确率、无关变化打断与额外确认成本 |

不通过关闭基线执行检查制造优势，也不把新增后台拒绝能力归因为交互效果。若未开展第二项人员比较，只报告支撑机制可运行及其功能结果，不宣称其独立改善用户表现。

在不同调整来源或业务事件中核查适用性，不仅使用道路封闭的不同结果分支；优先检验部分落实、延迟、连续修改等易混淆条件，同时保留正常成功案例。若只比较整套方案，结论限于整体效果，不能单独归因于关联反馈。

### 6.7 长时证据、辅助评价与结果解释

分别报告系统实际长时运行、短时人员介入和人员实际数小时监督。短时实验不支持降低疲劳或改善长时警觉性的结论；证据不足时限制结论，并审视题目与适用范围。

平衡体验顺序，采用难度相当场景，按参与者和情境报告数据。同一人的多次操作不当作独立参与者。按数据条件进行描述、效应和不确定性分析，不预写显著改善。

主观负荷、控制感与访谈辅助解释。报告未改善、额外确认成本和反效果；如方法增加负担又未改善关键判断，应修订机制或收缩贡献。

## 7. 讨论

### 7.1 专业依据、机制与实际效果

分析观察与理论启示是否一致，区分理论、设计假设、工程规则和实验发现。整套界面改善不证明理论或五项准则分别被验证。

### 7.2 候选创新的价值与适用条件

对照已有方法说明关联反馈帮助了哪些协作条件，哪些情况下普通反馈已经足够；分析依据检查与重新确认如何支撑关联链、何时无须打断，以及错误依赖判定和确认负担的代价。区分跨结果状态、跨业务案例和跨应用的证据，不能由一个案例推广至所有无人系统或 Agent 应用。

### 7.3 人工参与成本与 Agent–Frontend 分工

讨论信息、解释、确认和主动地图操作的帮助与干扰，分析规则、共享状态和工具的取舍。没有专门比较时不推出工具普遍优于规则；确认次数更多也不自动意味着更有效。

### 7.4 研究有效性与边界

说明参与者经验、场景覆盖、模拟程度、反馈可获得性、任务时长和平台能力对结论的影响。数据源缺失不能靠呈现机制补成事实，应用背景不直接构成长时效果证据。

## 8. 结论与展望

### 8.1 结论与贡献

回答 G1/G2、EQ1/EQ2，归纳完整协作机制、核心候选关联反馈和依据有效性支撑机制各得到何种证据支持。区分已提出、已实现、已验证及仍待验证的内容。

### 8.2 后续工作

依据实际不足安排更多协作情境、真实平台接入和更长期研究。用户状态估计只在必要性得到支持后引入，并继续遵守原工程约束。

| 新版一致性主线可能扩大研究范围 | 保留旧版题目、八章与三项机制；按一项核心候选创新加一项支撑机制组织 |
| 条件变化处理只有原则性描述 | 4.2.4增加相关性、可行性、取舍变化与依据不足的判定及重新确认规则 |
| 前端校验可能被误认为执行保证 | 5.2明确职责与模拟边界，4.2.4区分提交检查和执行前复核 |
| 新增机制缺少对应验证 | 6.3补充变化与处置核查，6.5固定两项EQ2主指标，6.6分开比较并控制后台能力 |

第2章提供依据，第3章形成需求与框架，第4章设计机制，第5章实现，第6章验证，第7章解释。八节为研究与写作结构，投稿时可按篇幅压缩，不省略论证关系。
