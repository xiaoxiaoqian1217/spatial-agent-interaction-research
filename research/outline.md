## 研究主线

### 一个核心问题

> 在长时空间任务中，如何让用户持续理解 Agent 的执行情况，并在必要时有效调整执行？

### 两个核心目标

1. **支持正确的用户态势感知**：用户知道发生了什么、理解其与任务目标的关系，并能判断后续影响。
2. **支持有效的人机协同控制**：用户能够适时介入、调整执行，并确认调整是否真正生效。

用户需要理解情况才能合理干预，干预后的反馈又帮助用户更新理解。研究中的“态势感知”指用户对执行情况的理解。

### 两个可验证评价问题

- **EQ1：** 相比基础交互，本文机制能否帮助用户更准确地理解 Agent 当前执行状态、关键变化及其后续影响？
- **EQ2：** 本文机制能否帮助用户正确实施任务调整，并准确判断调整是否真正生效？

EQ1 与 EQ2 分别对应两个核心目标，并在第 6 节通过任务事实、实际操作结果和辅助主观评价获得证据。

### 五个交互设计维度

| 设计维度 | 核心问题 | 主要支撑目标 |
| --- | --- | --- |
| 注意力选择 | 哪些信息值得关注，何时需要提醒？ | 态势感知 |
| 状态可理解性 | 当前在做什么，为什么处于这个状态，对目标意味着什么？ | 态势感知 |
| 连续性 | 当前事件如何关联目标、计划和地图对象？调整前后及离开返回时如何衔接？ | 两个目标 |
| 可预期性 | 下一步准备做什么，可能产生什么影响，还有哪些不确定性？ | 两个目标 |
| 可介入性 | 用户何时、以什么范围介入，如何确认修改生效？ | 协同控制 |

五维作为候选交互设计框架，后续通过文献、任务需求分析和评审说明形成依据、边界及关系。各维度可以交叉，不要求分别归入两个互不相交的分支，也不分别扩展为五个独立研究方向。

金字塔原理用于组织研究问题及其支撑关系。论文的理论依据来自态势感知、自动化监督、人机协同以及空间信息交互等研究，设计效果需要通过验证获得证据。

## 3. 任务需求与五维交互框架

### 3.1 长时空间任务定义、特征与研究边界

本文不以绝对运行时长定义“长时”。研究重点是执行期间出现状态演化、上下文累积和用户重新介入问题的空间任务。代表性任务通常具有以下特征：

- 执行跨越多个阶段；
- 任务或环境状态持续变化；
- 计划可能在执行过程中调整；
- 用户可能离开执行回路后重新返回；
- 任务对象之间具有持续的空间关系；
- 执行过程中存在用户介入机会。

上述特征用于选择研究任务和说明适用边界，不要求所有任务机械满足相同阶段或固定时长。

### 3.2 用户需求与两个核心目标

从实际任务中的理解和干预困难，归纳态势感知与协同控制需求，建立需求与目标的对应关系。

### 3.3 五维交互框架的构建过程、定义与边界

五维不能仅通过逐项寻找支持文献获得，而需要展示可追溯的构建过程：

**文献或任务观察 → 用户困难 → 设计需求 → 候选维度 → 合并、去重与修订 → 五维框架。**

给出各维度的定义、边界和相互作用，并检查遗漏或重复。尤其说明“连续性”共同处理的是跨阶段、计划变化、任务与空间对象关联以及用户离开返回时的上下文联系，而不是多个无关问题的简单合并。

### 3.4 关键执行情境与五维需求映射

分析正常持续执行、关键状态变化、计划变化与重规划、等待用户决定、异常与恢复、用户离开后返回、用户主动调整等情境，建立“关键执行情境 × 五维设计需求”矩阵。

执行过程允许等待、重规划、异常恢复等循环，不假定所有任务必然按同一组固定阶段线性推进。

矩阵用于回答：在当前情境中，用户最需要解决什么问题，哪些维度应优先获得支持，为什么需要对应机制。

### 3.5 需求、维度与机制的对应关系

将框架落实到第 4 节的三类机制：

| 具体机制 | 主要落实的设计维度 |
| --- | --- |
| 执行信息组织与呈现 | 注意力选择、状态可理解性，并通过变化摘要支持连续性与可预期性 |
| 任务与地图关联 | 连续性、状态可理解性、可预期性，并支持用户确定干预对象 |
| 动态干预与结果反馈 | 可介入性，并通过影响预览、生效与失败反馈支持可预期性与连续性 |

上述对应允许交叉，用于指导设计和后续分析，不预设为已经验证的因果关系。

**本节产出：有依据且可追溯的五维框架、关键执行情境与需求矩阵、需求到机制的对应关系。**

## 4. 交互机制设计

### 4.1 执行信息组织与呈现

#### 4.1.1 面向任务目标的信息组织

将执行事件组织成目标、计划、进度、异常与结果，区分内部事件和用户需要理解的任务状态。

#### 4.1.2 信息分层与注意力引导

确定摘要、详情和主动提醒的使用方式，突出关键变化，控制信息负担。

#### 4.1.3 状态含义与行为依据表达

基于任务约束、工具结果和已知事实解释状态及变化原因，并表达必要的不确定性。

#### 4.1.4 离开后返回的变化摘要与上下文恢复

当用户离开执行过程后重新返回时，集中呈现离开期间的关键变化、对原目标或计划的影响、当前执行位置以及尚待处理的决定，帮助用户恢复任务上下文，而不是要求其重新浏览全部执行日志。

### 4.2 任务与地图关联机制

#### 4.2.1 任务、计划步骤与空间对象关联

关联任务目标、执行步骤、设备、路径和区域，使用户能够在任务视图与地图之间理解同一执行过程。

#### 4.2.2 执行变化与后续影响表达

呈现当前执行范围、计划前后差异、已完成与未完成部分，以及调整可能影响的任务和区域。区分计划中的下一步与对后果的预测。

#### 4.2.3 地图交互中的 Agent–Frontend 协同边界

本小节不将问题简化为“规则还是 Agent”，而是区分前端在 Agent 执行过程中的三种职责：确定性呈现、提供交互上下文、提供可调用的交互能力。

| 前端参与方式 | 核心问题 | 适用原则 | 地图例子 |
| --- | --- | --- | --- |
| **前端规则** | 已有业务结果如何稳定呈现？ | 当业务状态或 Agent 结果已经足以唯一确定界面行为时，由前端按确定性规则响应，不再引入 Agent 决策 | Agent 返回路线数据后，前端按固定策略绘制路线、突出关键点并调整视野 |
| **共享前端状态 / 上下文** | Agent 是否缺少当前交互环境中的必要信息？ | 仅向 Agent 提供影响当前任务判断的最小必要状态；适合持续、体量可控的交互状态 | 用户说“调整我当前选中的区域”，前端提供当前选区几何、活动任务或正在编辑对象 |
| **Frontend Tool / 前端交互能力** | Agent 的任务执行是否需要请求当前前端交互环境完成一个能力？ | 当调用时机属于 Agent 的任务决策，或任务需要依赖当前交互环境完成动作并取得结果时，通过受控工具调用；需要时将执行结果返回 Agent 继续任务 | Agent 执行到需要用户补充空间约束的步骤，请求前端进入区域选择或路线编辑交互，并取得用户完成后的几何结果 |

判断顺序如下：

1. **已有业务结果是否已经能够确定地图响应？** 若能，优先使用前端规则。
2. **Agent 是否只是缺少当前前端上下文？** 若是，优先共享最小必要状态；若状态适合按需获取、实时计算或不适合持续同步，再考虑读取型前端能力。
3. **Agent 是否需要主动请求当前前端完成一次交互或执行能力？** 若是，使用受控 Frontend Tool，并在后续任务需要时将执行结果返回 Agent。

需要特别区分：

- **工具与规则并不互斥。** Frontend Tool 描述 Agent 如何调用前端能力；工具内部如何执行仍可以完全由确定性规则控制。
- **需要前端参与不等于需要增加前端 Agent。** 前端可以只提供共享状态和受控函数，由业务 Agent 在必要时使用。
- **存在自然语言或语义解析不等于必须使用 Frontend Tool。** Agent 可以先解析用户指代或业务意图，随后由前端规则完成已经确定的地图呈现。

本节关注的是在人—Agent—地图协同中如何分配信息、决策和交互能力：前端何时只是呈现执行结果，何时作为 Agent 的交互上下文来源，何时作为 Agent 可调用的执行资源。具体状态同步、工具注册、调用传递、参数校验和结果回传放在第 5 节；其适用边界在第 7.3 节结合验证观察讨论。工具调用能力本身不作为用户态势感知改善的证据。

### 4.3 动态干预与结果反馈

#### 4.3.1 介入时机、对象与范围

明确用户何时需要确认、调整、暂停或中止任务，以及能够修改的目标、约束和任务部分。

#### 4.3.2 修改影响与计划衔接

说明修改从何处生效、对未完成任务的影响，以及已完成部分如何保留和解释。

#### 4.3.3 干预生效、失败与执行恢复反馈

区分修改请求已提交、已被接受、部分接受、被拒绝和实际生效等状态。说明已经完成或已超出可修改阶段的任务部分，反馈更新后的计划与实际执行情况；当修改未完全生效或执行失败时，说明原因、影响范围和可恢复方式，支持用户正确判断任务是否按新要求继续。

**本节产出：能够实施的交互机制及其运行规则，并说明每项机制对应的用户需求。**

## 6. 实验与评估

### 6.1 研究设计、参与者与对比条件

结合领域专家评审与小规模用户任务实验。内部成员应具备与目标用户相近的任务背景，说明参与者来源和经验。

对比基础交互方案与本文方案，保持任务、Agent 能力、地图数据和可用业务操作尽量一致，避免将能力差异误归因于呈现方式。使用难度相近的任务并安排不同使用顺序，控制学习影响。

**基础交互方案**应提供合理的传统 Agent 交互能力，例如 Agent 对话、地图、常规任务状态或进度，以及与实验方案相同的基本业务操作与干预能力；但不提供本文重点机制中的任务—计划—空间对象连续关联、关键变化摘要、干预影响范围表达和明确的生效/失败反馈。

**本文方案**在相同业务能力基础上加入第 4 节提出的交互机制。这样对比主要检验交互组织和协同机制的价值，而不是“有信息”相对于“没有信息”的价值。

### 6.2 五维框架评审

检查维度定义是否清楚、关键需求是否遗漏、维度之间是否重叠，以及框架能否帮助形成可实施的设计。专家评审用于检验框架合理性、覆盖性和可实施性，不替代用户任务实验中的效果证据。

### 6.3 用户态势感知评估（对应 EQ1）

围绕离开后返回、环境或计划变化等情境，考察用户对当前状态、关键变化、变化意义和后续影响的判断是否正确。以预设任务事实和实际执行状态为判断依据，不能仅凭界面提供了信息就认定用户已经理解。

主要证据可包括状态理解正确率、关键变化识别、后续影响判断和离开返回后的上下文恢复表现。

### 6.4 人机协同控制表现评估（对应 EQ2）

围绕执行中修改要求及失败或部分生效情境，考察用户是否选择正确的干预对象和范围、能否完成指定调整、实际执行是否符合修改要求，以及用户能否正确识别修改已生效、部分生效或未生效。

任务完成时间等效率指标可作为辅助指标，但不替代干预正确性和生效判断。

### 6.5 辅助评价与访谈

结合认知负荷、控制感和访谈解释效果与问题。用户信任可作为辅助观察；若研究信任校准，需对照系统实际能力和用户判断另行设计测量，不能仅用满意度代替。

### 6.6 结果分析

按 EQ1、EQ2 和两个核心目标报告结果，结合五维解释观察到的问题和机制表现。区分框架评审结果与用户实验结果；整套界面更有效不能直接证明每个维度都不可缺少，也不能仅凭少量案例得出普遍性的 Agent 与规则优劣结论。

样本量、量表、统计方法和最终任务脚本在实验方案中确定。小样本结果按探索性证据强度解释，不预写普遍适用或显著提升的结论。

**本节产出：与研究目标对应的验证证据，以及对效果、失败情境和适用条件的分析。**

## 7. 讨论

### 7.1 信息充分性与注意力负担

讨论更多信息、解释和提醒在何种情况下帮助用户，何种情况下增加负担。

### 7.2 执行连续性对用户态势感知的支持作用

结合跨阶段、计划变更与中断恢复的结果，讨论连续性如何支持理解。传统态势感知理论已包含时间属性，不预先声称连续性是对该理论的扩展。

### 7.3 Agent–Frontend 协同与规则响应的适用边界

根据原型和验证观察，讨论前端何时适合作为确定性呈现层、何时需要向 Agent 提供交互上下文、何时值得作为 Agent 可调用的执行资源，以及主动前端操作何时可能干扰用户。若没有专门的比较证据，本节将结论限定为设计取舍和观察到的适用条件，不推导普遍性的 Agent、Frontend Tool 与规则优劣结论。

### 7.4 研究有效性、适用范围与局限

讨论参与者经验、样本规模、任务与原型条件的影响，区分在长时空间任务中获得的证据与对其他 Agent 场景的迁移设想。

## 8. 结论与展望

### 8.1 研究结论与贡献

回答核心研究问题和两个评价问题，归纳获得理论与验证证据支持的框架、机制和发现。

### 8.2 后续工作

结合实际局限，说明更复杂任务、不同用户群体或其他应用场景的后续验证方向。
