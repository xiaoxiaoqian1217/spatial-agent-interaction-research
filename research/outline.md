## 研究定位与全文主线

### 业务背景与研究对象

空中、地面、四足三类异构无人平台（无人机、无人车、机器狗）组成班组，各由对应执行智能体直接控制；另设态势、情报、规划三类支撑智能体。操作员通过现有终端开展在环远程监督，必要时参与决策和调整。

**长时空间 = 长时程（任务持续数小时以上）+ 广域（被控对象分布于地理空间）。** 不擅自增加平台数量、地理面积和实测任务时长。持续变化、多次参与和空间对象关系是需要分析的任务特征；长时间运行不直接等同于疲劳或理解下降。

**全文出发点：** "长时监督"不等于全程无人监督，也不以关闭页面再返回作为必要前提——即使界面始终打开，任务持续推进、多平台并发事件和用户处理过程本身，仍会造成用户所见态势与系统实际态势的偏差。时间差不需要"离开"才发生，它内生于"编辑需要时间而执行不暂停"。这正是双态势一致性问题普遍存在的理由。

### 一个核心问题、两个目标、三项机制

> 在任务持续执行和变化时，如何支持操作员理解 Agent 的执行情况，在必要时参与决策、准确表达调整，并确认后续执行是否符合双方确认的要求？

| 层次 | 内容 |
| --- | --- |
| G1 研究目标 | 支持正确的用户态势感知：感知事实、理解其与目标的关系、判断后续影响 |
| G2 研究目标 | 支持有效的人机协同：准确参与取舍和调整，并正确判断要求是否落实 |
| M1 协同机制 | 执行信息组织与呈现，为过程理解和决策提供上下文 |
| M2 协同机制 | 用户与 Agent 的协同介入，支持双向发起、澄清、取舍、版本绑定与一致性校验、确认 |
| M3 协同机制 | 介入后的执行衔接与反馈，关联用户要求、计划变化和实际执行依据 |

三项机制共同覆盖理解、参与和确认的协作关系。正常执行可以持续由 M1 支持，不强制每个事件触发人工介入；M2、M3 可多次发生并更新 M1。结果交付需要对照目标和已确认要求，不能只用一次 Agent 运行结束代替业务完成。

**贯穿性矛盾（窄核）：** 任务持续执行，而操作员理解情况、编辑调整、提交确认需要时间；其依据的态势快照（记为 C_v）与提交时系统实际态势（记为 C_{v+k}）之间存在时间差。本文称两者为"双态势"，方法核心是介入全过程中对该时间差的一致性管理：介入时绑定所依据的态势版本，提交时校验其有效性，对冲突分类处置，并在介入后持续反馈落实状态。两类触发（操作员主动调整、任务变化驱动的取舍）进入同一介入调整事务。论文组织单位是"一次完整任务中的人机协同全过程"，不是单个局部事件；长时任务中的调整是协同的常态工作方式，不是异常处理。

“用户态势感知”指用户对任务的感知、理解和预测；系统估计用户负荷或响应状态属于另一问题。"双态势"在本大纲中重新释义为：操作员所见的任务态势快照与系统实时运行态势；二者的时间差管理（双态势一致性）为本文核心方法线索。原义中的用户状态估计不作为本文方法；若后续作为扩展引入，必须遵守零新增硬件、仅用终端行为日志、离散等级和轻量可解释规则的约束，不能将响应变慢直接认定为疲劳。

### 两个评价问题

- **EQ1（对应 G1）：** 在相同任务信息可获得的条件下，本文机制能否帮助用户更准确地理解当前执行、关键变化及后续影响？
- **EQ2（对应 G2）：** 本文机制能否帮助用户准确表达和实施任务调整，并正确识别已落实、部分落实、拒绝、失败或状态未知？

后台执行结果与用户对结果的判断分别测量，避免将执行正确等同于用户理解，或将主观控制感等同于实际落实。

## 1. 引言

### 1.1 研究背景

介绍异构无人平台班组的长时空间任务与操作员远程监督形态，说明目标委托、自主执行和必要人工参与的衔接需求，明确论文研究人—Agent—界面的协作关系。

### 1.2 核心问题与工程动机

分析执行信息分散、变化对目标的影响难理解、调整指代和范围不明确、方案更新与实际落实容易混淆等候选问题。通过项目流程、日志或走查核查，不能将未观察到的现象写成已证实痛点。

围绕“理解执行—必要参与—确认落实”提出问题。告警风暴、疲劳识别、离席返回不设为必然前提；告警在影响任务理解和决策时进入研究。明确写出：即使界面始终打开、操作员全程在环，任务推进与多平台事件仍使其依据的上下文发生变化——一致性问题是常态介入的内生问题，而非离席恢复的特例。

### 1.3 研究目标、范围与评价问题

明确 G1/G2 与 EQ1/EQ2，解释正常监督、主动与被动参与、结果确认均属于整体研究。任务规划、平台控制及通用多智能体编排为依赖能力，本文重点是交互机制。

### 1.4 本文工作与预期贡献

概括理论和任务分析指导的框架、三项机制、原型与验证。核心候选贡献集中于 M2 与 M3 的衔接，不能把全面展示功能当成创新，也不因关注一项候选贡献而缩小整体主题。

## 2. 理论基础与相关研究

**本章回答“为什么这样设计、已有方法做到哪里”。每节给出概念、适用解释、设计启示与边界。**

### 2.1 用户态势感知与执行透明性

以 Endsley 情境感知模型区分感知、理解和预测，分析操作员对事实、目标意义和未来影响的信息需求。结合 Agent 透明性研究，说明解释应基于任务约束、工具结果和可核查事实，展示内部日志不等于帮助理解。

区分下一步计划与后果估计，表达不确定性。结合脱离回路与自动化监督研究讨论注意力转移和重新参与的条件，不由时长直接推出疲劳；页面持续打开也不代表用户持续理解。

### 2.2 行动模型、执行鸿沟与评估鸿沟

以 Norman 行动模型分析目标到操作、结果到评价之间的困难：

- 执行鸿沟：用户意图与可操作对象、范围及约束的转换。
- 评估鸿沟：系统实际变化与用户判断是否符合原要求的转换。
- 设计启示：对象映射、操作边界、调整确认、结果对照和反馈。
- 理论边界：认知模型不直接保证后台一致性，关联、执行衔接和异常规则仍需工程实现及验证。

### 2.3 混合主动交互与人机监督协同

将混合主动交互明确为交互范式，讨论用户与 Agent 分别发起请求、提出或拒绝方案、澄清并继续任务的方式。结合监督职责和业务权限，区分发起建议、批准方案、执行及运行中调整的责任。

“谁发起交互”不等于“谁拥有执行权限”。当前不承担根据心理状态动态切换自动化等级的研究。

### 2.4 共同基础与闭环沟通

以共同基础理论（grounding）说明协作双方必须就"话是针对什么说的"达成一致；以贡献模型区分"呈现"与"接受"两阶段。引入航空闭环沟通（复诵—核对—纠正）及其"收到不等于理解、理解不等于执行"的原则，分析其在长时异步执行中的扩展：任务持续数小时时，"已接受"与"已生效"不再同时发生，确认需分阶段。设计启示：意图结构化表达、决定依据记录、分阶段生效反馈。

### 2.5 并发控制与运行中动态变更

为"编辑期间任务仍在执行"的一致性管理提供方法来源：操作变换的意图保持准则（并发修改后原意图是否仍成立）、乐观并发控制的"读—验证—写"三阶段（提交时校验依据是否过期）、长事务补偿（已执行步骤不可回滚、只能补偿）、业务流程管理对运行中实例动态修改的正确性准则。设计启示：介入起草＝读（基于态势快照）、提交＝验证（快照是否过期）、处置＝写或退回重新确认；冲突需从文本/数据语义翻译为本领域语义（空间约束、步骤可执行性、平台阶段）。上述机制来自文档协同与数据库领域，未见迁移到操作员—自主执行体任务调整的先例；迁移时的语义差异需在 2.7 的比较中说明，工程迁移不自动等于方法创新。

### 2.6 空间任务中的可视化与交互研究

围绕任务、计划步骤与平台、路径、区域的关联，比较空间选择、计划差异表达和多视图对应。说明地图在理解、表达与核查中的作用，不以界面有地图作为空间研究的充分依据。

### 2.7 已有研究比较与候选贡献定位

比较目标用户、任务条件、可见信息、介入表达、可修改范围、不可回退动作处理、落实判断和验证方式。核查已有方案是否支持用户要求与计划、执行依据的对应，以及部分落实与连续调整的处理。

将领域应用、已有技术组合、机制改进分别说明。不得先认定空白，再选择性寻找文献；工程迁移可以有价值，但不自动等于方法创新。

### 3.3 用户目标、关键决策与信息需求

对 S1—S6 按“用户目标—需要作出的决策—必要信息—可用操作—结果判断条件”进行任务分析。保留来源：实际观察、日志、专家反馈或待验证假设。

归纳 R1 理解执行及变化、R2 准确参与与调整、R3 确认落实及后续处理。原五维改为重点突出、含义清楚、上下文连续、后果可预期、操作边界明确等跨机制准则，允许交叉，不再证明五维完备性和独立因果作用。

### 3.4 协同交互总体框架、双态势一致性与共享任务上下文

定义 M1—M3 的职责、输入输出与衔接，以及任务目标、计划步骤、空间对象、执行状态、用户决定、调整记录和执行依据之间的关系。区分任务生命周期、一次 Agent 运行和一次人工介入。

**双态势一致性的形式化（全文定义基准，配"两线分叉"示意图）：** 操作员开始介入时依据的态势快照记为 C_v，提交决定时系统实际态势记为 C_{v+k}；两者在任务进度、平台位置与阶段、约束条件上的差异称为时间差。调整意图 I 以 C_v 为依据；系统职责为判定 I 在 C_{v+k} 下的可满足性并分类处置，而非假定执行在编辑期间暂停。冲突的一般定义：使 I 的全部或部分无法在 C_{v+k} 下安全、有效执行的状态差异。介入调整事务的生命周期：起草（基于 C_v）→ 绑定（记录 C_v 版本）→ 校验（对 C_{v+k}）→ 处置（接受/部分接受/重新确认/拒绝）→ 确认（分阶段生效反馈）→ 跟踪（执行落实与回顾）。

**候选创新在本节体现为：①双态势一致性的判定与处置；②同一调整要求如何贯穿表达、计划变化和落实反馈，并在再次调整时保持联系。** M3 将落实依据返回 M1，支撑继续理解和必要再介入；正常监督与结果交付仍在框架内。

### 3.5 需求、情境、机制与验证的可追溯关系

| 需求 | 重点情境 | 机制设计 | 评价对应 |
| --- | --- | --- | --- |
| R1 执行理解 | S1、S2，并贯穿 S3—S6 | 状态、目标意义、空间对象和影响关联 | EQ1 |
| R2 准确参与 | S1、S3、S4、S5 | 请求上下文、对象范围、取舍、澄清与确认 | EQ2 的表达与操作 |
| R3 落实确认 | S3—S6 | 用户要求、计划差异与执行依据关联 | EQ2 的结果判断与后续处理 |

在本章记录情境覆盖，在第六章记录具体案例怎样覆盖这些情境。不能以同一案例的不同结果分支自称覆盖整个应用。

**本章产出：** 角色与任务分析、协作情境表、设计准则、总体框架及需求—机制—验证矩阵。

## 4. 协同交互机制设计

### 4.1 执行信息组织与呈现机制（M1）

#### 4.1.1 面向目标和决策的信息组织

将事件组织为理解确认、计划、进展、关键变化、异常和结果；区分事实、解释、计划与后果估计。针对正常监督、征询、调整及结果确认确定信息重点。

#### 4.1.2 任务、计划与空间对象关联

使任务视图和地图中的平台、路径、区域能够相互定位，说明变化在哪里、与何种任务相关、影响哪些部分。地图持续支撑过程理解，不仅在出现障碍后使用。

#### 4.1.3 信息分层、变化摘要与影响说明

采用摘要、详情和必要提醒，突出当前决策所需内容并保留依据。区分计划下一步与可能后果，标明估计条件和不确定性。重新参与时的变化摘要仅在任务需要时设计，不将离席当成必然前提。

### 4.2 用户与 Agent 的协同介入机制（M2）

#### 4.2.1 双向发起与职责边界

支持 Agent 征询和用户主动补充、修正；明确提出、确认、拒绝、取消、暂停与继续的权限和条件。只有任务取舍、权限或新约束要求时才进入人工决策。既有规划可自动处理的变化不机械请求确认。

#### 4.2.2 介入上下文与准确表达

将原因、目标任务、涉及对象、可修改范围、相关约束与选项共同呈现。自然语言、地图选择和受控组件可组合使用；不明确的对象与约束需澄清。

绑定决定所依据的态势版本：记录用户起草时所见快照 C_v 的标识，作为提交时校验与后续追溯的输入。输出明确的用户决定及其适用上下文。前端选区完成仅说明输入形成，不能代表任务调整落实。相关规则应适用于范围、优先级或资源安排等业务允许的调整，不绑定单一事件。

#### 4.2.3 影响预览、计划确认与条件变化处理

将用户要求与候选计划差异关联，呈现保留、改变及不能调整的部分，允许接受、修订或放弃。用户确认方案与执行端接受指令分别反馈。

若用户操作期间的状态变化会实质影响可行性或调整范围，更新影响说明或重新确认；不对无关变化重复打断。明确决定依据，避免在新状态下直接执行过时决定。

### 4.3 介入后的执行衔接与反馈机制（M3）

#### 4.3.1 调整意图、计划变化与执行依据关联（核心候选创新）

定义最小关联内容：调整记录与目标约束、涉及的任务和空间对象、确认时的计划与差异、生效条件、执行端反馈及来源和时间。一个调整可对应多个步骤与平台。

说明关联的创建、更新、按用户要求汇总和被后续调整替代的规则。以此支持用户核查原要求，而非仅显示分散的状态标签。数据关联本身不预设为创新，需比较已有方案并验证其交互价值。

#### 4.3.2 依据驱动的落实状态表达

区分请求接收、方案更新、指令下发、执行端接受、开始按新方案执行及后续结果。具体阶段由可获得的业务依据确定，不虚构后端反馈，也不要求所有任务经过同一线性序列。

缺少证据时显示待确认或未知，多对象调整保留部分落实情况。“开始执行”不等于“任务完成”或“未来持续满足约束”。阶段与最终结果需对照目标和已确认要求呈现。

#### 4.3.3 异常与连续调整的执行衔接

对应用户要求说明已落实、未落实、不能判断的部分及原因；明确已发生动作或已超出可修改阶段的部分，依据既有能力提供重试、修订、取消或恢复入口。

连续调整时标明反馈属于哪次决定、是否被替代，防止迟到的旧反馈覆盖当前状态。外部动作不能通过回退对话撤销，后续调整以实际状态为依据。

**本章产出：** 信息规范、双向协作流程、调整关联与状态规则。候选创新具体承载于4.2.2—4.3.3，其余内容支撑完整协作主题。

## 5. 原型系统设计与实现

### 5.1 原型范围与总体架构

说明监督终端、交互适配层、既有智能体和执行端之间的职责及信息流。标明真实接入、模拟和未实现部分，不重建完整无人平台或通用多智能体系统。

### 5.2 任务、调整与执行事件的关联实现

实现任务标识、计划变化、介入及调整记录与反馈关联，区分任务与 Run，处理重复事件、迟到反馈和连续修改。消息传输完成不等于任务执行完成。

结合实际选择描述 MQTT、HTTP/SSE、AG-UI 等实现手段；协议接入本身不作为研究贡献。

### 5.3 前端规则、共享状态与受控工具

| 前端职责 | 使用条件 | 例子 |
| --- | --- | --- |
| 确定性呈现 | 已有业务结果足以确定响应 | 绘制路径、突出区域、显示已知状态 |
| 共享交互上下文 | Agent 缺少当前交互环境中的必要信息 | 提供当前选区、编辑对象及相关任务，只共享必要状态 |
| 可调用前端能力 | Agent 需要前端完成交互或执行能力并取得结果 | 请求区域选择或路线编辑，取得结果后继续 |

判断顺序：结果可确定则用规则；仅缺上下文优先共享，按需读取或计算的可用读取型能力；需要主动请求前端完成交互时采用受控工具。工具内部可使用规则，自然语言不必然需要工具，前端参与不必然增加前端 Agent。

说明注册、参数校验、执行及取消/失败回传。前端工具完成与设备调整落实分别处理，使用工具本身不构成效果证据。

### 5.4 面向协作情境的核心界面实现

以 S1—S6 展示目标和计划确认、过程监督、征询与主动调整、恢复和结果确认的界面及状态关系，复用 M1—M3，避免为每个业务事件各造一套界面。

### 5.5 具体业务案例与端到端流程

主案例采用**区域持续侦察任务**（长时空间任务的典型形态）：异构班组分区侦察数小时，写成"完整任务剖面＋2–3 个介入窗口"的结构——任务剖面为粗粒度（下发与启程、常态执行、收尾），介入窗口为分钟级时间线特写。介入窗口至少包含：**一次用户主动调整**（如依态势判断调整复查优先级，对应主动参与）与**一次变化驱动取舍**（空域临时管制："后续避开该区域，已完成部分保留"；编辑期间平台进入管制区、步骤完成、平台电量告警等构成冲突类型的实例）。两类触发进入同一介入调整事务。分钟级特写仅用于介入窗口，任务其余部分粗写。

道路封闭等其他案例用于展示跨事件适用性，不以其成功、部分成功、失败分支代替协作情境覆盖。案例数依据覆盖和资源确定。方案和效果数据据实际能力或明确的模拟规则给出。此处才细化地图数据、操作步骤、反馈序列及异常分支。案例参数全部脱密，采用公开仿真想定。

## 6. 实验与评估

### 6.1 评价问题、参与者与公平对照

区分机制合理性、功能正确性、用户效果三类证据。说明内部人员经验与目标用户的差异，按资源和目标确定样本、任务数和分析方法。

基线采用真实现有界面或有依据的合理方案，保留同等业务能力、地图数据、可用操作、任务事实及基本成功/失败反馈。本文方案改变信息组织和关联方式，不能通过删除基线必要反馈制造优势。记录实际可获得信息、视觉复杂度和数据入口的差异。

### 6.2 情境覆盖与机制合理性评审

依据 S1—S6 建立覆盖表：每个情境的需求、实现、案例、指标和未覆盖部分。专家评审检查任务需要、定义、边界及机制衔接，不再评价五维独立性和完备性。

区分两种覆盖：**协作情境覆盖**包括委托、监督、征询、调整、恢复和结果确认；**结果状态覆盖**包括成功、部分落实、拒绝、失败及未知。二者不能互相替代。

### 6.3 功能、状态关联与持续运行验证

用可重复脚本或实际记录核查正常流程、双向介入、关联更新、结果确认，以及部分落实、连续修改和迟到反馈。真值来自执行端回执、观测或独立场景规则，不能用界面自身状态标签自证正确。

持续运行验证覆盖实际数小时任务与多次变化；加速回放只能验证事件处理和状态逻辑，不能证明人员长期监督效果。

### 6.4 用户态势感知评价（EQ1）

在不同情境中检查当前状态、变化意义、目标和空间影响、后续安排及不确定性判断。用任务事实或事前明确的合理条件评分，不把随机发生的未来结果作为预测题唯一标准。

记录理解正确性、关键变化遗漏和判断耗时；说明提问对任务的影响。自编事实题不直接命名为标准 SA 测量工具，采用标准方法时遵守相应实施要求。

### 6.5 调整表达与落实判断评价（EQ2）

分别记录输入与操作的对象、范围和约束是否正确；执行端实际落实情况；用户对成功、部分落实、拒绝、失败或未知的判断；重复提交、错误确认和不恰当的后续操作。

效率是辅助指标，不能代替正确性。未发现问题或未作出正确判断的情况需单独报告，不能只计算成功发现者的耗时。依据情境分析，不把所有结果混成一个总分。

### 6.6 核心候选创新的针对性比较

资源允许时固定主要信息和 M1/M2 的其他功能，比较相同调整、计划和执行事实分别展示，与显式关联到同一用户要求的展示。重点检验落实判断、部分落实发现及后续操作。

在不同调整来源或业务事件中核查适用性，不仅使用道路封闭的不同结果分支；优先检验部分落实、延迟、连续修改等易混淆条件，同时保留正常成功案例。若只比较整套方案，结论限于整体效果，不能单独归因于关联反馈。

### 6.7 长时证据、辅助评价与结果解释

分别报告系统实际长时运行、短时人员介入和人员实际数小时监督。短时实验不支持降低疲劳或改善长时警觉性的结论；证据不足时限制结论，并审视题目与适用范围。

平衡体验顺序，采用难度相当场景，按参与者和情境报告数据。同一人的多次操作不当作独立参与者。按数据条件进行描述、效应和不确定性分析，不预写显著改善。

主观负荷、控制感与访谈辅助解释。报告未改善、额外确认成本和反效果；如方法增加负担又未改善关键判断，应修订机制或收缩贡献。

## 7. 讨论

### 7.1 专业依据、机制与实际效果

分析观察与理论启示是否一致，区分理论、设计假设、工程规则和实验发现。整套界面改善不证明理论或五项准则分别被验证。

### 7.2 候选创新的价值与适用条件

对照已有方法说明关联反馈帮助了哪些协作条件，哪些情况下普通反馈已经足够。区分跨结果状态、跨业务案例和跨应用的证据，不能由一个案例推广至所有无人系统或 Agent 应用。

### 7.3 人工参与成本与 Agent–Frontend 分工

讨论信息、解释、确认和主动地图操作的帮助与干扰，分析规则、共享状态和工具的取舍。没有专门比较时不推出工具普遍优于规则；确认次数更多也不自动意味着更有效。

### 7.4 研究有效性与边界

说明参与者经验、场景覆盖、模拟程度、反馈可获得性、任务时长和平台能力对结论的影响。数据源缺失不能靠呈现机制补成事实，应用背景不直接构成长时效果证据。

## 8. 结论与展望

### 8.1 结论与贡献

回答 G1/G2、EQ1/EQ2，归纳完整协作机制及候选关联反馈机制得到何种证据支持。区分已提出、已实现、已验证及仍待验证的内容。

### 8.2 后续工作

依据实际不足安排更多协作情境、真实平台接入和更长期研究。用户状态估计只在必要性得到支持后引入，并继续遵守原工程约束。
