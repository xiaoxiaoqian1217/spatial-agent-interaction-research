## 研究主线

### 一个核心问题

> 在长时空间任务中，如何让用户持续理解 Agent 的执行情况，并在必要时有效调整执行？

### 两个核心目标

1. **支持正确的用户态势感知**：用户知道发生了什么、理解其与任务目标的关系，并能判断后续影响。
2. **支持有效的人机协同控制**：用户能够适时介入、调整执行，并确认调整是否真正生效。

用户需要理解情况才能合理干预，干预后的反馈又帮助用户更新理解。研究中的“态势感知”指用户对执行情况的理解。

### 五个交互设计维度

| 设计维度 | 核心问题 | 主要支撑目标 |
| --- | --- | --- |
| 注意力选择 | 哪些信息值得关注，何时需要提醒？ | 态势感知 |
| 状态可理解性 | 当前在做什么，为什么处于这个状态，对目标意味着什么？ | 态势感知 |
| 连续性 | 当前事件如何关联目标、计划和地图对象？调整前后如何衔接？ | 两个目标 |
| 可预期性 | 下一步准备做什么，可能产生什么影响，还有哪些不确定性？ | 两个目标 |
| 可介入性 | 用户何时、以什么范围介入，如何确认修改生效？ | 协同控制 |

五维作为候选交互设计框架，后续通过文献、任务需求分析和评审说明形成依据、边界及关系。各维度可以交叉，不要求分别归入两个互不相交的分支，也不分别扩展为五个独立研究方向。

金字塔原理用于组织研究问题及其支撑关系。论文的理论依据来自态势感知、自动化监督与人机协同等研究，设计效果需要通过验证获得证据。

## 3. 任务需求与五维交互框架

### 3.1 长时空间任务特征与研究边界

分析跨阶段执行、空间对象持续变化、计划调整、用户离开与返回等特征。围绕代表性地图任务展开，不将单纯延长运行时间作为长时任务的充分定义。

### 3.2 用户需求与两个核心目标

从实际任务中的理解和干预困难，归纳态势感知与协同控制需求，建立需求与目标的对应关系。

### 3.3 五维框架的形成依据、定义与关系

说明五维如何由文献与任务需求归纳形成；给出各维度的含义、边界和相互作用，检查是否存在遗漏或重复。

### 3.4 执行生命周期与五维需求映射

分析正常执行、计划变化、等待用户决定、用户离开后返回等关键执行情境，建立“执行阶段或情境 × 五维设计需求”矩阵。

执行过程允许等待、重规划、异常恢复等循环，不假定所有任务必然按同一组固定阶段线性推进。

矩阵用于回答：在当前情境中，用户最需要解决什么问题，哪些维度应优先获得支持，为什么需要对应机制。

### 3.5 需求、维度与机制的对应关系

将框架落实到第 4 节的三类机制：

| 具体机制 | 主要落实的设计维度 |
| --- | --- |
| 执行信息组织与呈现 | 注意力选择、状态可理解性，并支持连续性与可预期性 |
| 任务与地图关联 | 连续性、状态可理解性、可预期性，并支持用户确定干预对象 |
| 动态干预与结果反馈 | 可介入性，并通过影响预览和生效反馈支持可预期性与连续性 |

上述对应允许交叉，用于指导设计和后续分析，不预设为已经验证的因果关系。

**本节产出：有依据的五维框架、执行情境与需求矩阵、需求到机制的对应关系。**

## 4. 交互机制设计

### 4.1 执行信息组织与呈现

#### 4.1.1 面向任务目标的信息组织

将执行事件组织成目标、计划、进度、异常与结果，区分内部事件和用户需要理解的任务状态。

#### 4.1.2 信息分层与注意力引导

确定摘要、详情和主动提醒的使用方式，突出关键变化，控制信息负担。

#### 4.1.3 状态含义与行为依据表达

基于任务约束、工具结果和已知事实解释状态及变化原因，并表达必要的不确定性。

### 4.2 任务与地图关联机制

#### 4.2.1 任务、计划步骤与空间对象关联

关联任务目标、执行步骤、设备、路径和区域，使用户能够在任务视图与地图之间理解同一执行过程。

#### 4.2.2 执行变化与后续影响表达

呈现当前执行范围、计划前后差异、已完成与未完成部分，以及调整可能影响的任务和区域。区分计划中的下一步与对后果的预测。

#### 4.2.3 地图交互的触发与执行策略

本小节集中讨论 Agent 主动前端工具调用与确定性规则的职责边界。

| 内容 | 具体研究内容 |
| --- | --- |
| 由谁决定触发 | 业务状态与固定条件已能确定展示行为时，由规则触发；交互动作仍需结合任务语义判断时，由 Agent 决定 |
| 如何执行 | Agent 通过受控工具提出地图操作，前端校验参数、执行操作并反馈结果 |
| 如何保持用户控制 | 处理自动操作与用户当前操作的冲突，提供必要的提示、拒绝或恢复方式 |

先说明任务信息如何关联地图，再说明相关地图交互由谁决定、如何触发和执行。是否调用工具取决于具体交互需求，工具调用能力本身不作为用户态势感知改善的证据。

具体工具注册、调用传递与结果回传放在第 5 节；主动操作的收益、干扰与适用边界在第 7.3 节讨论。

### 4.3 动态干预与结果反馈

#### 4.3.1 介入时机、对象与范围

明确用户何时需要确认、调整、暂停或中止任务，以及能够修改的目标、约束和任务部分。

#### 4.3.2 修改影响与计划衔接

说明修改从何处生效、对未完成任务的影响，以及已完成部分如何保留和解释。

#### 4.3.3 生效反馈与执行恢复

区分修改请求已提交、已被接受和实际生效，反馈更新后的计划与执行情况，支持用户确认任务是否按新要求继续。

**本节产出：能够实施的交互机制及其运行规则，并说明每项机制对应的用户需求。**

## 6. 实验与评估

### 6.1 研究设计、参与者与对比条件

结合领域专家评审与小规模用户任务实验。内部成员应具备与目标用户相近的任务背景，说明参与者来源和经验。

对比基础交互方案与本文方案，保持任务、Agent 能力和可用业务操作尽量一致，避免将能力差异误归因于呈现方式。使用难度相近的任务并安排不同使用顺序，控制学习影响。

### 6.2 五维框架评审

检查维度定义是否清楚、关键需求是否遗漏、维度之间是否重叠，以及框架能否帮助形成可实施的设计。

### 6.3 用户态势感知评估

围绕离开后返回、环境或计划变化等情境，考察用户对当前状态、变化意义和后续影响的判断是否正确。以任务事实为判断依据，不能仅凭界面提供了信息就认定用户已经理解。

### 6.4 人机协同控制表现评估

围绕执行中修改要求，考察干预完成情况、操作时间、修改对象与生效范围的理解，以及对实际执行反馈的判断。

### 6.5 辅助评价与访谈

结合认知负荷、控制感和访谈解释效果与问题。用户信任可作为辅助观察；若研究信任校准，需对照系统实际能力和用户判断另行设计测量，不能仅用满意度代替。

### 6.6 结果分析

按两个核心目标报告结果，结合五维解释观察到的问题和机制表现。区分框架评审结果与用户实验结果；整套界面更有效不能直接证明每个维度都不可缺少。

样本量、量表、统计方法和最终基线在实验方案中确定。小样本结果按证据强度解释，不预写普遍适用或显著提升的结论。

**本节产出：与研究目标对应的验证证据，以及对效果、失败情境和适用条件的分析。**

## 7. 讨论

### 7.1 信息充分性与注意力负担

讨论更多信息、解释和提醒在何种情况下帮助用户，何种情况下增加负担。

### 7.2 执行连续性对用户态势感知的支持作用

结合跨阶段、计划变更与中断恢复的结果，讨论连续性如何支持理解。传统态势感知理论已包含时间属性，不预先声称连续性是对该理论的扩展。

### 7.3 Agent 主动界面操作与规则的适用边界

根据验证观察，讨论主动操作何时有帮助、何时干扰用户，规则与 Agent 如何分工，以及提示、拒绝和恢复机制的适用条件。与第 4.2.3 节的设计形成对应。

### 7.4 研究有效性、适用范围与局限

讨论参与者经验、样本规模、任务与原型条件的影响，区分在长时空间任务中获得的证据与对其他 Agent 场景的迁移设想。

### 8.1 研究结论与贡献

回答核心研究问题，归纳获得理论与验证证据支持的框架、机制和发现。

结合实际局限，说明更复杂任务、不同用户群体或其他应用场景的后续验证方向。
