## 研究定位与全文主线

### 业务背景与研究对象

空中、地面、四足等异构无人平台组成执行班组，各由对应执行智能体直接控制；信息处理、态势分析、任务规划等支撑智能体提供协同支持。设备群作为多智能体系统自主执行长时空间任务，操作员通过空间交互界面进行远程监督，并在必要时进行调整、否决、改派或结果确认。

**长时空间 = 长时程（数小时以上）+ 广域地理空间分布。** 本文关注的不是“任务持续时间长”本身，而是由持续运行带来的：状态不断演化、多次自主变化、多次人工介入、历史信息累积、反馈延迟与前后状态容易混淆等协同问题。

自主接替是当前业务中最能集中体现上述问题的典型场景：设备失联/异常后由设备群自动完成接替，操作员保留否决/改派权。第二场景为上级新增区域或任务变化，用于验证机制是否不仅适用于失联接替。

### 一个核心问题、两个目标、三项机制

> 在长时空间任务持续执行和变化的过程中，如何通过空间交互界面帮助操作员持续理解多智能体系统正在做什么、为什么发生变化、变化会影响什么，并在必要时准确介入并确认调整是否真正落实？

| 层次 | 内容 |
| --- | --- |
| G1 | 支持任务过程与自主变化的准确理解：当前状态、关键变化、依据、空间影响及后续安排 |
| G2 | 支持有效且校准的介入：该介入时能够正确介入，不需要介入时不过度干扰，并能确认落实结果 |
| M1 | **基于证据的任务状态与空间变化表达**：组织当前状态、关键变化、已知/未知、历史及后续安排 |
| M2 | **自主变化/决策的解释与影响呈现**：解释发生了什么、为什么、波及哪些任务/对象/区域以及仍有哪些未知 |
| M3 | **用户介入与执行结果追踪**：支持调整/否决/改派及结果确认，区分“已发送、已接受、已执行、已完成/失败/未知” |

三项机制不是固定线性流程。正常监督可长期处于 M1；发生自主变化时触发 M2；用户需要调整时进入 M3；系统执行结果再次更新 M1，并可能形成新的 M2/M3 循环。

### 两个评价问题

- **EQ1（对应 G1）：** 在相同任务事实和后台能力条件下，本文机制能否帮助操作员更准确理解当前状态、关键变化、变化原因及其空间/任务影响？
- **EQ2（对应 G2）：** 在需要与不需要人工调整的条件下，本文机制能否帮助操作员更准确表达调整、减少漏介入/误介入，并正确判断调整是否真正落实？

后台执行结果与用户对结果的判断分别测量；主观负荷、信任、控制感等作为辅助指标。

# 1. 引言

## 1.1 研究背景

异构无人平台和多智能体协同逐渐从一次性指令执行转向长时、持续、可自主调整的任务运行。操作员角色相应从直接控制者转向监督者、协作者和必要时的介入者。空间任务具有对象分布广、状态持续变化、任务与设备/区域/路径高度关联等特点，传统以静态列表、状态标签和事件消息为主的界面难以完整支撑持续理解和介入。

## 1.2 问题提出

长时运行中的关键问题不只是“系统能否自主完成任务”，而是当系统发生自主变化或用户提出新要求时，操作员是否能够：

1. 看懂当前状态和已经发生的变化；
2. 理解变化为什么发生以及会影响哪些任务和空间对象；
3. 判断是否需要人工介入；
4. 准确表达调整要求；
5. 判断调整是否真正被执行并达到要求。

自主接替场景将上述问题集中体现：系统已经解决“谁来接替”，但人的监督仍需要解决“发生了什么、为什么这样接替、影响什么、是否需要否决或改派、调整是否落实”。

## 1.3 研究目标、范围与评价问题

明确 G1/G2、EQ1/EQ2。接替算法、路径规划、设备控制、通用多智能体编排均作为依赖能力，不作为本文研究对象；本文重点研究空间交互层中的信息组织、协同介入和执行反馈机制。

## 1.4 本文工作与贡献

按“问题建模—机制设计—原型实现—功能验证—用户评价”组织贡献。贡献表述区分已提出、已实现、已验证和待验证内容。

# 2. 理论基础与相关研究

**本章回答两个问题：为什么这样设计？已有研究已经做到哪里？** 每节均给出概念、与本文的设计启示及适用边界，避免从单一理论直接推出具体控件。

## 2.1 情境感知与自主系统监督

Endsley 情境感知三级模型：感知、理解、预测；脱离回路（out-of-the-loop）与自动化监督；多机器人监督控制；监督中的中断成本与重新参与。

**设计启示：** M1 支持对当前事实、变化和空间对象的感知；M2 支持对自主变化原因和后续影响的理解与预测。短时实验结果不能直接外推为“改善长时警觉性”。

## 2.2 人机行动模型与协同介入

引入 Norman 行动模型等人机交互理论，分析“形成目标—表达意图—执行操作—观察结果—解释结果”的闭环。

**设计启示：** M3 不应只提供一个“发送指令”按钮，而需要支持对象/范围/约束表达、确认、执行反馈与结果判断，形成完整行动闭环。

## 2.3 故障、失联与不确定信息表达

故障处理框架、lost-link 工程实践、不确定性显示、预测性状态显示的收益与风险。

**设计启示：** M1 采用基于证据的信息组织：区分当前已确认事实、最后报告、未知和后续计划，不把无依据预测伪装成事实。已知/未知是信息边界；是否采用未知包络等具体形式由原型比较决定，不作为全文预设创新。

## 2.4 任务分配、接替与混合主动协同

多机器人任务分配、容错重分配、任务接力、智能体辅助再任务、混合主动调度以及人在回路/混合增强智能。

**设计启示：** 接替算法属于后台能力；本文研究重点是自主变化发生后人如何理解、判断和介入，以及人在主动提出新要求时如何与 Agent 协同。

## 2.5 可解释计划与影响表达

可解释规划（XAIP）、模型调和、对比式解释、计划差异表达、双向主动权。

**设计启示：** M2 重点表达“发生什么—为什么—影响什么—还有什么未知”，而不是展示全部推理链；自主接替可以具体化为“谁接替/依据/波及/未知”。

## 2.6 空间交互与多机器人界面

多机器人空间界面、地面站工效、地图与任务联动、任务—设备—区域—路径关系表达，以及空间选择与自然语言/结构化输入协同。

**设计启示：** 空间元素不是装饰，而应直接支持理解、表达调整和核查结果。

## 2.7 已有研究比较与本文定位

建立比较表，至少包括：研究对象与场景、用户任务、状态/变化表达、影响解释、介入方式、执行反馈、空间关联、实验设计与结论。

区分：

- 已有方法已经解决的能力；
- 本业务已确认但学术价值待验证的问题；
- 文献中可能不足但证据仍需补充的部分。

不先认定研究空白再选择性寻找文献。

## 2.8 理论—设计要求—机制—评价对应

| 专业依据 | 设计要求 | 机制 | 评价入口 |
| --- | --- | --- | --- |
| 情境感知 | 当前状态、变化、任务与空间对象关系可理解 | M1 | 状态/变化理解正确性、遗漏、耗时 |
| 不确定性表达 | 区分事实、最后报告、未知、计划 | M1 | 已知/未知判断及错误 |
| 可解释规划 | 自主变化的原因与影响可理解 | M2 | 原因、影响、后续判断正确性 |
| 行动模型 | 调整表达—执行—结果判断形成闭环 | M3 | 表达错误、重复操作、落实判断 |

# 3. 长时空间任务分析与协同交互框架

## 3.1 系统应用场景、角色与研究边界

描述班组构成、执行智能体与支撑智能体、操作员职责、后台自主能力、空间监督终端和权限边界。说明哪些为真实系统能力、哪些待核实、哪些在原型中模拟。

## 3.2 长时空间任务带来的交互问题

明确“长时”如何转化为设计需求：

- 状态持续演化，不能只看单点状态；
- 多次自主变化与人工介入需要上下文衔接；
- 历史信息持续累积，需要区分当前有效状态与旧状态；
- 反馈可能延迟、乱序或部分落实；
- 空间对象、任务和设备关系可能随执行变化。

因此需要持续的信息组织、变化解释和介入结果追踪，而不是一次性消息反馈。

## 3.3 操作员目标、关键判断与信息需求

按“目标—判断任务—必要信息—可用操作—结果判断条件”分析 R1–R5：

- R1 理解进展与空间分布；
- R2 理解关键变化和后续安排；
- R3 准确表达空间调整；
- R4 理解影响并判断是否介入；
- R5 确认落实并衔接后续任务。

每项需求标注来源：文献、业务流程、专家/内部人员核查或待验证假设。

## 3.4 协同交互总体框架

形成“理解执行—理解变化—参与调整—确认落实”的循环框架，并说明 M1–M3 输入、输出和衔接关系。

共享任务上下文至少包括：任务目标、计划步骤、设备、区域、路径、事件、当前状态、自主变化、用户调整、执行依据和结果反馈。

区分：任务生命周期、一次自主变化事件、一次人工介入，避免 Run/事件/交互操作在概念上混为一体。

## 3.5 核心验证场景与第二场景

### 3.5.1 自主接替

正常监督 → 设备失联/异常 → 系统自主接替 → M1/M2 呈现变化 → 操作员判断 → 必要时否决/改派 → M3 追踪 → 回到持续监督。

覆盖：接替合适、接替不合适、连续变化、失联恢复、部分落实/失败/未知。

### 3.5.2 新增区域/任务变化

上级新增区域或任务要求 → 系统形成调整 → 呈现原任务与新要求的空间影响 → 用户补充/修订 → 执行 → 结果确认。

用于检查三项机制是否能够跨越单一失联场景复用。

## 3.6 需求—情境—机制—验证可追溯矩阵

将 R1–R5、M1–M3、两个验证场景、实现功能和 EQ1/EQ2 一一对应，作为第 4–6 章的统一入口。

# 4. 交互机制设计

## 4.1 M1 基于证据的任务状态与空间变化表达

核心内容：

- 当前任务、设备、区域、路径双向定位；
- 当前状态与关键变化组织；
- 已确认事实、最后报告、未知、后续计划区分；
- 时间、来源和依据可追溯；
- 历史按需查看，不让旧状态覆盖当前状态；
- 自主接替场景中可具体表现为“失联前最后状态—当前未知—接替后的新任务关系”。

基线采用合理的常规状态标签、任务列表、事件记录和地图定位，而不是无反馈界面。

## 4.2 M2 自主变化/决策的解释与影响呈现

统一解释结构：

1. **发生什么**：自主接替、任务调整、计划变化等；
2. **为什么**：触发原因与可获得依据；
3. **影响什么**：受影响任务、设备、区域、路径和后续安排；
4. **还有什么未知**：信息不足、待确认或可能继续变化部分。

支持空间化前后差异、按需展开和必要的对比式解释。自主接替中具体化为“谁接替/为什么/波及什么/未知什么”。

## 4.3 M3 用户介入与执行结果追踪

支持用户通过地图选区、对象选择、结构化约束或自然语言补充表达调整意图。系统给出确认摘要及必要影响提示。

执行反馈至少区分：发送、接受、开始执行、部分落实、完成、拒绝、失败、未知；记录依据、时间和关联的调整要求。

支持连续修改、迟到反馈归属、失联恢复后的回交或维持，并避免把“前端操作完成”“消息发送成功”和“任务真正落实”混为一个成功状态。

## 4.4 设计准则与边界

- 只展示支持理解与判断的信息，不展示无必要推理链；
- 确定性前端行为优先由规则实现；
- 当前选区、任务等必要信息通过共享上下文提供；
- 只有必须由前端实际执行并返回结果的能力才使用受控前端工具；
- 不因采用 AG-UI、CopilotKit、Frontend Tool 等技术本身宣称创新；
- 机制位于空间交互层，不额外引入独立“前端 Agent”作为论文前提。

# 5. 原型系统设计与实现

## 5.1 原型范围与总体架构

实现最小可运行的长时空间任务监督原型，包括：监督终端、交互适配层、已有/模拟 Agent 与执行端。真实接口、实际数据和脚本模拟部分明确标注；不重建完整设备平台、接替算法或通用编排系统。

## 5.2 共享任务上下文与数据关联

实现任务、设备、区域、路径、事件、自主变化、用户调整、执行依据和反馈之间的稳定关联；处理重复事件、迟到反馈、连续修改及状态更新。

## 5.3 前端规则、共享状态与受控工具

- 规则：确定性状态展示、地图定位、时间线、变化差异等；
- 共享状态：当前选区、任务、空间对象、用户输入上下文；
- 受控工具：确需前端执行并把结果返回 Agent 的操作。

说明这些实现如何支撑 M1–M3，而不是把协议接入本身作为研究贡献。

## 5.4 核心界面实现

地图主视图 + 任务/过程视图 + 自主变化/影响面板 + 调整输入/确认 + 执行反馈与结果核查。多个场景复用同一套机制和界面结构，不为每个事件单独设计系统。

## 5.5 端到端业务案例

至少实现：

1. 自主接替（合适）；
2. 自主接替（需要人工介入）；
3. 新增区域/任务变化；
4. 部分落实/失败/未知或失联恢复中的一种异常反馈。

# 6. 实验与评估

## 6.1 评价框架与参与者

区分三类证据：

- 机制与需求是否合理；
- 系统状态与关联是否按规则正确运行；
- 用户是否因此获得更好的理解、介入和结果判断。

专家评审不能替代用户效果实验；实现成功不能替代用户理解。

## 6.2 公平基线与整体方案对照

**主要实验采用整体 A/B 对照，而不是把 M1、M2、M3 都拆成独立实验。**

两组保持相同：任务事实、Agent/后台能力、地图数据、任务难度、基本操作和必要成功/失败反馈。

- 基线：合理常规地图 + 任务列表 + 变化记录 + 基本调整/反馈；
- 本文方案：在此基础上增加 M1–M3 的情境化组织、空间关联、影响表达和执行落实追踪。

整体对照只能支持“整套方案”的效果结论。

## 6.3 业务与机制合理性评审

由业务专家/内部成员检查 R1–R5、权限、场景流程、合理介入条件、接替合适/不合适条件、可接受的模拟边界。记录反例并修订设计。

## 6.4 功能与状态规则验证

通过固定脚本验证：

- 状态与空间对象映射；
- 自主变化事件关联；
- 用户调整记录；
- 部分落实/失败/未知；
- 连续修改与迟到反馈；
- 当前状态不被旧反馈覆盖。

真值来自执行端回执、日志或预定义场景规则，不以界面自身状态自证。

## 6.5 EQ1：任务过程与自主变化理解评价

使用任务事实探针/SAGAT 式冻结提问等方式评价：

- 当前状态和对象匹配正确性；
- 关键变化遗漏；
- 自主变化原因理解；
- 空间/任务影响判断；
- 后续安排判断；
- 判断耗时。

自编题目明确称为任务事实题，不冒称标准量表。

## 6.6 EQ2：协同介入与结果确认评价

操纵“无需介入/需要介入”“调整完全落实/部分落实/失败/未知”等条件，评价：

- 对象、范围、约束表达错误；
- 漏介入率；
- 误介入/误否决率；
- 重复提交或错误确认；
- 落实状态判断正确性；
- 介入和判断耗时。

后台实际结果与用户判断分别记录。

## 6.7 可选特色机制针对性实验

资源允许时，只从 M1–M3 中选择**一个最有差异性的特色设计**进行单项对照，例如：

- 空间影响显式关联 vs 普通事件通知；或
- 调整要求—执行反馈显式关联 vs 分散显示。

固定其余功能，单独检验该设计的增量收益。没有该实验时，不宣称某个单项机制独立有效。

## 6.8 长时证据与结论边界

区分：

| 证据 | 可以支持的结论 |
| --- | --- |
| 加速回放数小时事件 | 状态逻辑与事件处理 |
| 系统实际数小时运行 | 对应条件下持续运行和多次介入处理能力 |
| 短时人员实验 | 特定协作条件下的理解、操作和判断效果 |
| 人员实际数小时监督 | 对应条件下的长期使用表现 |

无人员长时实验时，不声称降低疲劳、提高长期警觉性或解决 out-of-the-loop，只讨论长时任务结构带来的设计需求。

# 7. 讨论

## 7.1 机制有效条件

分析不同资源约束、操作员经验、事件频率、任务复杂度下 M1–M3 的收益和代价；明确哪些简单场景普通基线已经足够，避免把复杂交互机制视为始终更优。

## 7.2 核心场景与跨场景复用

区分：自主接替场景中的证据、第二场景中的复用证据，以及向其他无人系统/Agent 应用推广所需的进一步验证。

## 7.3 工程应用价值

讨论对本单位长时空间任务监督系统建设的价值，以及“规则、共享状态、受控工具”的工程边界。

## 7.4 研究有效性与限制

讨论参与者与真实目标用户差异、模拟程度、样本规模、场景覆盖、信息可获得性、实验时长及业务事实来源对结论的影响。

---

# 8. 结论与展望

按实际证据区分：

- 已建立的问题模型；
- 已设计的交互机制；
- 已实现的原型能力；
- 已获得的实验结果；
- 尚未验证的长期使用与跨应用推广问题。

展望包括真实平台接入、长期部署研究、更多自主变化类型与介入形式。

## 当前写作与实施原则

1. **论文主线不再围绕单一“失联接替”收缩。** 自主接替是核心验证场景，不是全文唯一研究对象。
2. **三项机制保持通用，场景中再具体化。** 例如自主接替中的“谁/依据/波及/未知”是 M2 的具体实例。
3. **长时必须转化为设计需求。** 重点是持续变化、历史累积、多次介入、反馈延迟与上下文衔接，不直接等同疲劳。
4. **实验以整体公平对照为主。** 单项机制实验作为可选深化，避免实验规模失控。
5. **创新从证据中收敛。** 单位未实现、用了 Agent/AG-UI/Frontend Tool 均不是充分创新依据。
6. **业务案例服务于论文机制。** 不因案例细节不断扩写系统背景。
