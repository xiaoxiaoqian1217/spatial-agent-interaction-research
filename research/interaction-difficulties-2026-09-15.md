# 任务已经开始了，用户再想改一点，困难在哪里？

研究日期：2026-09-15。

## 先说我的判断

**目前最值得继续研究的是：任务正在执行时，用户怎样只改自己想改的部分，并看清这次修改到底有没有落实。**

用一句大白话说，就是：

> 我只想把这里改一下，怎么让系统改对，不把其他要求弄乱，而且让我知道它真的改了？

这比“如何提升态势感知”更具体，也比“根据情境生成界面”更接近用户要办的事。
地图选区、文字输入、参数表单、修改预览和执行反馈，都可以围绕这件事研究。
至于它们应该由规则组织，还是需要交互 Agent，现有证据还不能决定。

这份报告依据相关研究、现有地图软件文档和本项目场景推演形成。
其中，别人的实验发现会注明来源；巡查例子都是分析用的假设，不是本项目已经发生的事故或用户观察。
这是一轮有针对性的探索，不是穷尽文献的系统综述，也没有做本项目的用户实验。

## 1. 为什么先选“执行中修改”，而不是其他问题？

我先把可能发生交互的几个时刻拆开比较。
下表是选题判断，不是对问题发生频率的统计。

| 时刻 | 用户可能遇到的困难 | 本轮判断 |
| --- | --- | --- |
| 刚下达任务 | 系统理解的区域和要求是否正确？ | 值得研究，但先看固定地图和编辑表单是否足够 |
| 正常执行 | 现在进行到哪里，需不需要我管？ | 要先知道用户实际需要做什么判断，不能从任务时间长直接推断负担大 |
| 设备自主接替 | 换了设备，会不会影响我的任务？ | 取决于接替是否影响用户目标；一切正常时可能无需用户参与 |
| 执行中新增区域或修改要求 | 哪些改、哪些保留、怎么确认改到了？ | 当前最具体，且能找到相邻场景的研究证据 |
| 发生异常 | 是重试、调整要求，还是等系统处理？ | 可能重要，但要先知道实际有哪些异常和可选处理办法 |
| 任务结束 | 结果满足了哪些要求，还有哪些没完成？ | 值得保留，但依赖后台能够提供什么结果证据 |

“执行中修改”同时涉及用户表达、系统理解、已有工作和后续反馈，可以沿着一个完整过程检查。
即使后台没有多个独立报告，这个问题也仍可能存在。
反过来，如果业务根本不允许执行中修改，或用户几乎不会这么做，它就不适合成为论文主线。

## 2. 用一个例子，把四个候选困难讲清楚

假设系统正在巡查 A 区域，学校周边是原有重点，一部分巡查已经完成。
用户临时提出：“把旁边 B 区域也加进去，原来的重点别改。”
下面逐步分析这句话可能在哪些地方不好办。

### 困难一：我说的“这里”，系统理解的是不是同一块地方？

“旁边那一块”可能是整个园区，也可能只是围墙外侧。
地图上点一个位置，也不能自然说明用户要改一个点、附近一圈，还是整片区域。
用户需要有办法指出范围，并检查系统采用了哪个范围。

这不是凭空猜想：早期地图交互实验比较过语音、笔输入及两者结合，发现结合输入能够减少一些空间表达错误。
但实验使用人模拟系统理解，并不是现代 LLM，也不能证明动态界面比固定地图更好。[Oviatt，CHI 1996](https://chi1996.acm.org/proceedings/papers/Oviatt/slo_txt1.html)

**在我们场景里要检查的是：用户是否被迫用很多话描述一块本来可以直接选出来的区域，以及系统是否把选区和这次要求关联起来。**

可能只需要很普通的设计：选中现有区域，或圈出范围，再显示本次采用的边界。
如果 B 本来就有唯一编号，选一下便能确认，问题可能已经解决，不应强迫用户重新画一遍。

### 困难二：我只改这一处，为什么还要重新说明其他要求？

用户说“增加 B”，并不等于要重新下达整个任务。
但如果交互只支持重新填写完整任务，用户可能需要再写一遍 A 的重点要求。
如果系统重做计划后只显示完整新计划，用户又可能需要从头检查哪些东西被改了。

这里真正费劲的地方是：**用户只想检查一个局部改动，却要重新表达或检查整个任务。**

相关线索来自 Cocoa 的共同规划研究：参与者在重新规划后，仍希望保留有用的旧步骤和输出。
这是科研文档任务中的发现，支持“修改时已有工作仍可能有价值”，没有直接证明巡查系统经常丢失原约束。[Cocoa，CHI 2026，第 5-8 节](https://kevinpjk.github.io/assets/pdf/cocoa_chi_2026.pdf)

因此，“原约束会被弄丢”目前只是需要检查的风险，不能写成已确认的业务痛点。
可以先探索一个清楚的修改预览：本次新增什么、原要求哪些继续有效、哪些受到影响、哪些还无法判断。
用户若只改错画的一条边，其他仍有效的输入应能继续使用。
如果这条边改变了面积，从而影响原有参数或计划，就需要标出需要重新检查的内容。

固定表单、差异展示和明确的保留规则都有可能做好这些事。
仅仅增加一个“原要求保持不变”勾选框，不足以保证后台实际保留了要求。

### 困难三：我正在修改，任务也在继续，刚才看到的情况还作数吗？

假设用户开始调整时，某设备尚未进入 B；等用户准备提交时，它已经完成了部分相关工作。
此时仍按刚才的情况预览，用户可能无法判断新要求会影响哪部分后续执行，是否会重复已有工作。

**这是本轮场景推演提出的问题，尚无本项目观察，也没有在本轮文献中找到直接对应的空间任务验证。**

它值得检查，是因为用户操作与后台执行可能同时推进。
但是，地图上任何状态变化都不值得弹窗打断用户。
需要区分“设备位置动了一点”和“这次修改的适用条件变了”。

可以先考虑保留用户输入，只在变化影响当前修改时更新预览，并说明受影响的部分。
如果业务规定修改期间暂停执行，或者所有修改只作用于尚未开始的工作，这个困难可能明显减轻。
版本检查和执行衔接需要后台支持；界面的研究对象是如何让用户理解变化并继续操作，不能把纯粹的并发程序错误都包装成交互问题。

### 困难四：系统说“好的”，到底是收到要求，还是已经照着做了？

用户提交“增加 B”以后，可能存在几个不同结果：要求已收到、计划已更新、设备开始执行、对应工作已完成。
如果只回复一句“已调整”，用户可能不知道自己还需不需要等待或检查。

Magentic-UI 的 12 人质性研究记录了修改计划未被采纳，以及用户希望更清楚地看见计划变化的情况。
这说明“能提出修改”与“修改得到落实”之间确实可能存在问题，但原因也可能是 Agent 执行失败，并非界面本身。[Magentic-UI，2025，第 7.4 节](https://arxiv.org/html/2507.22358v1)

我们可以据此检查：**这一次要求，能不能对应到具体的修改结果和后续状态。**

例如，对“增加 B”显示“计划已加入 B，尚未开始执行”，比一句“成功”更容易判断。
如果后台只返回了报告，就只能根据报告中确实有的信息反馈；不能推测设备已经执行。
“未收到执行反馈”也不等于“没有执行”，界面应保留这种区别。

## 3. 普通界面和规则流程能不能解决？

**很可能能解决相当一部分，而且必须把它们作为认真设计的比较方案。**

QGroundControl 的官方文档已经展示了地图任务编辑、未上传修改提示，以及规划、上传、执行之间的区分。
所以“地图能改任务”和“让用户知道修改处于哪个阶段”都不是新概念。
文档也没有证明它能解决本项目的全部问题，这里用它提醒我们不要低估已有界面。[QGroundControl Plan View](https://docs.qgroundcontrol.com/master/en/qgc-user-guide/plan_view/plan_view.html)

可以这样比较三种做法：

| 做法 | 在这个例子里怎么用 | 需要检查什么 |
| --- | --- | --- |
| 功能完整的固定界面 | 用户选区域、改参数、看变化、提交，再看反馈 | 用户能否顺利找到所需功能并完成操作？ |
| 按规则组织交互 | 没有边界才要求圈选；已有参数直接保留；有实际取舍才要求选择 | 这些规则能否覆盖实际任务，而不强迫用户做多余步骤？ |
| 交互 Agent 组织交互 | 结合不同要求，选择需要补充、检查或操作的内容 | 是否比规则更可靠或更省事，收益能否抵消延迟和理解偏差？ |

三者都可以有地图、表单和反馈，也都可以让界面随状态变化。
规则同样可以组合已有能力，不必每出现一种情况就写一个完整页面。
因此，“有一个交互需求层”或“组件可以组合”本身，不能证明交互 Agent 必不可少。

## 4. 动态交互究竟什么时候可能有价值？

这一方向已选为优先探索的候选机制，后续细化见[动态交互机制草案](contextual-interaction-mechanism.md)。
以下仍为待验证的设计判断，不是已取得的用户效果。

目前有一个值得检验的方向：**根据当前情境、用户已表达的要求和尚未明确的信息，组织此刻需要的交互，并随着信息补充和情况变化调整后续交互。**
初始范围可能不清楚，需要先帮助用户表达和确定，而不是从已经选好区域开始。
用户已经说明的不用再问、仍有效的不用重做，是这个方向中的衔接原则，不是整个研究问题。

例如同样是新增区域：

- B 已有明确边界，就直接显示供检查，不再要求圈选。
- B 范围不清楚，就提供选择或圈选能力。
- 用户已经给出必要参数，就保留这些参数。
- 新增 B 确实影响原目标时，才展示影响并让用户处理取舍。
- 修改期间条件变化时，保留仍有效的输入，指出需要重新检查的部分。

这里“动态”的是用户要走哪些步骤、补哪些内容、检查哪些变化，以及地图与表单如何配合。
整体页面布局完全可以保持稳定。
这些做法首先可以用规则实现，再观察哪里确实处理不好。

同时必须防止一个反效果：为了让用户更有控制感，反而让他不停确认。
Magentic-UI 的参与者就有人认为，刚提出修改又被要求批准新计划显得多余。[Magentic-UI，第 7.4 节](https://arxiv.org/html/2507.22358v1)
是否需要再次确认，要看是否产生了新的选择、影响或业务要求，不能规定每次都弹同一个确认框。

## 5. 如果用规则实现，还有论文价值吗？

有可能，但需要说清楚贡献比普通功能实现多在哪里。

一个可以继续检验的问题是：

> 在空间任务中，如何根据当前任务情境、用户已表达的要求及尚未明确的信息，组织此刻需要的交互，并随着信息补充和情况变化调整后续交互？

可研究的内容包括：怎样判断哪些信息还有效，哪些变化需要重新检查，以及怎样把一次修改和后续反馈关联起来。
这些都需要给出明确设计，并与已有任务编辑方式比较。
如果只是把常见地图工具和表单拼在一起，贡献更偏应用整合。
如果能提出适用于多种修改情况的方法，并证明它减少了重复操作或误判，才有更扎实的机制贡献依据。

本轮文献不能证明这个问题无人研究，也没有证明我们的设计优于已有方案。
尤其是计划编辑、保留已有工作和人参与执行都已有相关研究，后续需要在具体方法上找差异。
“用了规则”不会自动取消论文价值，“用了 LLM”也不会自动增加论文价值。

## 6. 接下来可以怎样把这个判断做实？

先做一个范围有限的任务修改原型，采用固定地图和规则流程即可。
目的不是证明规则失败，而是看上述困难是否真的影响操作，以及哪种设计能改善。

可以用下面这些情况走查和比较，既覆盖最初尚未表达清楚，也覆盖后续变化。
没有真实后台时可先用可重复的模拟状态，但必须注明模拟条件，不能把结果当现场证据。

| 情况 | 重点检查 |
| --- | --- |
| 用户只说“旁边那块”，范围尚不明确 | 能否通过澄清、定位、选择或圈选确定正确范围？ |
| 用户已经给齐区域和参数 | 是否还被迫重复输入或多次确认？ |
| 只缺区域边界，其他要求已明确 | 能否只补这一项，已有内容是否保留？ |
| 用户改了边界，其他内容仍有效 | 是否被迫重走整个流程？ |
| 信息完整但新旧要求存在冲突 | 能否理解具体取舍并修订要求，而不是反复补参？ |
| 编辑期间发生有关或无关的执行变化 | 是否只对真正影响本次修改的变化作出提示？ |
| 修改只完成了一部分，或反馈尚未到达 | 用户能否正确判断哪些已落实、哪些待确认？ |

比较方案应使用相同的后台能力和信息，都具备基本编辑、纠错和反馈功能。
不能拿一个功能残缺的聊天框来衬托新方案。
重点记录区域是否选对、原要求是否保留、是否重复输入、是否误以为修改已落实，以及操作时间。
满意度可以记录，但不能代替这些结果。

如果固定界面已经顺畅解决，就接受这个结果，继续找真正未解决的困难。
如果规则组织明显减少负担，先把这一机制做扎实。
只有出现规则难以处理的真实要求组合，再评估交互 Agent，且单独检查它增加的错误与等待。

后台最终至少能否提供“采用了什么要求”“修改后怎样安排”“实际反馈到了哪里”，是这条方向能研究多深的条件。
缺少哪一层信息，就明确缩小哪一层结论；不要求业务 Agent 额外承担界面设计任务。

## 7. 这轮探索得到什么，尚未得到什么？

得到了一个有相邻研究支持、能落到具体操作的优先候选：**执行中的局部修改及其落实确认**。
其中，“空间范围是否说清”和“修改是否被采纳”有直接的相关研究线索。
“巡查原约束如何保留”和“修改期间执行继续推进”仍需在本场景中验证。

尚未得到规则不够用的证据，也没有确定动态界面或交互 Agent 是创新点。
当前适合把这个方向推进到具体走查和原型比较，再根据结果决定是否收敛为论文主线。

详细研究条件与证据边界见[一手研究笔记](../literature/notes/interaction-evidence-2026-09-15.md)。
项目原有的[任务走查草稿](interaction-walkthrough.md)可以继续使用，本文作为其文献依据和候选困难分析。
