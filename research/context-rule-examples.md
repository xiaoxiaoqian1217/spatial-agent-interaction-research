# 情境—需求—策略规则示例

> 2026-09-16 工作设计。以下为可供原型实现和专家评审的假设，不是业务规程、已实现功能或实验结论。后台提供约束判断与执行事实，交互模块不替代业务决策。

## 1. 表示与实现的区别

Context / Situation 描述任务事实及其关系，Need 描述任务要求界面支持的问题，Strategy 决定信息、地图、操作及发起方式。规则可以跨越这些环节，状态机既可描述任务演进，也可管理确认与核查；不能把技术固定分配给某个层次。

第一阶段不使用 LLM，也不需要新增前端 Agent。Need 不是四个标签的空壳，每项至少带上对象、待解决问题、证据和适用条件。策略仍需访问完整情境与权限。

## 2. 规则记录格式

| 字段 | 要求 |
| --- | --- |
| ruleId / version | 规则标识、版本与修改理由 |
| scope | 适用任务、对象和业务条件 |
| conditions | 当前状态、变化、约束检查、空间影响、决策状态 |
| evidence | 来源、时间、有效性；明确已知、最后报告与未知 |
| need | 类型、对象、需要支持的问题；B1不设置此项 |
| strategy | 信息、地图表达、可用操作、交互方式与发起方 |
| authority | 业务权限依据、是否必须确认；与交互方式分开 |
| priority / conflict | 多规则合并、冲突及证据不足处理 |
| exit / recheck | 需求何时已解决、何时重新判断 |
| counterexample | 不应触发的相近情境与预期回退 |

每次输出记录 contextVersion、ruleId/version、触发证据、策略和时间。重复事件应合并；用户操作和执行反馈继续更新情境，不能让过时规则一直占据界面。

## 3. C1：异常后的自主接替

共同事实：A失联，后台给出B接替建议。A只显示最后报告位置及时间，不能把失联等同于损坏，也不能把建议当成已经执行。

| 情境分支 | 任务导出的 Need | 信息与地图 | 操作及交互方式 |
| --- | --- | --- | --- |
| 后台确认符合既有约束，且允许自主接替 | Understand：谁失联、谁接替；后续Verify | 显示A最后报告、B当前任务和接替范围 | Inform；可查看或主动调整，不重复要求确认 |
| 接替将造成尚未解决的原区域覆盖缺口 | Understand + Assess：缺口在哪里、影响什么；必要时Control | 同时显示原覆盖区、拟接替区、缺口及候选方案 | Suggest或Request；具体是否可自动执行取决于权限 |
| 关键变更必须人工确认 | Assess + Control：取舍与确认对象 | 原/新任务及受影响区域对比 | Confirm；后台按权限等待批准，界面不能自行放行 |
| 缺少约束检查结果或位置证据过期 | Understand + Assess：哪些仍未知 | 标记未知、最后报告时间和待补充证据 | 提供核查入口；不推断方案可行，不静默执行新变更 |
| 执行端已接受，尚无开始执行证据 | Verify：接替是否真正开始 | 显示“已接受/待执行证据”，保留原新对象关联 | 按需查看；不能显示“已落实” |
| 新证据表明只完成部分接替 | Verify + Assess，必要时Control | 标明已完成与未覆盖部分、关联原要求 | 查看原因或提交修订；不把部分落实合并为成功 |

示例规则 `R-C1-GAP`：有覆盖缺口且尚未解决时，输出针对缺口区域的 Assess；仅当存在需用户处理的取舍或权限条件时增加 Control。策略显示缺口和方案比较。若用户正在绘制选区，先保留其视野并显示定位入口；经用户点击才聚焦。业务紧急告警按共用规则呈现，不代替确认或控制动作。

退出条件：缺口已被独立执行证据消除，或旧建议已撤回/替换。若当前只是“建议已提交”，需求不能退出。反例：相同失联事件但备用平台接替不造成缺口，不应无条件弹出方案选择。

## 4. C2：新增区域后的主动调整

| 情境分支 | Need与对象 | 交互组织 |
| --- | --- | --- |
| 用户选区并要求加入巡检，约束尚未明确 | Understand + Control：新增区域与保留要求 | 共享选区几何，核对区域与约束，提供提交/取消 |
| 后台方案显示新增区域与原安排相容 | Assess：变化范围；Control按权限启用 | 对比原/新范围、任务影响和方案依据 |
| 新要求与“保持原区域覆盖”冲突 | Assess + Control：冲突及取舍 | 同时突出新增与受影响区域，要求澄清，不悄悄删除原约束 |
| 连续修改后旧方案回执迟到 | Verify：回执归属 | 关联旧调整标识，不覆盖新要求，不提示新方案已生效 |
| 新方案完整、部分、失败或未知 | Verify：哪些要求已落实 | 用执行证据分别核查新增区域与保留约束，提供后续处理入口 |

## 5. 跨案例复用与反证

候选可复用规则：当后台报告方案与保留约束冲突时，形成针对受影响对象的 Assess；需要用户取舍时增加 Control。这可以同时用于接替导致缺口和新增区域导致原区域覆盖下降。

这只是复用假设。B1也可以复用谓词、策略组件与状态机，不能刻意禁止它复用。比较时向两者加入相同未见情境或约束，记录策略是否适当、修改了几处、引入了多少回归错误以及依据是否完整。若P只是增加Need标签而未改善这些表现，应保留该负面结果。

## 6. 待确认项

- 接替、重新规划和人工批准的真实业务权限。
- 位置与反馈的有效时间、紧急告警阈值及去重窗口。
- 可接受的多种策略与必须保留的信息。
- 正常无介入、证据不足、同事件不同后果的测试分支。

正式实验前由业务依据和评审确定这些参数，不能为了让方案表现更好而在测试后调整。详见[对照协议](../experiments/protocols/context-driven-comparison.md)。
