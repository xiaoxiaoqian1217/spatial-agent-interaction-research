# 动态交互机制草案：已有的沿用，需要的补上，受影响的再检查

更新日期：2026-09-15。
状态：已选为优先探索的候选机制，尚未进行原型实验，也未证明新颖性和效果。
本草案细化[交互困难报告第 4 节](interaction-difficulties-2026-09-15.md)，并用[装备失联场景](lost-link-interaction-difficulties-2026-09-15.md)检查适用边界。

## 1. 我们具体研究什么？

> 当任务、用户输入或后台信息变化时，怎样保留仍有效的交互成果，只让用户补充缺少的内容、检查受影响的部分，并从当前位置继续完成任务？

“交互成果”就是用户已经选好的区域、填过的参数、表达过的要求和作过的决定。
“动态”具体体现在下一步需要做什么、哪些操作可以跳过、哪里需要重新检查，以及地图与表单怎样配合。
页面布局可以保持稳定。

研究目标不是让所有流程变短，而是减少不必要的操作，同时避免漏掉真正需要处理的问题。
有时新情况带来新的取舍，合理的交互反而需要增加一步。

## 2. 每次变化后，先判断四件事

| 要判断什么 | 具体例子 | 交互如何变化 |
| --- | --- | --- |
| 这次要处理什么，关联哪个对象？ | 用户是在增加 B，还是修改原有 A？ | 让地图、参数和说明关联同一对象，不能误用上次选区 |
| 已有什么，而且现在仍能使用？ | B 的边界已经确定，原重点要求仍有效 | 沿用并提供查看、修改入口，不要求重新输入 |
| 缺少或发生变化的是什么？ | 只缺参数，或边界变化使旧预览不再适用 | 只补缺项，或更新受影响的预览 |
| 下一步由谁完成？ | 用户补边界，后台重算影响，或系统正在自主处理 | 分别提供操作、等待状态或结果，不把所有事情都变成人工确认 |

判断依据应来自具体输入、任务记录、业务规则和后台反馈。
不需要先猜测用户心里是不是焦虑、困惑或需要更多控制。
系统没有依据时，就不能假装知道下一步应该做什么。

## 3. 最重要的区别：没填、待核查和已经失效，不是一回事

| 情况 | 应该怎样处理 | 不应该怎样处理 |
| --- | --- | --- |
| 必要参数还没填，而且用户可以提供 | 请用户补充该参数 | 清空其他内容，要求重填整个任务 |
| 用户选过的边界仍适用 | 继续沿用，允许主动修改 | 因为切换了步骤就要求再画一次 |
| 边界变了，旧参数是否适用尚待检查 | 保留参数值，标明待检查，由相应规则或后台校验 | 直接把原参数改掉，或把它视为已经验证有效 |
| 旧预览基于已经变化的边界 | 更新预览，说明变化，按业务要求重新检查 | 继续把旧预览当作本次提交的依据 |
| 装备失联后的进展未知，用户也不知道 | 说明缺少执行依据及当前处理状态 | 弹出必填表单，让用户猜一个完成比例 |

**保留用户输入，不等于继续沿用旧的验证结论。**
例如，原巡查频率可以继续作为用户要求保留，但修改区域后，是否还能满足这个频率需要重新核查。
如果不能满足，应说明实际取舍，不能悄悄降低用户要求。

## 4. 新增区域：交互怎样随情况改变？

假设用户希望增加 B，同时保持 A 的原有重点要求。
以下过程是设计推演，字段和业务关系需在实际场景中核查。

| 当前情况或变化 | 用户接下来看到什么、做什么 | 保留什么 |
| --- | --- | --- |
| 已选 B，只缺一个必要参数 | 地图显示采用的范围，表单只突出缺少的参数 | B 的选区、A 的原要求和其他已填内容 |
| 范围和参数已经完整 | 查看本次变化与实际需要核查的影响，按权限提交 | 已有输入，不再走选区和补参步骤 |
| 用户拖动 B 的一条边 | 地图保留编辑状态，依赖该边界的影响预览更新 | 参数值、原要求和无关的输入 |
| 后台发现原要求无法同时满足 | 展示具体冲突及可用处理方式，让用户修改相关要求 | 未受影响的要求和选区 |
| 一条无关的设备位置更新到达 | 正常更新状态，不切走当前表单 | 当前焦点、草稿和已完成的步骤 |
| 用户已提交，又发起第二次修改 | 第一笔修改保留落实状态，第二笔作为新的草稿处理 | 两次修改各自的输入和反馈对应关系 |

这里最需要验证的是第三行：用户改了一个部分，系统能否只重新处理依赖它的内容。
这是比“缺什么显示什么”更完整的交互过程。

例如，可以在原型中明确设定以下关系：

> B 的边界改变，会影响面积和后续安排预览；不会自动改变用户保留 A 重点要求的意图。

这种关系需要业务依据，不能只凭字段名称相似就认定相关。
用户之前确认的是旧范围下的安排，不能把那次确认直接套到已经改变的安排上。
是否需要再次确认，仍按本次变化和业务授权规则判断。

## 5. 装备失联：同一机制怎样用？

场景从“装备失联，处理策略尚未确定”开始。
接替只是可能的后续分支，不作为固定第二步。

| 当前情况或变化 | 需要的交互支持 | 可以省去什么 |
| --- | --- | --- |
| 刚收到失联事件 | 最后报告、未知部分、受影响任务及实际处理状态 | 尚无依据的策略选择和接替表单 |
| 后台正在按既有规则处理，暂无人工事项 | 让用户了解处理进展，保留主动查看入口 | 不必要的审批 |
| 后台明确需要一项用户能提供的信息 | 说明用途，提供对应补充入口 | 重述整个任务或填写用户也不知道的数据 |
| 后台提出需要用户处理的取舍 | 呈现依据、影响和可用操作 | 无关的设备详情与操作步骤 |
| 联系恢复，新反馈消除了待决定事项 | 说明变化，撤销或更新不再适用的操作 | 继续要求用户回答已经过时的问题 |
| 后续确实选定接替 | 展示相关任务变化，并跟踪实际执行反馈 | 让用户重新从全部装备中挑选一次 |

用户正在填写的信息即使暂时不再需要，也不应无提示地消失。
可以保留草稿或查看入口，同时明确它已不适用于当前处理。
失效决定不能继续提交为有效决定；输入也不能自动转用于另一个对象或新的策略。

这个场景检验的是：随着证据和系统处理进展变化，交互能否及时调整，而不强迫用户走一条预先定死的完整流程。

## 6. 第一个原型怎样分工？

先采用明确规则实现上述判断，暂不增加交互 Agent。
这是为了让每次显示、跳过或重新检查都有可追溯依据，便于分辨交互设计问题与模型误解。

| 部分 | 负责什么 |
| --- | --- |
| 现有业务系统或模拟后台 | 提供任务事实、采用的要求、影响检查、处理安排及实际反馈 |
| 交互规则模块 | 记录草稿及其适用对象，依据已定义关系决定沿用、补充、更新或停止某个交互步骤 |
| 前端 | 调用地图能力、显示表单和说明，保留输入与焦点，把用户操作传回去 |

交互规则模块可以先是前端的一段独立逻辑，不必部署成新的服务，因此不必新增网络通信层。
它也不要求业务 Agent 额外输出布局或界面计划。
真实后台没有相应事实或影响检查能力时，原型只能使用注明为模拟的输入，不能让前端自行宣称业务判断成立。

地图圈选和表单都可以向同一份修改草稿写入内容。
渲染页面本身不应重复提交修改，也不应在收到每条后台事件时重置正在编辑的地图。
提交时由后台再次检查当前条件，界面预览不能代替最终有效性检查。

## 7. 和普通条件显示的区别，需要诚实回答

只根据“任务报错了”显示异常卡片，主要改变的是显示内容。
本草案进一步检查：用户已经完成的内容是否仍适用、哪些结果依赖变化的信息、谁需要接着行动，以及怎样延续当前操作。

但普通的状态机、条件表单和依赖规则也能实现这些行为。
不能因为逻辑拆成了几层，就宣称有新算法或新的智能能力。
候选贡献在于是否提出了适合这些空间任务的组织方法，以及它是否确实改善了操作和判断。

后续若要引入交互 Agent，需要先指出具体哪类真实情况使既有规则难以处理，再比较它能解决什么、增加什么错误和等待。
两个预先写好的演示案例不能证明泛化能力。

## 8. 怎样比较，才能知道它有没有用？

先选一个主要问题：**局部变化之后，用户能否少做无关操作，同时正确检查真正受影响的内容？**

常规比较方案也要具备输入保存、已知值预填、字段校验、修改预览、基本地图联动和执行反馈。
不能故意让它丢输入，或要求每次从头填写，再把改进归功于动态交互。

重点比较用户自行在完整编辑区检查，和系统按已定义的影响关系引导局部补充与检查这两种组织方式。
两者提供相同信息和修改能力，也都允许主动查看完整内容。
如果两种方式实际行为已相同，就需要重新审查差异，不能靠改名字凑出实验条件。

| 验证情况 | 预期检查的行为，不是已获得结果 |
| --- | --- |
| 输入已经齐全 | 不重复补参，仍能检查实际影响 |
| 只有一个必要输入缺失 | 只补这一项，其他输入保持可用 |
| 改动导致部分预览过时 | 旧预览不再作为有效依据，相关内容重新检查 |
| 到达无关状态更新 | 编辑不中断，不额外要求确认 |
| 失联恢复使待决定事项不再适用 | 过时事项不能继续作为有效操作，用户知道发生了什么 |
| 后台信息仍不足 | 保持未知，既不要求用户猜测，也不宣称处理完成 |

功能检查先验证输入保留、依赖关系与状态衔接是否按设计工作。
随后用户比较记录重复输入、重新查找、判断错误和操作时间，并检查是否因过度省略而漏看重要影响。
步骤更少不能单独算成功；若误判增加，就需要调整设计。

## 9. 当前决定与下一步

已决定优先探索“沿用已有输入、补充必要内容、按影响重新检查、延续当前操作”的交互组织机制。
尚未决定它是论文最终创新，也未选定交互 Agent 架构。

下一步先围绕新增区域做可操作的小原型，因为它能直接演示输入保留和局部变化。
失联场景用于检查同一方法能否处理后台事件、责任变化和交互取消，而不把失联固定导向接替。
原型初期使用明确的模拟状态和规则，取得真实业务信息后再核查和替换。
