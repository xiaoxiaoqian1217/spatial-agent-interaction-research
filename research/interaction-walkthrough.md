# 执行中新增区域的交互困难探索

当前先探索用户在具体任务中遇到什么困难，再决定需要研究的交互机制。
规则工作流、动态能力组合与交互 Agent 均为待选技术路径。
本文档是任务走查草稿，尚无观察结果，不作为已经确认的需求或研究贡献。

## 走查情境

一项区域巡查任务正在执行，用户希望增加 B 区域，同时保留已完成的工作及 A 区域的原有重点要求。
区域名称仅用于推演，实际任务对象、允许调整的内容及后台反馈能力需与业务人员核对。
请参与者按自己习惯的方式完成这项调整，先不指定其使用聊天、表单或特定地图工具。

## 走查步骤与观察点

下列步骤用于帮助记录，可以按实际流程增删或调整顺序。
提问应先让参与者解释自己的判断与操作，再追问原因，避免预先暗示某项设计存在问题。

| 环节 | 中性提问 | 记录内容 |
| --- | --- | --- |
| 了解当前任务 | 修改之前，你需要先了解什么？在哪里查看？ | 所需信息、查找入口、实际可得性，以及无需查看的信息 |
| 表达新增范围 | 你会怎样说明要增加的区域？ | 表达方式、对象和边界如何确定、是否需要往返查找 |
| 表达保留要求 | 这次调整中，哪些内容改变，哪些继续有效？ | 用户如何表达、系统如何呈现、是否需要重复输入 |
| 检查系统理解 | 你怎样判断系统理解了你的意思？ | 判断依据、是否存在无法确认的部分、是否需要修正 |
| 修改已输入内容 | 如果此时想改一下范围，你会怎么做？ | 已有选区及参数如何处理、哪些保留合理、哪些必须重新确认 |
| 决定是否提交 | 还需要知道什么，才能决定是否提交？ | 实际必要的信息、取舍和操作权限，以及已有方式是否足够 |
| 核查后续结果 | 提交后，你怎样知道调整已经生效？ | 接收、计划变化与执行反馈如何判断，何时继续观察或再次操作 |

## 记录方式

优先使用现有系统；尚未实现的部分可用简单草图走查，并注明该部分属于模拟。
尽可能邀请实际操作员参与；仅由研究者推演时，将发现标记为假设。
同时记录顺利完成的步骤，避免只搜集支持新增机制的现象。

每个候选困难按以下格式记录：

- 发生情境和用户目标：
- 使用的系统或草图及已知限制：
- 可观察行为或参与者原话：
- 后果，例如延误、重复操作、错误或无法作出判断：
- 用户现有的处理办法及其是否足够：
- 可能原因，区分信息缺失、业务规则不清和交互支持不足：
- 证据状态，注明实际观察、参与者陈述或研究者推演：
- 其他可能解释及下一步核查：

单次出现可以发现问题，但不能据此宣称问题普遍或反复发生。
后台不提供必要信息时，先记录数据条件，不直接归因于界面设计。

## 如何选择后续研究问题

走查后，优先考虑对用户判断或操作有明确影响、有具体证据、且现有处理方式仍存在不足的问题。
将候选问题写成“在什么情境下，用户为了完成什么，因为什么障碍而出现什么后果”。
再比较现有界面的小幅改进、固定流程、组合规则和交互 Agent 等方案，说明各自解决了什么及引入了什么成本。
若尚未发现明确困难，继续补充实际任务与观察，不据此提前确定动态交互机制为论文主线。
