**正式论文正文与研究过程材料分开管理**：论文正文放在 `paper/`，文献、研究框架、实验记录等使用 Markdown 等便于版本管理的格式。

## 当前研究问题

本文关注目标委托执行中的用户理解、调整和结果核查。
后台存在多个智能体不等于用户需要处理多个独立输出，实际可用信息与交互困难尚待核查。

> 在长时空间任务中，用户理解情况、表达调整和核查结果时遇到哪些具体困难，需要怎样的交互支持？

传统界面也围绕用户需求设计，但常由用户将目标转换为具体操作。
本文比较交互职责、信息组织和参与方式的变化，不预设Agent界面普遍优于传统界面。

G1支持过程理解，G2支持有效参与与结果确认。
长时空间任务是应用与验证背景，空间交互是理解、参与与核查的主要手段：操作员远程监督空中、地面、四足无人平台班组，必要时调整目标与范围。
设备控制、多智能体内部编排和事件协议为支撑能力；不将多源输出聚合与归因作为研究目标。

### `paper/` 与 `literature/papers/` 的区别

- `paper/`：**我们自己正在撰写的论文**。
- `literature/papers/`：**别人已经发表、用于阅读和引用的论文**。

因此正式论文主文件只保留一处：`paper/thesis.docx`。

## 论文大纲

2026-09-14 更新的[八节论文大纲](research/outline.md)，按“问题与目标-理论与任务分析-协同机制-原型-验证与讨论”组织。

场景分为系统应用、典型协作情境与具体业务案例。
围绕目标委托、过程监督、Agent征询、用户主动调整、异常恢复、结果确认分析需求；道路封闭仅是验证案例。

暂以任务信息呈现、协同介入、执行衔接与反馈作为分析框架。
原五维改为跨机制设计准则，地图贯穿三项机制。

优先探索空间交互：围绕任务、设备、区域与路径，研究用户如何理解变化、表达调整和核查结果。
空间对象与任务过程的联动、空间操作与语言表达的衔接是候选设计入口，尚未选定具体创新。
交互机制和支撑交互的技术实现均可形成贡献，但需说明相对已有方案的差异及证据；不能由“单位尚未实现”或“感觉研究较少”推断新颖性。
调整意图与落实关联保留为备选特色。

## 研究原则

- 先明确研究问题，再选择实现技术。
- 区分“系统工程能力”和“论文研究贡献”。
- 每项交互机制都应对应明确的用户问题。
- 论文结论尽量由文献、实验、专家评审或其他可复核证据支撑。
