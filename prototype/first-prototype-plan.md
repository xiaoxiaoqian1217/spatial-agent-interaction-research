# 第一版原型：新增区域的情境交互与局部修改

日期：2026-09-15。
状态：演示重点、规则实现与正常界面对照已由用户明确；实现位置为代码检查后的建议，尚未实施。
机制依据见[动态交互机制草案](../research/contextual-interaction-mechanism.md)。
本次修订依据当前机制草案，将原先以局部修改为主的覆盖范围扩展到首次表达、信息补充、冲突处理及修改衔接。
2026-09-15 第二次修订：恢复"范围已明确但要求未说明"分支，与机制草案及研究问题的五类情况对齐；明确失联脚本只用于功能验证与专家评审，不进入用户对照实验；增加各分支预期差异假设表；将多边形边界编辑标注为首个技术验证点。

## 1. 要回答的问题

面对不同明确程度的新增区域要求，系统能否组织此刻需要的交互，并随信息补充、业务冲突和局部修改调整后续交互？
局部修改仍是重点演示分支，检查系统能否保留仍有效的输入，只重新检查受影响的内容，并让用户正确理解变化。
装备失联作为补充场景，检查后台事实变化后，正在进行的交互能否更新或取消。
原型效果尚待验证，不预设它优于设计完善的正常界面。

## 2. 主演示脚本

初始任务正在巡查 A 区域，用户希望新增一块范围，并要求保留 A 的原有重点要求与已完成工作。
B 是新增范围的代号，不代表用户已经选好位置或边界。
所有任务、设备、影响计算与执行反馈均使用明确标注的模拟数据。

### 2.1 五类可独立进入的情况

| 情况 | 示例 | 需要演示的交互 |
| --- | --- | --- |
| 范围不明确 | "把旁边那块也加进去"存在多个候选范围 | 提供候选定位与澄清；已有范围可选择，没有现成边界且业务允许时可圈选，不替用户猜定范围 |
| 范围已明确但要求未说明 | B 的范围已选定，但 B 是否沿用 A 的重点要求未说明 | 只澄清沿用关系这一项，提供"沿用 A 的要求"与"单独设置"入口，保留已明确的范围与其他内容，不要求重新表达范围 |
| 范围与要求均已明确 | 用户已明确要新增哪块范围及相关要求 | 直接检查影响，按权限提交，允许主动修改 |
| 存在冲突 | 范围与要求已明确，但模拟后台判定新增要求与原任务要求无法同时满足 | 展示冲突依据和可用取舍，支持修订，不能要求用户重复说明范围 |
| 过程中修改 | 用户已查看预览，又修改 B 的一条边 | 保留输入，重新检查依赖边界的内容，并接着完成任务 |

"只缺参数"分支以沿用关系歧义为例：用户说"把 B 也加进去"时，B 是否沿用 A 的巡查频次、时段等要求本身需要澄清，这是范围歧义之外独立的一类歧义。
范围歧义对应候选定位与圈选，要求歧义对应继承关系澄清，二者需要不同的澄清交互；这一区分是候选设计发现，待实验检验。
沿用 A 的要求之后可能触发冲突分支，两类情况可以自然衔接。
"过程中修改"指提交前，用户看过新增安排后发现 B 圈多了，将其缩小，系统更新安排并保留 A 的原要求。
这些是可独立进入、随新信息转换的情况，不是强制依次完成的五步向导。
首版使用预设表达及结构化模拟状态驱动规则，不声称实现任意自然语言理解。
两组都使用相同的模拟理解结果与候选范围，避免把理解能力差异混入交互比较。
入口情境由版本化场景脚本注入，代表系统"已经理解到某程度"的状态，不代表理解能力本身被验证。

### 2.2 重点演示：局部修改后继续

1. 用户从上述适用入口明确 B 和必要要求，查看新增区域对后续安排的影响预览。
2. 用户拖动 B 的一条边，继续在当前地图中编辑。
3. 系统保留 A 的要求及无关草稿，将依赖旧边界的面积、安排预览和相关校验标记为过时。
4. 模拟后台按新边界重新检查；如果原要求无法满足，保留用户要求并呈现冲突，不能自动降低要求。
5. 用户只修改或核查受影响部分，查看最新变化后提交。
6. 界面分别显示模拟后台已接受修改、安排已更新、收到执行反馈，不能把提交成功等同于执行完成。

主脚本中插入一次无关设备位置更新，检查地图编辑、输入焦点及草稿是否保持。
同时检查从范围澄清进入影响检查、从冲突进入修订后检查的衔接。
范围与要求均已明确时可以直接进入检查，不能为演示强制制造歧义或冲突。

## 3. 失联补充脚本

本脚本只用于功能与机制验证及专家评审，不进入本轮用户对照实验，避免等价任务设计量翻倍。
它作为同一机制处理后台事件驱动的更新与取消的泛化证据。
先出现装备失联与最后报告，明确哪些进展未知、后台正在做什么。
后台提出有依据的待决定事项后，用户开始填写处理意见。
随后分别回放两种变化：新反馈改变了可选处理方式，需要更新事项；联系恢复且新反馈明确消除了该事项，需要取消事项。
联系恢复本身不自动表示任务影响已经消失。

更新或取消时说明原因，保留原草稿供查看，并阻止过时决定继续提交。
旧草稿不能自动用于另一个设备、事项或策略。
另设仅恢复通信、任务进度仍未知的分支，检查界面是否继续如实呈现未知。

## 4. 公平比较

| 条件 | 正常界面 | 按当前情境组织交互的界面 |
| --- | --- | --- |
| 输入与地图 | 保存输入、预填已知值、字段校验、地图联动 | 相同 |
| 业务依据 | 相同任务数据、规则、影响预览和反馈 | 相同 |
| 初始要求 | 用户在常规地图和编辑区使用澄清、候选选择和圈选工具 | 根据范围是否明确组织当前入口，已完成的部分可沿用 |
| 范围明确与冲突 | 提供影响检查、冲突说明及修订工具，用户自行选择所需操作 | 范围明确时进入检查，存在冲突时组织取舍与修订 |
| 局部修改后 | 在完整编辑区呈现更新结果、冲突和必要校验，用户自行检查 | 额外指出沿用项与受影响项，并组织当前需要补充或核查的内容 |
| 过时事项 | 显示状态变化并阻止无效提交 | 相同，进一步将当前操作引导更新到仍适用的事项 |
| 完整信息 | 可以查看完整输入与影响 | 同样可以，不能因局部引导而隐藏重要影响 |

两组共用草稿数据、业务校验和提交有效性检查，并提供相同的澄清、范围选择、范围修改与冲突处理能力，仅改变交互组织方式。
不能把输入丢失或允许过时提交设计成对照组缺陷。
若正常界面已有相同的局部引导行为，应重新界定实验差异，不能仅靠名称划分条件。

## 5. 实现位置建议

建议将可运行原型放在 `D:/xxq/work/generative-ui-platform/apps/web-workbench` 的独立实验入口中。
研究依据、实验方案与结果仍放在本研究仓库，不复制维护第二套前端实现。

检查现有 README、AGENTS.md 与相关源码后，可确认 Workbench 已有 Vue、MapLibre、地图选取与路线预览、路线征询组件，以及测试工具。
现有征询代码包含响应资格检查和失效接口，但这些不等于已经实现后台事件驱动的事项更新与草稿保存。
现有地图修改入口主要是路线修订位置标注；本次 B 区域的边界编辑和相关依赖检查仍需实现。
Workbench 当前没有多边形绘制与编辑库（无 terra-draw / mapbox-gl-draw），边界拖拽是关键路径上最大的未验证实现风险。
首个技术验证点：最小可行边界编辑只包含顶点与边中点拖拽手柄，以及边界版本号递增；不做吸附与撤销栈，不抽象通用依赖引擎。
依赖关系硬编码为小图：边界 → 面积 → 安排预览 → 校验项，与下文不扩展为通用 Runtime 的约束一致。

建议新增局部目录 `src/features/interaction-study/`，容纳实验页面、两种交互组织方式、草稿逻辑、确定性规则和模拟事件。
目录名与入口路径为建议，不代表代码已经存在。
复用现有地图基础和合适的 UI 组件；实验草稿按实验运行隔离，避免沿用现有路线征询的全局单例承载两组状态。

第一版规则直接在前端独立模块实现，模拟后台单独提供事实与提交检查。
模拟输入显式区分范围是否明确、要求是否明确、是否存在已确认冲突，以及下一步由用户还是后台处理。
规则据此组织澄清、选择或圈选、影响检查、取舍和反馈，并在每次新信息到达后重新判断适用交互。
各类情况可以共存，例如范围修改后出现业务冲突；先处理会影响后续判断的范围问题，再依据新信息确定剩余事项，不预先排成不可变的完整流程。
草稿、影响预览与待决定事项记录适用对象及相关版本，收到旧计算结果时不能覆盖新边界下的结果。
提交时再次核对相关事实版本及事项状态，覆盖用户点击提交与后台更新同时发生的情况。
这些是本场景的局部实现，不扩展为通用 Runtime、Surface Lifecycle 或新的协议平台。

首版不依赖 LLM 或动态生成组件，以固定组件和明确规则验证交互组织。
未来接真实后台时再复用仓库已有的原生接入边界，并显式处理能力缺口。

## 6. 验收与记录

先按用户实际操作跑端到端流程，并检查地图、表单、焦点、提示和失效按钮的视觉状态。
功能检查至少覆盖以下事项：

- 五类情况分别进入适用交互，范围已明确时不重复要求选区，范围不明确时不擅自选定对象，要求未说明时只澄清沿用关系。
- 澄清、补充和冲突修订后能自然进入下一项实际需要的交互，输入与对象关联保持正确。
- 已确认的冲突不被当作范围尚未说明，用户可以理解并处理取舍。
- 修改 B 边界后，A 的要求和无关草稿保持。
- 旧影响预览不能作为当前提交依据，延迟返回的旧计算不能覆盖新结果。
- 无关后台更新不中断编辑。
- 规则检查失败时保留用户输入，并指出具体冲突。
- 待决定事项更新或取消后，草稿可追溯，旧按钮与提交入口均不能提交过时决定。
- 两组使用相同事件序列、数据、校验规则和模拟延迟。

用户比较前，先按下表冻结各分支预期观察到的差异；这是待检验假设，不是结果。
假设在实验开始前冻结，未成立的分支如实报告，不事后重构假设。
若某分支两组无差异，收缩对应结论，例如"固定界面在入口组织上已足够，机制价值集中于变化处理"。

| 分支 | 预期可观察差异（假设） | 对应评价 |
| --- | --- | --- |
| 范围不明确 | 两组都能形成正确范围；实验组重复表达更少、进入影响检查更快 | EQ2 表达正确性与耗时 |
| 范围已明确但要求未说明 | 实验组只澄清沿用关系；基线组更可能出现重填或误改无关项 | EQ2 重复输入与误改次数 |
| 范围与要求均已明确 | 两组均能完成检查与提交；预期差异最小，作为操纵检查 | 任务完成情况 |
| 存在冲突 | 实验组更快理解取舍对象，更少把冲突误判为缺少参数 | EQ1 取舍理解与判断耗时 |
| 过程中修改 | 实验组更准确区分沿用项与受影响项，更少遗漏受影响校验，更少重复检查无关内容 | EQ1/EQ2 遗漏影响与重新查找 |
| 无关后台更新 | 两组编辑均不中断；预期无差异，作为操纵检查 | 焦点与草稿保持 |

用户比较记录范围表达正确性、取舍理解、任务完成情况、完成时间、重复输入、重新查找、遗漏影响和判断错误，以及对当前适用事项的理解。
按五类情况分别记录结果，避免总体用时掩盖某个分支的误判或操作困难。
正式比较时平衡条件顺序，并使用等价任务，减少学习效应。
步骤减少不能单独作为成功依据；若重要影响被遗漏，应调整引导方式。

记录实现版本、实验条件、模拟事件及用户操作，以便复现。
这些预设情况只能验证对应场景，不能证明规则泛化能力、自然语言理解能力或论文新颖性。
