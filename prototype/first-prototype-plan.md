# 第一版原型：新增区域的局部修改

日期：2026-09-15。
状态：演示重点、规则实现与正常界面对照已由用户明确；实现位置为代码检查后的建议，尚未实施。
机制依据见[动态交互机制草案](../research/contextual-interaction-mechanism.md)。

## 1. 要回答的问题

用户修改新增区域的一部分后，系统能否保留仍有效的输入，只重新检查受影响的内容，并让用户正确理解变化？
装备失联作为补充场景，检查后台事实变化后，正在进行的交互能否更新或取消。
原型效果尚待验证，不预设它优于设计完善的正常界面。

## 2. 主演示脚本

初始任务正在巡查 A 区域，用户新增 B 区域，并要求保留 A 的原有重点要求与已完成工作。
所有任务、设备、影响计算与执行反馈均使用明确标注的模拟数据。

1. 用户选定 B，填写必要参数，查看新增区域对后续安排的影响预览。
2. 用户拖动 B 的一条边，继续在当前地图中编辑。
3. 系统保留已填参数、A 的要求及无关草稿，将依赖旧边界的面积、安排预览和相关校验标记为过时。
4. 模拟后台按新边界重新检查；如果原参数无法满足，保留用户原值并呈现冲突，不能自动降低要求。
5. 用户只修改或核查受影响部分，查看最新变化后提交。
6. 界面分别显示模拟后台已接受修改、安排已更新、收到执行反馈，不能把提交成功等同于执行完成。

主脚本中插入一次无关设备位置更新，检查地图编辑、输入焦点及草稿是否保持。
另设只缺一个参数和输入已齐全两个起始状态，检查是否出现重复补充。

## 3. 失联补充脚本

先出现装备失联与最后报告，明确哪些进展未知、后台正在做什么。
后台提出有依据的待决定事项后，用户开始填写处理意见。
随后分别回放两种变化：新反馈改变了可选处理方式，需要更新事项；联系恢复且新反馈明确消除了该事项，需要取消事项。
联系恢复本身不自动表示任务影响已经消失。

更新或取消时说明原因，保留原草稿供查看，并阻止过时决定继续提交。
旧草稿不能自动用于另一个设备、事项或策略。
另设仅恢复通信、任务进度仍未知的分支，检查界面是否继续如实呈现未知。

## 4. 公平比较

| 条件 | 正常界面 | 按影响引导的界面 |
| --- | --- | --- |
| 输入与地图 | 保存输入、预填已知值、字段校验、地图联动 | 相同 |
| 业务依据 | 相同任务数据、规则、影响预览和反馈 | 相同 |
| 局部修改后 | 在完整编辑区呈现更新结果、冲突和必要校验，用户自行检查 | 额外指出沿用项与受影响项，并组织当前需要补充或核查的内容 |
| 过时事项 | 显示状态变化并阻止无效提交 | 相同，进一步将当前操作引导更新到仍适用的事项 |
| 完整信息 | 可以查看完整输入与影响 | 同样可以，不能因局部引导而隐藏重要影响 |

两组共用草稿数据、业务校验和提交有效性检查，仅改变交互组织方式。
不能把输入丢失或允许过时提交设计成对照组缺陷。
若正常界面已有相同的局部引导行为，应重新界定实验差异，不能仅靠名称划分条件。

## 5. 实现位置建议

建议将可运行原型放在 `D:/xxq/work/generative-ui-platform/apps/web-workbench` 的独立实验入口中。
研究依据、实验方案与结果仍放在本研究仓库，不复制维护第二套前端实现。

检查现有 README、AGENTS.md 与相关源码后，可确认 Workbench 已有 Vue、MapLibre、地图选取与路线预览、路线征询组件，以及测试工具。
现有征询代码包含响应资格检查和失效接口，但这些不等于已经实现后台事件驱动的事项更新与草稿保存。
现有地图修改入口主要是路线修订位置标注；本次 B 区域的边界编辑和相关依赖检查仍需实现。

建议新增局部目录 `src/features/interaction-study/`，容纳实验页面、两种交互组织方式、草稿逻辑、确定性规则和模拟事件。
目录名与入口路径为建议，不代表代码已经存在。
复用现有地图基础和合适的 UI 组件；实验草稿按实验运行隔离，避免沿用现有路线征询的全局单例承载两组状态。

第一版规则直接在前端独立模块实现，模拟后台单独提供事实与提交检查。
草稿、影响预览与待决定事项记录适用对象及相关版本，收到旧计算结果时不能覆盖新边界下的结果。
提交时再次核对相关事实版本及事项状态，覆盖用户点击提交与后台更新同时发生的情况。
这些是本场景的局部实现，不扩展为通用 Runtime、Surface Lifecycle 或新的协议平台。

首版不依赖 LLM 或动态生成组件，以固定组件和明确规则验证交互组织。
未来接真实后台时再复用仓库已有的原生接入边界，并显式处理能力缺口。

## 6. 验收与记录

先按用户实际操作跑端到端流程，并检查地图、表单、焦点、提示和失效按钮的视觉状态。
功能检查至少覆盖以下事项：

- 修改 B 边界后，A 的要求、参数值和无关草稿保持。
- 旧影响预览不能作为当前提交依据，延迟返回的旧计算不能覆盖新结果。
- 无关后台更新不中断编辑。
- 规则检查失败时保留用户输入，并指出具体冲突。
- 待决定事项更新或取消后，草稿可追溯，旧按钮与提交入口均不能提交过时决定。
- 两组使用相同事件序列、数据、校验规则和模拟延迟。

用户比较记录完成时间、重复输入、重新查找、遗漏影响和判断错误，以及对当前适用事项的理解。
正式比较时平衡条件顺序，并使用等价任务，减少学习效应。
步骤减少不能单独作为成功依据；若重要影响被遗漏，应调整引导方式。

记录实现版本、实验条件、模拟事件及用户操作，以便复现。
两条预设脚本只能验证对应场景，不能证明规则泛化能力或论文新颖性。
