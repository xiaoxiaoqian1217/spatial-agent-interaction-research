# 情境驱动地图交互：对照与增量验证协议

> 2026-09-16 设计草案，尚未开展实验。招募数量、任务时长、分配顺序、阈值、题目和评分将在预试后冻结；预试数据不并入正式结果。当前不声称统计显著性、用户收益或长期疲劳改善。

## 1. 分别检验什么

- EQ1：情境、Need与策略是否符合任务证据及权限。
- EQ2：整套动态交互组织是否改善理解、判断、操作和核查。
- EQ3：显式Need表示相对直接情境映射是否有增量价值，其维护成本是否值得。

任务导出的交互需求不等同于用户真实意图。专家认同不等于用户收益；程序按规则运行也不等于规则本身合理。

## 2. 三个条件

| 条件 | 定义 | 控制要求 |
| --- | --- | --- |
| B0 固定组织 | 地图、任务列表、变化记录、编辑和反馈入口组织固定；数据实时刷新 | 必要信息、业务操作和安全告警完整，不人为隐藏证据 |
| B1 直接规则动态组织 | 完整情境及交互约束 → 策略，不建立显式Need表示 | 允许多因素判断、复用条件/策略、使用状态机；不能退化为单事件弹窗 |
| P 显式需求层 | 情境 → 带对象和依据的Need → 策略；保留对原情境的访问 | 同样使用规则/状态机，不使用LLM，不增加独享的后台或地图能力 |

三者共享事实与到达时序、数据质量、Agent执行能力、业务权限、可用业务操作、地图组件、候选方案、执行结果与必要告警。B1/P还共享策略候选集与交互保护规则。记录规则设计投入、调试样例和实现差异，不能仅给P更多开发时间或更完整证据。

固定组织不等于固定数据；动态规则界面不等于固定界面。Need不是隔离全部上下文的瓶颈，策略需要知道具体对象、风险范围和证据状态。

## 3. 现实可行的分阶段安排

### 阶段A：B1/P独立情境回放

1. 从两个既有案例构建开发集和保留集，覆盖正常、无须介入、组合变化、缺证据、连续修改、迟到反馈等分支。
2. 规则作者仅用开发集设计；保留集包含未用于调试的组合和反例。冻结后测试，若继续修改，重新建立保留集。
3. 业务评审者基于任务证据独立给出可接受需求/策略及理由。记录评审者背景、原始标注和分歧；不要只由规则作者给自己的输出评分。
4. 隐去条件名称并随机排列策略输出，评审信息是否充分、地图对象是否适当、打扰是否必要、操作是否符合权限。解释质量按“事实—约束—选择依据”评分，不因出现Need术语加分。
5. 向两者增加同一新分支，记录修改规则/模块数、修改耗时和回归错误；首次实现成本与后续修改成本分开报告。单作者计时仅作工程观察。

输出完全相同也是有效结果。此时不能期待内部多一层自然带来用户表现改善；可继续比较追溯与维护成本。未匹配率降低也不必然更好，应检查是否因过度触发造成误判。

### 阶段B：B0/P小规模用户对照

用于检验整套动态组织的效果。使用同难度但内容不同的等价脚本，平衡条件顺序和脚本分配，提供相同训练，避免同一答案重复出现造成学习效应。预先声明参与者是领域操作员、内部技术人员还是其他代理用户，分别记录相关经验。

优先采用被试内比较以适应招募条件；具体人数和任务时长按资源与预试确定，不预先保证检验效力。记录逐人配对表现、分布、失败/超时及不确定性；小样本以探索性证据表述，不能由满意度直接声称提升任务绩效。

### 可选阶段C：B1/P用户对照

只有要声称“需求层改善用户表现”时才需要该比较；控制条件同上。若A阶段两者交互输出相同或无明确差别，先评估是否有必要做该实验，并收缩结论。

## 4. 情境与评分冻结

两重点案例保留：异常后的自主接替、新增区域后的主动调整。至少覆盖同一事件在不同约束下应采用不同策略，以及不同事件可复用相同需求/策略的情况。

每个片段冻结：任务事实与证据时间、约束与权限、可接受Need集合、策略集合、用户操作集合、起止事件、终止/超时条件和评分理由。允许合理多解，不能把作者预设UI当作唯一标准答案。

| 指标 | 记录与分母 |
| --- | --- |
| 情境覆盖 | 能完整表达的预定义测试分支 / 全部预定义测试分支；另列遗漏字段 |
| Need漏判/误判 | 按四类分别记录，与独立标注比较；多标签一致性同时报告 |
| 未匹配与冲突 | 未匹配/出现冲突的待决策片段数 / 全部待决策片段数；另列解决与未解决冲突 |
| 策略适切性 | 可接受输出片段比例，并分别记录信息缺失、地图对象错误、不必要打断、权限问题 |
| 解释与复用 | 依据缺失数、新分支所需修改、回归错误和维护时间；不以代码行数单独证明优越 |
| 理解正确性 | 同一评分规则下的状态、变化、影响及未知项题目正确比例 |
| 介入判断 | 应介入片段中的漏介入；无需介入片段中的误介入，分开报告 |
| 空间调整 | 对象、范围、约束分别评分，不把一次任务成败掩盖为总分 |
| 落实核查 | 对完整、部分、失败、未知的分类正确性；依据独立执行证据 |
| 耗时与负担 | 固定事件起止，超时/未完成单列；记录操作数、视野打断、主观负荷及控制感 |

用户研究优先选理解正确性与介入/核查错误为主要指标，时间与负荷为次要指标；最终选择在预试后、正式实验前冻结，不能看结果挑指标。主观负荷若使用标准量表，须先核对原始量表与计分方法；自编问题明确标为探索性问项。

## 5. 记录与结论边界

保存条件、脚本版本、情境快照、命中规则与版本、Need（P）、策略、证据、用户操作、反馈、时间和评分。解释应来自记录，不能测试后补写一个看似合理的触发理由。

- A支持所测情境的策略/维护结论；不代表真实用户效果或全面泛化。
- B支持整套动态组织效果；不能单独证明需求层或Mixed Initiative的贡献。
- C才可能支持需求层的用户增量效果，仍受样本和场景限制。
- 短时研究不支持长期疲劳、持续警觉性或真实无人平台部署的结论。
- 若无收益、收益仅在少数分支或维护成本偏高，应如实报告并考虑直接映射方案。
